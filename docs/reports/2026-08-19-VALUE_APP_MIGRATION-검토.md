## 0. 총평

지시서의 **문제 진단은 정확하다.** 첫 화면 72장 노출이 최대 이탈 지점이라는 판단, 정확한 개수 요구의 압박, 결과가 워크북과 연결되지 않은 채 끝난다는 지적은 모두 원본 소스와 원본 문서가 자인하는 바와 일치한다. §6·§7 두 신규 화면의 **설계 의도**도 옳다.

문제는 **그 의도를 얹은 토대**다. 지시서는 원본 앱을 "퓨처나우 플랫폼이라는 빈 땅"에 옮기는 것으로 상정했으나, 퓨처나우 플랫폼은 이미 19명의 사용자·5개 차수·22건 참여·45건 갈무리가 도는 운영 시스템이고, 인증 모델·RLS 패턴·문안 규범·계약 구조가 전부 확정·잠금되어 있다. 지시서 §1의 "확정된 아키텍처 결정" 6줄 중 **DB 거점 1줄만 플랫폼 확정 사양과 일치**하고, 나머지는 플랫폼이 이미 반대로 결정해 둔 사항이거나 존재하지 않는 대상을 참조한다.

| 구분 | 건수 | 성격 |
|---|---|---|
| **반박** | 9 | 그대로 진행하면 사양 위반·보안 결함·구현 불가 |
| **보완** | 11 | 방향은 옳으나 빠진 것 |
| **수용** | 5 | 그대로 진행 |
| **지휘부 결정 필요** | 7 | 클코가 임의 판단하지 않음 |

**착수 판정: 보류.** 아래 Q1·Q2 두 결정이 나오기 전에는 V-1조차 착수할 수 없다. 둘 다 라우트 위치와 테이블 설계를 갈라 놓기 때문이다.

## 1. 반박

### R-1. 비로그인 익명 수집은 플랫폼 확정 사양의 정면 반대다 — 최대 쟁점

지시서 §1: "인증 : 초기 비로그인 (이름·이메일 입력)" · §3-2: `create policy … for insert to anon, authenticated with check (true)`

`architecture.md` §5.5 Q1이 정반대로 확정되어 있다.

> Q1 | **로그인 기반(비로그인 미허용)** | 실명제·인도자 전용. 현 RLS(`auth.uid()` 요구)와 일치

같은 문서 §6.2가 한 번 더 못 박는다.

> **실명제·인도자 전용**: SAIL의 익명 URL 공유 모델(`user_id IS NULL` 허용 SELECT 절)은 **제거**한다.

즉 플랫폼은 익명 경로를 **한 번 갖고 있다가 의도적으로 걷어낸** 이력이 있다. 지시서는 그것을 되돌리는 것이고, 이는 클코가 판단할 수 있는 범위가 아니라 ADR을 새로 세워야 하는 사양 변경이다.

**실측 근거 — 이 DB에는 anon 테이블 쓰기 선례가 0건이다.** 마이그레이션 41건 전수 확인 결과 `anon`에게 부여된 권한은 **오직 SECURITY DEFINER 함수 EXECUTE 3종**(`is_cohort_coach`·`is_cohort_member`·`resolve_cohort_by_code`)뿐이다. 테이블 DML은 예외 없이 `TO authenticated`이고, 심지어 중간저장 테이블은 주석에 이유까지 적어 두었다.

```
-- 권한: 로그인 사용자만(anon 불요 — 중간저장은 인증 경로).
   supabase/migrations/20260630134334_response_drafts.sql:34
```

`users`에 대해서는 `REVOKE UPDATE … FROM anon`을 명시적으로 걸어 두었다(`20260629100002:14`).

**보안 실질**: `with check (true)` + 익명 INSERT는 인터넷 누구나 교회 프로덕션 DB(SAIL·퓨처나우 공유 거점)에 임의 행을 무제한 삽입할 수 있는 표면이다. 레이트 리밋도, 참여자 검증도, 정리 경로도 지시서에 없다. 데이터가 "극소량"이라는 §1의 전제는 **정상 사용 시**에만 참이다.

**부수 결함**: 지시서 §3-2 마이그레이션에는 `GRANT INSERT … TO anon`이 없다. 이 저장소의 관례(모든 테이블 마이그레이션이 GRANT를 명시)를 따르지 않았고, 기본 권한 상태에 따라 정책만으로는 동작하지 않을 수 있다.

**권고 (강)**: 로그인 기반으로 되돌린다. 참여자는 이미 `/join` 코드 입력 → 계정 생성 → `enrollments` 결속을 거치므로, 가치 앱은 **결속 이후 자산**이 되면 된다. 그러면
- 이름·이메일 재수집이 사라진다(§3-1의 `name`·`email` 컬럼 자체가 불필요 — `users`에 이미 있다).
- 조회코드 RPC(R-8)가 통째로 불필요해진다.
- 개인정보 신규 수집이 0이 되어 §11의 고지 부담이 소멸한다.
- `user_consents`(라이브 18행)의 기존 동의 이력을 그대로 재사용한다.

접근성 우려(§1 "사전 과제 접근성")는 근거가 약하다. 참여자는 어차피 사전진단·갈무리를 하려면 로그인해야 하고, 갈무리는 라이브에서 45건이 실제로 기록됐다. 가치 앱만 로그인을 면제할 이유가 없다.

### R-2. `public.profiles`는 존재하지 않는다 — RLS 정책이 실행 불가

지시서 §3-2:

```sql
exists (select 1 from public.profiles p
        where p.id = auth.uid() and p.role = 'coach')
```

**라이브 실측 결과 `public` 스키마의 테이블 17종에 `profiles`는 없다.**

```
users · results · groups · group_members · coach_applications · user_contacts
cohorts · enrollments · responses · alerts · response_drafts · report_interpretations
user_profiles · user_consents · cohort_sessions · checkins · deltanote_preregistrations
```

역할은 `public.users.role`에 있고(`architecture.md` §5.1), 이름이 비슷한 `user_profiles`는 성별·생년·종교·신앙연수만 담는 별개 테이블이다(role 컬럼 없음). 이 정책은 마이그레이션 적용 시점에 `42P01 relation does not exist`로 실패한다.

**추가로 패턴 자체가 금지되어 있다.** `CLAUDE.md` §5:

> RLS는 `SECURITY DEFINER` 헬퍼(`is_admin` 등) 패턴을 따른다(architecture §6.1). **정책끼리 테이블을 직접 참조해 재귀를 만들지 않는다.**

`architecture.md` §6.1이 이 규율의 유래(SAIL이 Postgres 42P17 무한 재귀를 겪고 해결한 이력)까지 적어 두었다. 즉 테이블 이름을 `users`로 고쳐도 여전히 위반이다.

**교정**: `public.user_role(auth.uid()) IN ('coach','admin')` 또는 `public.is_admin(auth.uid())` 조합. 단 R-9를 함께 해결해야 한다.

### R-3. 저장 시점이 설계상 성립하지 않는다 — INSERT 전용 RLS인데 결과 화면에서 UPDATE가 필요하다

지시서가 정의한 흐름은 이렇다.

```
최종 3개 확정 → §7 내 말로 바꾸기 → §6 워크북 대조 입력 → 결과 화면
                                                         └ §6-2 정합 판정 3택 → alignment 컬럼에 저장
```

§6-2의 판정(`통합니다`/`조금 다릅니다`/`잘 모르겠어요`)은 **결과 화면 위에서** 일어난다. 그런데 §3-2의 RLS에는 **INSERT 정책과 SELECT 정책만 있고 UPDATE 정책이 없다.** 결과 화면 진입 시 행이 이미 삽입되어 있다면 `alignment`는 영원히 NULL이고, 삽입을 판정 이후로 미루면 §6-2가 "결과 화면 상단"에 있을 수 없다.

**더 큰 문제는 단일 삽입 구조 자체다.** 지시서의 설계는 전 과정을 클라이언트에 버퍼링하다가 끝에서 한 번 INSERT한다. 그런데 §4의 출발점이 바로 **이탈 방지**였다. 흐름 총 길이는

> 이름·이메일 → 카드 5화면(72장) → 2단계 → 3단계 → 쌍대비교 10회 → 최종 3개 → §7 → §6 → 결과

이고, 지시서는 이미 가장 지친 지점 뒤에 화면을 **두 개 더** 얹었다. 이 구간에서 이탈하면 앞의 모든 노동이 **0으로 저장된다.** 참여자에게도 손실이고, 운영 지표로도 "몇 명이 어디서 떨어졌는지"를 볼 수 없다.

**교정 (권고)**: 최종 3개 확정 시점에 **먼저 저장**하고, §7·§6은 증분 갱신으로 만든다. 익명 경로를 유지한다면 anon UPDATE 정책은 절대 열 수 없으므로(누구나 남의 행을 고친다) **SECURITY DEFINER RPC 2종**(`create_value_result` → id·코드 반환, `patch_value_result(id, code, …)`)으로만 쓰기를 허용해야 한다. R-1 권고대로 로그인 기반이면 `user_id = auth.uid()` UPDATE 정책 한 줄로 끝난다.

### R-4. "사전 과제"라는 시점 규정과 §6 워크북 대조가 서로를 부정한다

지시서 §0·§1은 이 앱을 **STEP 1 사전 과제**로 규정한다("사용 시점: 사전 과제(현장 사용 아님)").

그런데 §6은 이렇게 묻는다.

> STEP 1 워크북에서 **이미 찾으신 것들이 있습니다.**
> 라이프 커브에서 존재감이 가장 높았던 순간 / 패턴 찾기에서 찾은 나의 강점 / 재해석에서 발견한 나의 갈망

그리고 §8은 결과를 들고 **활동 5**로 가라고 한다.

세 문장을 나란히 놓으면 이 앱의 자리는 **활동 4와 활동 5 사이**다. 즉 STEP 1 **사전** 과제가 아니라 STEP 1 **진행 중** 과제다. 만약 정말 1회차 이전에 하는 것이라면, 참여자 전원이 §6에서 `건너뛰기`를 누르고 `alignment` 컬럼은 100% NULL이 되며, §6은 개발 비용만 쓰고 동작하지 않는 화면이 된다.

**플랫폼 실측이 이 모순을 더 키운다.** 1회차 갈무리(`session1.ts`)가 이미 같은 것을 디지털로 수집하고 있다.

| 지시서 §6 입력 | 플랫폼 기존 필드 | 출처 |
|---|---|---|
| 재해석에서 발견한 나의 갈망 | `desire_from` / `desire_to` — "오늘 바꿔 쓴 문장 한 쌍을 옮겨 주세요. (책 49~52쪽)" | `session1.ts:44-47` |
| (§7 내 말로 바꾸기의 귀착점) | `identity_sentence` — "오늘 완성한 존재가치 선언문을 그대로 옮겨 주세요. (책 53~58쪽)" | `session1.ts:53` |

`identity_sentence`의 placeholder는 `나는 ___의 가치를 최우선으로 여기며, ___하는 삶을 살기를 갈망하는 사람이다`(`session1.ts:57`)다. **§7이 만들려는 것이 정확히 그 첫 번째 빈칸이다.** 지시서 §7도 "이 재정의 결과가 존재가치 선언문의 앞 칸으로 그대로 들어간다"고 스스로 적었다. 그런데 지시서는 이 연결을 **종이로만** 하라고 한다(§8 "옮겨 적어 오세요"). 플랫폼에 이미 그 칸이 있는데 참여자에게 같은 문장을 두 번 쓰게 하는 설계다.

**또 하나의 내부 모순**: §6은 참여자에게 "어긋난다는 건 오히려 좋은 신호입니다"라고 말해 놓고, 같은 절 끝에서 "'조금 다릅니다' 비율이 높으면 앞 단계 설계 문제를 시사하는 운영 지표가 된다"고 한다. **같은 값을 한쪽에서는 좋은 신호로, 한쪽에서는 결함 지표로 쓴다.** 둘 중 하나를 버려야 한다. (권고: 참여자 문안이 옳다. 머리로 고른 가치와 삶이 증명한 가치의 불일치는 이 워크의 재료이지 앱의 버그가 아니다. 운영 지표로는 `건너뛰기율`과 `단계별 이탈률`을 쓴다.)

### R-5. 배치 위치가 계약 구조를 위반한다 — `app/values/`는 세 겹으로 틀렸다

지시서 §1: "경로 : `future.yebom.org/values` (App Router `app/values/`)"

**① 경로 문자열이 실제와 다르다.** 이 저장소는 `src/app/`이다(`architecture.md` §4). `app/values/`를 만들면 라우트로 인식되지 않는다.

**② 코드 소유 계층이 틀렸다.** `CLAUDE.md` §1·§2:

> `/src/core`는 `/src/instruments`를 참조하지 않는다. … 코어에 채점·리포트·**진단 고유 로직을 한 줄도** 넣지 않는다.

가치 카드 72장·단계 설정·성찰 질문·문안은 전부 **퓨처나우 고유 자산**이다. `src/app/values/`에 통으로 두면 앱 레이어에 인스트루먼트 로직이 눌러앉는다. 올바른 배치는

```
src/instruments/futurenow/values/
  cards.ts       ← values.json 을 TS 상수로 (fetch 제거)
  stages.ts      ← 단계 설정·범위
  copy.ts        ← 참여자 문안 (문안 원칙 잠금 대상)
  reflection.ts  ← 성찰 질문
  pairwise.ts    ← 쌍대비교 순수 로직 (단위테스트 대상)
src/app/…/values/page.tsx  ← 라우트·서버 액션만
```

**③ 라우트 위치가 동선과 어긋난다.** R-1 권고(로그인 기반)를 따르면 `/my/cohorts/[cohortId]/values`가 맞다. `proxy.guard.ts`의 `PROTECTED_PREFIXES`에 `/my`가 이미 있어 **미인증 차단이 자동으로 걸린다.** 최상위 `/values`는 보호 목록에 없어 별도 게이트를 손으로 붙여야 한다.

> 참고: 지시서 §11의 "미들웨어 matcher는 negative-lookahead 구조이므로 신규 경로가 자동 포함된다. matcher를 좁히지 않는다"는 **정확하다**(`proxy.guard.ts:24-31`의 S-1 불변식과 일치). 다만 이 저장소에서 그 파일 이름은 미들웨어가 아니라 **`proxy.ts`**다(Next 16 규약). 그리고 matcher 커버리지는 *신원 헤더 위조 strip* 보장이지 *인증 게이트* 보장이 아니다 — 게이트는 `PROTECTED_PREFIXES`가 따로 정한다. 지시서가 이 둘을 같은 것으로 읽고 있다.

### R-6. 참여자 문안이 플랫폼 문안 규범과 충돌한다 — 일부는 테스트가 실패로 잡는다

`futurenow_copy_principles.md`는 스스로 지위를 이렇게 선언한다.

> 지위: 문안에 관한 **최상위 규범.** 회차별 지시서·발주서가 이 문서와 충돌하면 **이 문서가 이긴다.**

그리고 그 규범은 선언에 그치지 않고 **회귀 테스트로 잠겨 있다**(`copyRegression.test.ts`, `session1~4.test.ts`).

| 지시서 문안 | 위반 | 근거 |
|---|---|---|

### R-7. 카테고리 묶음 노출은 원본 앱의 제1원칙을 깨고, 선택 분포를 왜곡한다

§4-1의 5묶음 분할은 산술은 정확하다(실측 대조 결과 14/13/13/13/19 = 72, 카테고리 18종 배분 일치). 문제는 산술이 아니다.

**① 앱의 존재 이유와 충돌한다.** 원본 `docs/00-HANDOVER.md`가 서비스 핵심 원칙을 이렇게 못 박았다.

> 사용자가 사회적으로 "중요해야 한다"고 생각하는 항목이 아니라, **마음이 끌리고 자신다움을 느끼는 가치**를 발견하도록 돕는 것

`docs/02` §2는 금지 패턴까지 명시한다 — "정답·우열·**사회적 기준을 암시하는 표현**". 그런데 §4-1이 붙이는 화면 제목은 정확히 사회적 영역 프레임이다. **"사람과의 관계에서" / "나의 태도와 됨됨이에서" / "세상과 나의 자리에서."** 이 제목이 붙는 순간 질문이 "무엇에 끌리는가"에서 **"이 영역에서 나는 무엇을 중시해야 하는가"**로 바뀐다. 원본이 카드를 섞어 놓은 것은 게으름이 아니라 설계였다.

**② 분포가 기계적으로 왜곡된다.** 카테고리 크기는 14부터 1까지 편차가 크다(관계 14 : 물질 1). 화면을 카테고리로 나누면 참여자는 화면당 개수를 **비슷하게 맞춘다**(순차 화면의 알려진 배분 행동). 결과적으로 관계 14장에서 3~4개, 물질 1장에서 1개가 뽑혀 **작은 카테고리가 구조적으로 과대 대표**된다. 카드 세트 설계자가 관계에 14장을 배정한 의도가 화면 분할로 상쇄된다.

**③ 예산 배분 문제가 실제 UX 결함을 만든다.** §4-2는 총량을 15~25개로 잡았는데, 이 총량을 5화면에 나눠 쓰게 하면서 **뒤 화면을 미리 보여주지 않는다.** 1화면(관계)에서 마음 가는 대로 12개를 고른 참여자는 5화면에 도달했을 때 남은 예산이 3개다. 뒤로 가서 지우게 만들거나, 상한을 무시하게 만든다. 둘 다 §4가 없애려던 압박을 형태만 바꿔 되살린다.

**권고 — 카테고리를 버리고 분할만 취한다.**

1. 72장의 표시 순서를 **카테고리가 섞이도록 고정 배열**한다(참여자별 셔플 아님 — 재개·비교 가능성 유지. `core/response/ordering.ts`에 제약 셔플 선례가 있다).
2. 그 배열을 15/15/14/14/14로 잘라 5화면. **화면 제목은 주제어 없이** "1/5" 진행 표시만.
3. **탐색 중에는 상한을 걸지 않는다.** 끌리면 다 고른다.
4. 5화면을 지난 뒤 **정리 화면 한 장**을 둔다 — 고른 전부를 한눈에 놓고 15~25로 줄인다. 여기서 처음으로 개수를 말한다.

이러면 §4의 목표(과부하 해소·개수 압박 완화)는 그대로 달성하면서 카테고리 편향과 예산 배분 문제가 동시에 사라진다. 화면 수도 같다(5 + 정리 1).

만약 지휘부가 주제별 화면을 유지하기로 결정한다면, 최소한 **화면 순서를 참여자마다 회전**시키고(첫 화면 효과 상쇄) **화면별 선택 개수를 표시하지 않는다.**

### S-4. `custom_value`와 §7이 같은 것을 두 번 한다

§3-1은 `custom_value`를 "원본 기능 유지"로 남겼다. 그런데 원본 저장소는 이 기능을 **정책 미결 레거시**로 분류해 두었다(`docs/06` §2.1 — "제거하거나 새 정책으로 전면 재구현"). 그리고 §7 '내 말로 바꾸기'가 하려는 것("표준 카드를 내 언어로 다시 쓴다")이 그 기능의 원래 의도를 더 낫게 구현한 것이다. 둘을 함께 두면 참여자에게 "3개 중 하나를 내 단어로 갈아치우기"와 "3개 각각에 내 문장 붙이기"가 동시에 나온다.

권고: `custom_value` 폐기. §7로 일원화.

```
@react-pdf/renderer · @supabase/ssr · @supabase/supabase-js · next · react · react-dom · zod
```

그리고 `CLAUDE.md` §8과 `design_system.md` §9가 UI 부품 출처를 지정한다 — 코어는 `/src/core/ui`(Button·Card·ProgressBar·CheckRow·TextArea·Stepper·ListRow…), 진단 전용 시각화는 인스트루먼트 소유. 즉 **컴포넌트 이식은 선택지가 아니다.** 화면은 기존 토큰·컴포넌트로 새로 짜야 하고, 셸은 `AppHeader variant='flow'`(출구 없는 선형 흐름 — 진입 5화면이 이미 쓰는 방식)가 가치 앱 단계 화면에 그대로 맞는다.

지시서 §2 표의 "UI 재구성"은 Sort 한 줄에만 붙어 있는데, **전 화면에 붙어야 한다.**

### S-6. Route Handler가 아니라 Server Action이다

§2: "tRPC 라우터 → Next.js Route Handler로 재작성"

이 저장소에 `route.ts`는 **0개**이고, 쓰기 경로는 전부 `actions.ts` 서버 액션이다(8개 파일). Route Handler를 새로 도입하면 인증 컨텍스트(`core/context.ts`)·에러 규약(`core/errors.ts`)·`VERIFIED_UID_HEADER` 전달 경로를 따로 배선해야 한다. 관례대로 서버 액션으로 간다.

### S-7. 스키마 보완 제안

R-1·R-3·R-9 결정에 따라 형태가 갈리지만, 어느 쪽이든 다음이 빠져 있다.

| 컬럼 | 이유 |
|---|---|
| `cohort_id` | R-9. 코치 격리의 유일한 근거 |
| `instrument_id` | 진단 간 격리 규약(ADR-14). 향후 SAIL·타 진단과 공존 |
| `card_set_version` | 카드 문구·구성이 바뀌면 과거 결과 해석 불가. 원본 `docs/02` §6이 이미 경고 |
| `client_request_id` (UNIQUE) | 원본의 중복 저장 문제(`docs/06` §4)가 그대로 따라온다. 세션 플래그는 탭 2개면 뚫린다 |
| `updated_at` | R-3 증분 저장 시 필수 |
| 보존기간 근거 | §11이 "보관 기간 명시"를 요구하는데 스키마·정리 경로가 없다. `deleted_at` 또는 정리 정책 |

**대안 검토 — 기존 `responses` 재사용**: `responses`는 `instrument_id`·`cohort_id`·`answers(JSONB)`를 갖고 있고 `wave`는 **nullable**이다(CHECK는 NULL을 통과). `instrument_id='futurenow_values'`, `wave=NULL`로 넣으면 RLS·불변성·코치 열람·본인 열람이 **전부 이미 구현되어 있다.** 신규 테이블 0, 신규 정책 0.
단 제약이 하나 있다 — 중간저장 `response_drafts`의 PK가 `(user_id, cohort_id, wave)`로 **`instrument_id`를 포함하지 않아**(`20260630134334:12`) 사전진단 작성본과 충돌한다. 중간저장이 필요하면 별도 draft 테이블이 필요하다. 이 선택지를 지휘부에 함께 올린다.

### S-8. 계정 승계 경로가 정의되지 않았다

§1은 "향후 세션 승계"라고만 적었다. `user_id`를 nullable로 두는 것만으로는 승계가 되지 않는다 — 나중에 로그인한 사람의 행을 **누가 어떤 근거로 잇는지**가 없다. 이메일 일치만으로 잇는 것은 R-8과 같은 취약점이다. R-1을 받아들이면 이 문제가 통째로 사라진다.

### S-9. '사전 과제'는 이미 쓰이고 있는 이름이다

참여자가 읽는 이행 약속문에 이미 있다.

```
'매주 모임시간을 잘 지켜 참석하고, 사전 과제와 사후 갈무리를 충실히 하겠습니다.'
   src/instruments/futurenow/copy.ts:121
```

여기서 '사전 과제'는 **사전진단**을 가리킨다. 가치 앱을 같은 이름으로 부르면 참여자·인도자 모두 무엇을 하라는 것인지 구분할 수 없다. 별도 호칭이 필요하다(§6-2 결정과 함께).

### S-10. 슬라이스에 빠진 것

| 빠진 것 | 근거 |

### S-11. V-1의 검증 기준이 §11과 자기모순이다

V-1 검증란: "`/values` 200, tsc 0"

지시서가 스스로 금지한 판정 기준을 슬라이스 표에 그대로 썼다. `CLAUDE.md` §9의 게이트 검증 규율(본문 콘텐츠 확인 + 리다이렉트 목적지 확인)에 맞춰 교정한다.

## 5. 권고 재설계 요약

Q1·Q2를 각각 '로그인 기반'·'1회차 직후'로 정한다는 전제에서, 위 반박·보완을 반영한 형태는 이렇다.

```
동선   /my/cohorts/[cohortId]  →  [가치 카드]  →  …/values
       ( /my 는 PROTECTED_PREFIXES 에 이미 있어 미인증 차단 자동 )

흐름   ① 안내 1장 (수집 없음 — 이름·이메일은 계정에 있다)
       ② 카드 5화면 (섞인 고정 배열 15/15/14/14/14 · 상한 없음 · 주제 제목 없음)
       ③ 정리 1화면 (여기서 처음 개수를 말한다 · 15~25)
       ④ 8~12개  →  ⑤ 정확히 5개
       ⑥ 쌍대비교 10회 (되돌리기 시 승수 복원 · 동점은 동점으로 표기)
       ⑦ 최종 3개  →  ★ 여기서 먼저 저장 ★
       ⑧ 내 말로 바꾸기 (증분 저장 · 값을 말하는 문안)
       ⑨ 대조 + 정합 판정 (증분 저장 · 건너뛰기 동등 비중)
       ⑩ 결과 (조회코드 없음 — 내 리포트에서 다시 본다)

코드   src/instruments/futurenow/values/{cards,stages,copy,reflection,pairwise}.ts
       src/app/my/cohorts/[cohortId]/values/{page.tsx,actions.ts}
       UI 는 core/ui + design_system 토큰. AppHeader variant='flow'

저장   Q3 결정에 따라 responses(instrument_id='futurenow_values') 또는
       value_assessments(cohort_id·instrument_id·card_set_version·client_request_id 포함)
       RLS 는 is_cohort_coach / is_admin DEFINER 헬퍼 경유
```

이 형태에서 지시서 §3-2의 RLS·§3의 RPC·§8의 조회코드·§1의 이름·이메일 수집이 전부 **불필요해지고**, 개인정보 신규 수집은 0이 되며, 남는 것은 §4·§6·§7의 UX 개선 — 즉 지시서에서 정말 값있는 부분 — 뿐이다.
