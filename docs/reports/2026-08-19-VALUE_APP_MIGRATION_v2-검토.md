## 0. 총평과 판정

**v2는 v1보다 결정적으로 낫다.** Q1(로그인 기반)·Q3·Q6 회신은 정확하고, §2 2단계 구조는 R-4가 지적한 시점 모순에 대해 내가 제안한 것보다 나은 답이다 — 나는 "시점을 하나로 고르라"고 했는데 v2는 **작업의 성격이 둘이라 시점도 둘**임을 보였다. §11-1의 재반박("카테고리를 버린다보다 상한을 걸지 않는다가 핵심 처방")도 옳다. 근거의 우선순위를 바로잡은 것을 수용한다.

그러나 v2는 **v1 검토가 다루지 않은 층**에서 걸린다. v1 검토는 지시서와 *확정 사양 문서*(architecture.md·CLAUDE.md·문안 원칙)를 대조했다. v2는 그 대조를 통과한다. 그런데 이 저장소에는 문서에 안 적힌 **구현 관례**가 있고, 그 관례가 곧 보안 경계다. v2 §3·§9는 그 층을 보지 못했다.

## 1. 착수 차단 3건

### B-1. 쓰기 권한 설계가 3주 전 지휘부가 명시적으로 기각한 형태다

v2 §3-2:

```sql
grant select, insert, update on public.value_assessments to authenticated;
create policy value_assessments_insert_own … with check (user_id = auth.uid());
create policy value_assessments_update_own … using (user_id = auth.uid()) with check (user_id = auth.uid());
```

세 겹으로 틀렸다.

**① `grant` 문이 무효다.** 라이브 `pg_default_acl` 실측 결과 이 프로젝트의 public 스키마 relation 기본값은 `anon=arwdDxtm`·`authenticated=arwdDxtm`(전 DML)이다. **`create table` 만 해도 authenticated 는 이미 INSERT·UPDATE·DELETE·TRUNCATE 를 갖는다.** v2의 `grant`는 이미 있는 것을 다시 주는 문장이고, 실효가 있는 것은 `revoke … from anon` 하나뿐이다.

저장소가 이 사실을 이미 문서로 남겼다.

```
-- 이 프로젝트는 default privileges 로 신규 public 테이블에 authenticated 전체 권한을 자동 부여한다
   supabase/migrations/20260727110000_checkins_revoke_write.sql:2
-- 테이블 단위 UPDATE 를 주면 참여자가 PostgREST 로 submitted_at 을 과거로 써서 … 조작할 수 있다.
--   애초에 주지 않는다.
   supabase/migrations/20260727100000_checkin_data_layer.sql:118-122
```

**② D1 규율(ADR-80)을 되돌린다.** 갈무리는 같은 상황에서 `INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER` 를 **명시 REVOKE** 하고 쓰기를 DEFINER RPC 로 일원화했다. 라이브 `pg_class.relacl` 이 그 결과를 보여준다 — `checkins → authenticated=rm`(읽기만). 반면 `responses·cohorts·response_drafts` 는 `arwdDxtm` 그대로다. **회수된 것은 갈무리 하나이고, 그것이 가장 최근의 지휘부 결정이다.**

이 플랫폼은 service_role 클라이언트를 쓰지 않는다. 전 경로가 anon 키 + 사용자 세션이므로([server.ts:20](src/core/supabase/server.ts#L20)) **PostgREST 는 참여자가 브라우저에서 직접 두드릴 수 있는 표면**이고 RLS·GRANT 가 유일한 방어다. v2대로 두면 참여자가 `stage='final'` 을 직접 써서 카드 탐색과 쌍대비교를 통째로 건너뛰고, 확정된 `value1~3`·`alignment`·`card_set_version` 을 사후에 덮어쓸 수 있다. §4-2 개수 규칙과 §2-3 "최종 3개 확정 후에는 잠근다"가 **클라이언트 전용 장식**이 된다. `TRUNCATE` 는 RLS 적용 대상이 아니라 회수하지 않으면 로그인 사용자 누구나 테이블 전체를 비울 수 있다.

**③ `is_cohort_member` 게이트가 없다.** 이 저장소에서 `cohort_id` 를 가진 테이블의 참여자 쓰기 정책은 **예외 없이** 멤버 게이트를 함께 건다.

| 테이블 | 정책 | 위치 |
|---|---|---|
| `responses` | `user_id = auth.uid() AND (cohort_id IS NULL OR is_cohort_member(cohort_id, auth.uid()))` | `20260626064658:248-251` |
| `response_drafts` | 동일 게이트 (insert·update 양쪽) | `20260630134334:24-28` |
| `checkins` | 동일 게이트 (방어 심층으로 존치) | `20260727100000:109-114` |

v2 §3-2는 "기존 `responses_select` 정책을 본으로 삼는다"고 적고 **SELECT 만 베낀 뒤 INSERT 선례를 떨어뜨렸다.** 결과: 로그인한 아무나 자기가 속하지 않은 차수의 `cohort_id` 를 실어 행을 넣을 수 있고, 자기 행의 `cohort_id` 를 남의 차수로 옮길 수 있다. 그러면 §3-2 SELECT 의 `is_cohort_coach(cohort_id, …)` 가 **그 차수 코치에게 낯선 사람의 `wb_peak`·`wb_strength`·`wb_longing` 원문을 열어 준다.** v1 검토 R-9가 세운 격리가 쓰기 쪽에서 되뚫린다. 반대로 자기 행을 다른 차수로 옮기면 담당 인도자 시야에서 사라진다.

> **교정.** §3-2 전체를 갈무리 선례로 다시 쓴다.
> ```sql
> GRANT SELECT ON public.value_assessments TO authenticated;
> REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
>   ON public.value_assessments FROM authenticated;
> REVOKE ALL ON public.value_assessments FROM anon;
> ```
> 쓰기는 self-scoped `SECURITY DEFINER` RPC 로 좁힌다 — `value_save_progress` / `value_finalize` / `value_patch`. 각 RPC 안에서 `is_cohort_member` · 개수 규칙 · `stage` 전이 · 확정 후 잠금을 **서버가 강제**한다. INSERT/UPDATE RLS 정책은 `is_cohort_member` 를 포함해 방어 심층으로 존치한다.
>
> 마이그레이션은 적용 후 수정 금지(`CLAUDE.md` §5)다. **V-3 전에 고쳐야 하고, 나중에 알면 보정 마이그레이션을 또 쌓아야 한다.**

### B-2. `value_assessments` 에 닿을 경로가 계획 어디에도 없다 — 계약 변경이 필요하다

**실측: `src/app` 과 `src/instruments` 전체에서 테이블 접근이 0건이다.** (`.from(` 4건이 잡히지만 전부 `sb.storage.from(BUCKET)` — Storage API 다.) DB 접근은 예외 없이 `/src/core` 안에 있고(42건), 앱·인스트루먼트는 **`CoreContext` 계약 메서드만** 부른다.

갈무리가 그 본이다. 인스트루먼트 전용 기능이면서도 DB 접근은 계약을 지난다.

```ts
// 회차 갈무리 카드 서버 액션(ADR-80). 코어 경유 — 쓰기는 전량 DEFINER RPC(checkin_*). 권한·게이트는 RPC 내부.
import { createServerContext } from '@/core/supabase/server';
…
const ctx = await createServerContext();
await ctx.saveMyCheckin({ cohortId, sessionNo, answers, flags });
   src/app/my/cohorts/[cohortId]/checkin/[session]/actions.ts:1-18
```

계약에는 `saveMyCheckin`·`getMyCheckin`·`submitMyCheckin`·`listCohortCheckins` 가 선언돼 있다([core-context.ts:146-156](src/contracts/core-context.ts#L146)).

즉 v2 §9가 배치한 `values/actions.ts` 가 `value_assessments` 를 읽고 쓰려면 **`/src/contracts/core-context.ts` 에 신규 메서드와 `domain.ts` 에 신규 타입을 더해야 한다.** 그런데 `CLAUDE.md` §1은 "**변경은 지휘부 승인 후에만** 한다"이고 `src/contracts/README.md:16` 이 같은 문장을 다시 새긴다.

**v2 지시서 전문에 '계약'·'contracts'·'CoreContext' 라는 낱말이 한 번도 나오지 않는다.** 승인도, 슬라이스도, 검증란도 없다. `CLAUDE.md` §11-4가 완료 보고에 "계약 대비 이탈 여부와 사유"를 요구하는데, v2는 그 항목이 발생한다는 사실 자체를 인지하지 못했다.

같은 뿌리에서 §8도 무너진다. §8은 "배선은 인스트루먼트 내부에서 처리한다. **코어를 경유하지 않는다**"고 했다. 이 저장소 구조에서 실행 불가능한 지시다 — 인스트루먼트에는 DB 접근 경로 자체가 없다.

> **교정.** ① §12에 **계약 슬라이스**를 신설하고 착수 전 지휘부 승인을 명시로 받는다(`domain.ts` +`ValueAssessment`, `core-context.ts` +조회/증분저장/코치열람 3종, `core/context.ts` 구현). 검증란은 "계약 델타 N + 승인 근거".
> ② §8의 "코어를 경유하지 않는다"를 삭제하고 실제 구조로 다시 쓴다 — **"순수 로직·문안·렌더 규칙은 인스트루먼트, DB 접근은 CoreContext 계약 메서드"**(ADR-80 갈무리와 동형).

### B-3. V-3 검증 다섯 축이 위 두 구멍을 그대로 통과시킨다

V-3 검증란은 `본인 / 타인 / 같은차수코치 / 다른차수코치 / 운영자` 다섯 축이다. **전부 읽기(SELECT) 축**이다. B-1의 쓰기 구멍은 이 매트릭스로 하나도 잡히지 않는다. 다섯 축이 전부 초록으로 통과하면서 "비멤버가 남의 차수에 행을 심는다"·"참여자가 개수 규칙을 우회해 `stage='final'` 로 뛴다"가 살아 있는 채로 **"역할별 실측 완료"가 보고된다.** `CLAUDE.md` §11-2의 "보안은 역할별 실측" 요구가 형식만 충족되고 실질은 거짓이 된다.

더해서 실행 조건이 안 적혀 있다. `tests/rls.integration.test.ts` 는 **옵트인 하니스**라 환경변수 없이는 조용히 SKIP 한다. "통과"만 보고하면 아무것도 검증하지 않은 것과 구별되지 않는다.

> **교정.** 검증란을 다시 쓴다 — `다섯 축 × SELECT` + **`비멤버 INSERT 거부`** + **`cohort_id 이전 시도 거부`** + **`직접 UPDATE 거부(has_column_privilege=false)`** + **`stage 역행 거부`**. 실행 커맨드와 통과 출력(SKIP 아님)을 보고에 싣는다.

## 2. 재반박 10건

### R2-1. 스키마가 v2 자신의 흐름을 담지 못한다 — 저장 지점이 2개뿐이다

5개 축이 독립적으로 같은 결론에 도달했다. v2는 R-3(선저장)을 "전면 수용"이라 판정했지만 **1차 내부와 2차 중반에는 적용하지 않았다.**

| 흐름 위치 | v2가 저장하는가 | 담을 컬럼 |
|---|---|---|
| 1차 카드 5화면 탐색 중 | **아니오** | 없음 |
| 1차 정리 화면 | **아니오** | 없음 |
| 1차 후보 확정 | 예 | `candidates` |
| 2차 5개 선정 | **아니오** | **없음** |
| 2차 쌍대비교 진행 | **아니오** | **없음** |
| 2차 최종 3개 | 예 | `value1~3` |

1차는 집에서 10~15분이다. 원본이 `localStorage` 24시간 복원을 넣은 이유가 그것이다([Sort.tsx:60-90](../../..)). 2차는 현장 7~8분인데 5개 선정과 쌍대비교 10회가 통째로 휘발성이다 — 원본조차 `values-step3`·`pairwise-progress` 두 키로 유지하던 것이다.

`stage` 가 `('candidates','final')` 2값이라 §2-3의 "이어하기"도 §6-3의 "단계별 이탈률"도 산출할 수 없다. §6-3이 R-4 후단 수용의 대가로 채택한 운영 지표 두 개가 **스키마에서 계산 불가능하다.**

> **교정.** `progress jsonb`(현재 화면·선택 집합·쌍대비교 승수·비교 인덱스)를 더하고 `stage` 를 최소 `('exploring','candidates','finalists','final')` 로 넓힌다. 계측용 `stage1_completed_at`·`stage2_started_at`·`finalized_at` 과 대조 건너뛰기를 값으로 남기는 `wb_skipped`(또는 `alignment` 에 `'skipped'` 허용)를 더한다. 화면 이동마다 증분 저장한다.

### R2-2. 1차에 '도달 불가 상태'가 되살아났다 — S-1이 없앤 결함이 한 칸 위로 옮겨졌다

§4-2 표: 카드 5화면 하한 **없음** → 정리 화면 하한 **12**(진행 차단).
§5-2 문구: 정리 화면은 "**15~25장**으로 줄여 주십시오".
§9: 셸은 `AppHeader variant='flow'` — **뒤로가기 없음**.

세 결정이 만나면 이렇게 된다. 카드 5화면에서 8장만 고른 참여자가 정리 화면에 도착한다. 진행이 차단되고, 안내는 "**줄이라**"고 말하며, 뒤로 갈 수 없고, 정리 화면은 §4-1대로 "고른 전부를 한눈에 놓고 **줄이는**" 화면이라 추가할 수단이 없다. **막다른 상태다.** 그리고 12·13·14를 고른 참여자에게는 게이트는 열리는데 문구는 15를 요구한다 — 수가 두 개다.

> **교정.** 셋 중 하나로 닫는다. (A) 카드 5화면 마지막에 하한 12를 걸어 정리 화면 진입을 보장한다. (B) 정리 화면에서 미선택 카드를 다시 열어 **추가**할 수 있게 한다(권장 — 상한 없는 탐색이라는 §11-1 처방과 결이 같다). (C) 정리 화면에 이전 화면 복귀를 두고 그것이 `variant='flow'` 의 예외임을 design_system 과 함께 확정한다. **어느 쪽이든 §4-2의 하한 수와 §5-2 문안의 수를 한 쌍으로 맞춘다.**

### R2-3. 참여자 문안 다섯이 §2가 새로 정한 시점과 어긋난다 — 그리고 V-9가 그것을 잠근다

| §6-1 헤더 | "**지난 시간에** 찾으신 것을 여기 옮겨 주십시오" | 지금 그 시간 안에 앉아 있다 |
| §6-2 라벨 | "**지난 시간에** 찾으신 것" | 동상 |
| §5-1 대체어 | '워크북' → "**지난 시간에** 찾으신 것" | 동상 |
| §6-2 '다릅니다' | "**1회차에서** 한 번 더 보십시오" | 지금이 1회차다 |
| §5-3 · §7 | "**1회차에 쓰실** 존재가치 선언문" | 같은 회차 뒷부분이라 아슬하게 참이나 오해를 부른다 |

1회차는 **첫 회차**다(`session1.ts` 표지 'FUTURE NOW · 1회차'). 참여자에게 '지난 시간'이라는 지시 대상이 아예 없다. 문안 원칙 §2-2가 정면으로 금지하는 것이다 — "그 페이지·그 문장은 혼자 읽을 때 무엇인지 모른다. **이름을 부르거나 위치를 말한다.**"

그리고 V-9가 이 문안을 **회귀 테스트로 잠근다.** 틀린 것을 잠그면 되돌리는 비용이 커진다.

> **교정.** "지난 시간에 찾으신 것" → "**오늘 찾으신 것**", "1회차에서 한 번 더" → "**오늘 남은 시간에 한 번 더**", "1회차에 쓰실" → "**오늘 쓰실**". 그리고 지시어 대신 대상의 이름이나 책 좌표를 부른다. **1차 화면은 미래형이 참이므로 1차용·2차용 문자열을 `copy.ts` 에서 `stage` 별로 분리한다.**

### R2-4. 참여자가 이 앱에 도달할 경로가 없다

V-1~V-11 어느 슬라이스도 진입점을 만들지 않는다. 참여자의 유일한 허브는 차수 홈([my/cohorts/[cohortId]/page.tsx](src/app/my/cohorts/[cohortId]/page.tsx))인데 v2에 그 파일에 대한 언급이 0건이다. **V-11까지 다 끝내도 URL 직접 입력 말고는 도달 불가다.**

부수 문제: `safeReturnTo` 화이트리스트가 갈무리 두 형태만 허용한다([safeReturn.ts:4-8](src/app/_lib/safeReturn.ts#L4)). values 경로가 없어 로그인 경유 진입이 `/home` 으로 떨어진다.

**진입 경로 두 개가 필요하고, 둘 다 선례가 있다** (지휘부 문의 2026-08-19 반영).

**(a) 차수 홈 카드.** 참여자의 유일한 허브가 차수 홈이고, 이미 상태별로 카드 순서를 바꾸는 구조다([page.tsx:150](src/app/my/cohorts/[cohortId]/page.tsx#L150) — "사전 미완이면 체크 먼저, 진행 중이면 갈무리 먼저"). 가치 카드를 한 장 더 끼우고 1차 미완 / 1차 완료·2차 대기 / 완료로 문구를 가른다. **`/`(공개 현관)나 `/home` 은 자리가 아니다** — 전자는 비로그인 화면이라 Q1과 충돌하고, 후자는 차수를 모르는데 이 앱은 차수 단위다(참여자가 여러 차수에 속할 수 있다 — 라이브 enrollments 22 / cohorts 5).

**(b) 짧은 공유 경로.** 1차는 집에서 하므로 인도자가 링크를 뿌린다. `/my/cohorts/<uuid>/values` 는 UUID 라 공유도 구두 안내도 불가능하다. 플랫폼이 이 문제를 이미 풀어 두었다 — 갈무리 QR 짧은 경로다.

```
// QR 짧은 경로(ADR-80). 현장 클로징에 열 명이 동시 진입 — UUID 경로는 구두 안내 불가.
//   흐름: 코드→차수 해석 → 미인증 /login?returnTo → 비멤버 안내(정지) → 멤버 /my/cohorts/{id}/checkin/{session}
   src/app/c/[code]/[session]/page.tsx:1-3
```

같은 형태를 복제한다 — `future.yebom.org/c/<가입코드>/values` → 코드 해석 → 미인증 `/login?returnTo=` 왕복 → **비멤버는 안내로 정지** → 멤버면 `/my/cohorts/<uuid>/values` 로 redirect. **비멤버를 `/join` 으로 보내지 않는 것이 핵심이다**(ADR-89) — 링크가 카톡으로 옮겨 다니므로 "링크만 있으면 누구나 실명제 차수에 자기등록"하는 표면을 열지 않는다. 가치 앱 링크도 똑같이 옮겨 다닌다.

구현상 `src/app/c/[code]/values/page.tsx` 로 두면 정적 세그먼트가 `[session]` 보다 우선해 충돌하지 않는다.

**명칭 주의.** 버튼 라벨로 '**존재가치**'는 쓰지 않는다. `identity_sentence` 가 이미 "존재가치 선언문"이고 1회차 갈무리의 필수 칸이라([session1.ts:53](src/instruments/futurenow/checkin/session1.ts#L53)) 같은 회차에서 한 이름이 두 물건을 가리키게 된다. 이 앱은 존재가치가 아니라 **선언문 첫 칸의 재료**다(§5-3·§7이 그렇게 적었다). v2 Q6 확정대로 '가치 카드'를 쓰되 S2-1대로 `_vocab/tool.ts` 원장에 넣는다.

> **교정.** 진입점 배선을 **V-5 직후 별도 슬라이스**로 신설한다(1차가 저장되는 시점 이후 — 그래야 링크가 의미를 갖는다). 차수 홈 카드 + `/c/[code]/values` 짧은 경로 + `safeReturnTo` 패턴 추가를 한 슬라이스로 묶는다. 배선 시점 이전까지 V-4~V-6의 미완 화면이 운영 차수 5건에 노출되지 않는지 함께 판정한다.

### R2-5. 코치 열람을 여는데 그 근거가 될 고지 문안이 없다

§12는 "개인정보 동의 슬라이스는 불필요하다"고 단정했다. **절반만 옳다.** 동의(`user_consents` 18행)는 재사용되지만 **화면 고지**가 빠졌다.

이 플랫폼은 코치 열람의 근거를 바로 그 고지에 결박해 두었다. `architecture.md` §6.2가 가시성 매트릭스를 설명하며 근거로 든 것이 저장 화면의 고지 문안이다 — *"적으신 내용은 인도자와 운영자가 읽습니다."* 사진에도 같은 고지가 붙는다(`LetterPhotos.tsx` — "첨부한 사진은 인도자와 운영자가 볼 수 있습니다."). 문안 원칙 §3은 이 자리를 축 1의 **예외**로 지정했다 — "프라이버시 고지는 부드러움이 아니라 정확함의 문제다."

§6-1의 `wb_peak`·`wb_strength`·`wb_longing` 와 §7의 라벨은 참여자 서술 원문이고 §3-2 RLS 로 같은 차수 코치가 읽는다. **고지 없이 열면 참여자에게 한 적 없는 약속을 어기는 것이 아니라, 한 적 없는 고지 위에서 읽는 것이다.**

> **교정.** §6-1 입력 화면과 §7 화면 하단에 갈무리와 동형의 고지를 넣는다. 문안은 축 1·2 예외 자리이므로 기존 문자열의 형태를 따른다.

### R2-6. 참여자 이동·삭제 경로 3종이 새 테이블을 모른다

라이브에 참여자 이동·제거·하드삭제 경로가 실재한다 — `participant_move`(`20260728140000`), `remove_cohort_member`(ADR-73), `deleteMember`(ADR-70). 셋 다 `value_assessments` 를 모른다.

`on delete cascade` 는 계정 삭제만 덮는다. **차수에서 제거된 참여자의 가치 결과는 남고, `is_cohort_coach(cohort_id)` 가 여전히 참이므로 코치 화면에 계속 보인다.** 다른 차수로 이동한 참여자는 응답은 따라가는데 가치 결과만 옛 차수에 남는다.

> **교정.** V-3 마이그레이션에 세 함수의 개정을 함께 싣는다. 어느 것을 따라가게 하고 어느 것을 지울지는 ADR-73/87의 기존 판단을 본으로 삼는다.

### R2-7. '2차 = 1회차 진행 중'을 강제하는 게이트가 없다

§2-2는 이 전제 위에서 R-4를 해소한다. 그런데 §2-3 구현 요구 4줄 어디에도 **시점 게이트가 없다.** 참여자는 1차를 마친 그 자리에서 이어서 2차를 할 수 있고, 그러면 §6 대조 화면은 v1과 똑같이 건너뛰기 100%가 된다. **R-4 해소가 참여자 선의에만 기댄다.**

> **교정.** §2-3에 다섯째 줄을 더한다 — "2차 개방 조건: `cohort_sessions` 의 1회차 개시 이전이면 2차 첫 화면을 열지 않는다(일정 미등록이면 현장 개시 신호로 대체)". 현장 개시 신호가 필요하면 그것이 인도자 쪽 작업이므로 §12에 슬라이스가 하나 더 생긴다.

### R2-8. §6-1이 세 칸 전부 공백을 정상 경로로 열어 두는데 §6-2에 빈 경우의 규칙이 없다

§6-1은 "세 입력 모두 비워도 진행된다" + 건너뛰기 버튼을 동등 비중으로 세운다. 그런데 §6-2는 그 값을 그대로 인쇄하고("봉우리: ○○ · 강점: ○○ · 갈망: ○○") "이 둘이 같은 곳을 가리킵니까?"를 묻는다. **왼쪽 열이 통째로 비면 질문이 성립하지 않는다.** v2에 (a) 셋 다 빈 경우 이 화면을 건너뛴다는 규칙도, (b) 일부만 채운 경우의 규칙도, (c) 빈 자리 문안 한 줄도 없다. V-8 검증란("건너뛰기 정상, alignment 저장")은 오히려 **건너뛴 참여자가 무의미한 `alignment` 를 남기는 것을 정상으로 통과시킨다.**

플랫폼은 같은 문제를 이미 계약으로 풀었다 — 되비추기 블록은 `empty` 문안 슬롯을 갖고, 앵커 키가 비면 나머지 값이 있어도 되비추지 않는다(`checkin/slots.ts`).

> **교정.** §6-2에 세 규칙을 정본으로 넣는다 — 셋 다 비면 화면 자체를 건너뛴다(`alignment` 미기록) · 일부만 있으면 있는 것만 인쇄한다 · 앵커(봉우리)가 비면 되비추지 않는다.

### R2-9. 성찰 질문 물량이 실측과 다르다

§11-2와 V-9는 "전용 질문 **49개** 재작성"이라 했다. 49는 `REFLECTION_QUESTIONS` 의 **키 수**이고, 그중 **9개는 72장에 없는 사문 키**다(사명·성공·우정·자기계발·재미·체면·탁월함·평판·행복). 실제 대상은 **카드 40장 · 질문 80개**다. 그리고 v2가 후순위로 미룬 32장이 **더 싼 쪽**이다(공통 3개로 이미 덮인다).

§11-2의 논거를 끝까지 밀면 — "최종 3개에만 붙는다 · 1회차 현장에서 인도자와 함께 다뤄진다" — **전용 질문 자체가 불필요하다.** 그리고 전용 40장 / 공통 32장이 섞이면 결과 화면에서 어떤 참여자는 전용 질문을, 어떤 참여자는 공통 질문을 보게 되어 품질 편차가 눈에 보인다.

> **교정 (재반박).** 숫자를 `40장 / 80문항 (사문 키 9 폐기)` 로 정정한다. 그리고 **전원 공통 3개로 통일**하는 안을 함께 올린다 — 더 싸고, 더 일관되며, v2 자신의 논거가 그것을 지지한다. 전용 질문을 유지한다면 80문항 전부가 문안 규범 통과 대상이 되어 V-9가 가장 비싼 슬라이스가 된다.

### R2-10. §10 결함 목록이 접근성과 카테고리 태그를 놓쳤다

**① 카드에 `#카테고리` 태그가 붙어 있다.** [`ValueCard.tsx:47-53`](../../..) 이 모든 카드 하단에 `#{value.category}` 를 렌더한다. §4-1이 화면 제목에서 주제어를 걷어내도 **카드마다 72번 되살아난다.** §4-1의 목적이 무력화된다. §10 결함 8종에 없다.

**② 키보드 조작 불가.** 카드 소팅의 `ValueCard` 는 `<button>` 이라 무사하지만, **쌍대비교·최종선택·결과 펼침은 전부 `<Card onClick>`(div)** 이다. `role`·`tabIndex`·키 핸들러가 없어 키보드로 조작할 수 없다. design_system §10("라디오/체크 `role`·`aria-checked`·키보드 Space/Enter")의 정면 위반인데 §10 결함 8종에 없다.

**③ §10-5의 "0/10 → 1/10" 교정은 원본이 이미 내린 결정을 되돌릴 수 있다.** 원본 진행률 표기가 의도된 것인지 확인이 필요하다. 새로 만드는 화면이라 실무 영향은 작으나, §10이 "원본 결함"으로 분류한 근거가 흔들린다.

> **교정.** §10 표에 ①②를 9·10번으로 추가한다. 특히 ①은 §4-1과 직결되므로 V-2(카드 상수화) 단계에서 "카테고리는 데이터에 남기되 **참여자 표면에 렌더하지 않는다**"를 명시한다.

| S2-8 | **동점 규칙 미완** | §10-4 "동점은 동점으로 표기"가 규칙이 아니다. 5개 10비교에서 3위 걸침 동점이 흔하다. 그때 최종 3개 화면이 무엇을 보여줄지 정본이 필요하다 |
| S2-9 | **§2-3 단축 경로(3화면)가 미배정** | 어느 슬라이스에도 없고, 72장을 3화면에 몰면 v1이 없앤 과부하가 돌아오며, 배열이 두 벌 필요해져 §4-1의 "고정 배열" 전제와 충돌한다. **대안: 화면 밀도는 유지하고 정리 화면만 생략한다** |
| S2-10 | **2차 시간 예산에 갈무리가 합산되지 않았다** | 같은 1회차에 갈무리도 한다(필수 5칸 · "약 4분"). 가치 앱 2차의 입력은 라벨 3 + 대조 3 + 판정 1 = **7칸**이다. 현장 총 디지털 부담이 12칸이 된다 |
| S2-11 | **design_system 에 없는 부품** | §6-1의 단일행 입력, 카드 그리드, 쌍대비교 2열이 §9 컴포넌트 목록에 없다. `CLAUDE.md` §8("확정 전 UI 임의 디자인 금지")에 걸리므로 design_system 갱신 슬라이스가 선행해야 한다 |
| S2-12 | **§7 예시 가치가 실재하지 않는다** | §7 모형이 쓰는 '진정성'·'연결'은 72장에 없다. 문안 확정 시 실제 카드명으로 바꾼다 |

**계획·규율 쪽 보완**: v2 헤더에 기준 커밋이 없다(ADR-102 발행 규율 — 현 HEAD `4e4d759`) · V-2~V-11 검증란에 tsc/린트/테스트 수와 접근성 항목이 없어 `CLAUDE.md` §11-2를 충족하지 못한다 · ADR 번호 108은 맞으나 이 작업은 ADR 한 개로 담기지 않는다 · OPEN_ITEMS #6(1·2회차 마음 칸 통일, "2기 시작 전 저장값 없을 때")과 V-10이 같은 파일·같은 시간 창을 다툰다 · 11슬라이스 보고가 `docs/reports/` 파일명 규약(지시서 슬러그 1:1)과 충돌한다.

## 6. 착수 가능 범위

§14의 "V-1 착수 가능하다"는 **맞다.** 다만 계획대로 가면 V-5에서 멈춘다.

| 슬라이스 | 판정 |
|---|---|
| **V-1** 골격 + 라우트 스캐폴딩 | **즉시 착수 가능.** 위 발견 중 어느 것도 막지 않는다. `safeReturnTo` 패턴 추가만 함께 넣는다 |
| **V-2** 카드 데이터 상수화 + 고정 배열 | **부분 착수 가능.** 72장 TS 상수화·id 1..72 보장 테스트는 지금 한다. 단 "카테고리는 참여자 표면에 렌더하지 않는다"(R2-10①)를 명시하고, 배열 판정 기준은 §4-1과 함께 확정한다 |
| **V-3** 마이그레이션 | **차단.** B-1·B-3 교정 + Q9 회신 후 |
| V-3.5 계약 | **신설 필요.** Q8 회신 후 |
| V-4 이후 | R2-1(스키마)·R2-2(도달 불가)·R2-3(문안 시점) 확정 후 |

지시하시면 **V-1과 V-2 착수분을 먼저 올리고**, Q8~Q11 회신을 받아 §3·§9 교정본과 함께 V-3으로 넘어가겠다.

## 부록 — 검증 방법과 기각분

6개 축(데이터·문안·배선·흐름·이식충실도·계획)을 병렬 검토하고, 축마다 **반증 전담**을 붙여 근거 줄번호를 직접 열어 확인하게 했다. 확신이 서지 않으면 기각 쪽으로 기울이도록 지시했다. 에이전트 12 · 도구 호출 220 · 원발견 83 → **기각 3 · 신규 15 · 생존 95**(차단 4 · 주요 28 · 경미 63). 본 보고서는 그중 중복을 병합해 35건으로 정리한 것이다.

라이브 실측은 거점 `zdoytzmvcafcebytttrm` 에 **읽기 전용**으로만 접근했다(`pg_default_acl`·`pg_class.relacl`·테이블 목록). 스키마 변경·데이터 조회는 하지 않았다.

**내 v1 검토의 오류 2건을 정정한다.** ① v1 §R-1 말미에서 "GRANT 가 없어 정책만으로는 동작하지 않을 수 있다"며 GRANT 추가를 권고했는데, 실제로는 **반대**다 — default privileges 가 이미 전권을 주므로 필요한 것은 REVOKE 다(B-1). ② v1 S-7의 `client_request_id UNIQUE` 권고는 append 모델을 전제한 것이라 v2의 1행 upsert 모델에서는 적용 대상을 잃었다(S2-3).
