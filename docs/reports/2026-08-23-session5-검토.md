## 0. 총평

**설계는 견고하다.** 4회차가 만든 구조(`back`·`Priors`·`neededBacks`·`pairText`·`group`·`order`)를 그대로 쓰고
새 위젯을 만들지 않는다는 원칙이 일관되며, 미결 일곱 건의 판정도 대부분 근거가 분명하다.
특히 **§1-#2(환경 사진을 받지 않는다)**·**§3-8(실행 동행 상자를 빼고 심화 ①로 대체)** 는
ADR-94 의 기준("도구가 있는가를 먼저 묻는다")을 스스로 적용한 좋은 판단이다.

다만 **코드로 대조한 결과 세 가지가 사실과 다르거나 선언 범위를 넘는다.**
그중 둘은 지시서가 정한 §9 완주 조건을 **그대로는 통과할 수 없게** 만든다.

|---|---|
| **반박** | 3 |
| **보완수용** | 4 |
| **수용** | 나머지 전부 |

## 1. 반박 ①  — 마음 낱말이 **둘** 겹친다. §9 완주 조건을 통과하지 못한다

### 사실

5회차 제안: `홀가분함` · `든든함` · `의욕` · `부담스러움` · `조바심` · `딱 맞는 말이 없음`

| 회차 | 마음 낱말(실측) | 충돌 |
|---|---|---|
| 1회차 | 후련함 · 먹먹함 · 놀라움 · 부끄러움 · 고마움 · 아직 모르겠음 | — |
| 2회차 | 설렘 · 막막함 · 벅참 · 두려움 · 간절함 · 아직 모르겠음 | — |
| 3회차 | 뜨끔함 · **홀가분함** · 조급함 · 담담함 · 해볼 만함 · 딱 맞는 말이 없음 | **홀가분함** |
| 4회차 | 선명함 · 아쉬움 · 두근거림 · 망설임 · **든든함** · 딱 맞는 말이 없음 | **든든함** |

`session3.ts` · `session4.ts` 에서 문자열 그대로 확인했다.

### 왜 반박인가

지시서 §1-#4 는 `홀가분함` 을 **1회차 `후련함` 하고만** 비교했다.

> *"1회차 `후련함` 과 어감이 가깝다는 지적이 맞다. 그러나 회차 간 낱말 겹침 금지는 **문자열 기준**이고
> 두 낱말은 다르다 … **§9 겹침 검증은 문자열 기준으로 통과한다.**"*

**통과하지 못한다.** 비교 대상이 1회차가 아니라 3회차였다. 그리고 §1-#4 가 다루지도 않은 `든든함` 이
4회차와 겹친다. 지시서 스스로 §7 에 `마음 낱말 앞 다섯이 1·2·3·4회차와 겹치지 않는다 (문자열 기준)` 를
넣었으므로, **그 테스트를 쓰는 순간 두 건이 레드로 뜬다.**

지시서 §1-#4 의 나머지 논지 — *"어감까지 겹치지 않게 하면 6·7회차에서 쓸 낱말이 남지 않는다"* ·
*"`홀가분함` 은 블록 1이 작동했는지 재는 유일한 지표다"* — 는 여전히 타당하다.
문제는 결론이 아니라 **대조 대상이 빠진 것**이다.

### 제안

두 낱말만 바꾸면 나머지 설계(면죄 셋 + 적재 둘, 부정 쪽 둘로 균형)는 그대로 산다.

| 자리 | 원안 | 대안 | 근거 |
|---|---|---|---|
| ① 면죄 | `홀가분함` | **`가뿐함`** | 짐이 내려간 감각을 그대로 유지. 3회차 `홀가분함`·1회차 `후련함` 과 문자열·어감 모두 구분된다 |
| ② 설계 | `든든함` | **`믿음직함`** 또는 **`할 만함`** | 4회차 `든든함` 회피. 다만 `해볼 만함`(3회차)과 가까우므로 **`믿음직함`** 을 권한다 |

**대안 최종 권고**: `가뿐함` · `믿음직함` · `의욕` · `부담스러움` · `조바심` · `딱 맞는 말이 없음`

`의욕`·`부담스러움`·`조바심` 은 1~4회차와 충돌 없음을 확인했다.

**지휘부가 겹침을 허용하기로 하면** §7·§9 의 겹침 검증 항목을 함께 내려야 한다.
지금처럼 문안과 검증이 어긋난 채로 두면 완주가 불가능하다. **어느 쪽이든 한 곳은 고쳐야 한다.**

## 2. 반박 ②  — `step`(다음 한 걸음) 위 되비추기는 **지금 구조로 불가능**하다

### 사실

`CheckinSession['step']` 타입에 `mirror` 가 없다.

```ts
step: {
  lastStep?: { key; label; options; note; mirror: Mirror };   // ← 여기에만 있다
  title: string;
  help: string;
  what: CheckinField;
  when: CheckinField;
  blocker: CheckinField;
  share?: { notice; toggleLabel };
};
```

되비추기를 그리는 자리도 셋뿐이다 — `CheckinCardClient.tsx` 의 `<MirrorOf>` 는
**1면 슬롯(`s.block.mirror`) · 심화 필드(`f.mirror`) · 지난 걸음(`lastStep.mirror`)** 에만 붙는다(457·482·499행).

`neededBacks` 도 같은 셋만 훑는다.

```ts
for (const s of orderedSlots(copy)) take(s.block.mirror);
for (const f of copy.deepen.fields) take(f.mirror);
take(copy.step.lastStep?.mirror);
```

### 왜 반박인가

지시서 §3-9 와 §4 는 **다음 한 걸음 블록 위**에 4회차 `domino_what` 을 되비추라고 한다.
그러려면 최소 넷을 고쳐야 한다.

1. `index.ts` — `step` 에 `mirror?: Mirror` 추가 (타입 변경)
2. `slots.ts` — `neededBacks` 에 `take(copy.step.mirror)` 추가
3. `CheckinCardClient.tsx` — 다음 한 걸음 블록 위에 `<MirrorOf>` 추가
4. `CheckinPreviewClient.tsx` — 미리보기에도 같은 자리

그런데 지시서 머리말은 범위를 이렇게 못 박았다.

> *"범위: `session5.ts` 신설 + 레지스트리 + 테스트. **DB·계약·마이그레이션 0. 새 위젯 0.**"*

그리고 §5 파일 목록에 `index.ts` 는 *"import + getCheckinSession 한 줄"* 로만 적혀 있고,
`slots.ts`·`CheckinCardClient.tsx`·`CheckinPreviewClient.tsx` 는 **아예 없다.**

`index.ts`·`slots.ts` 는 `/contracts` 가 아니므로 §9 의 *"계약 델타 0"* 은 지킬 수 있다.
그러나 **렌더 경로 변경은 문안 작업이 아니다.** 이 상태로 착수하면 §5 파일 목록 밖의 파일 셋을 건드리게 되고,
그것은 4회차 때 지휘부가 세운 "범위를 먼저 보고하고 승인받는다"(CLAUDE §3)에 걸린다.

### 제안 — 셋 중 하나를 골라 주십시오

**ⓐ 되비추기를 `lastStep` 위로 합친다(범위 유지 · 권고).**
`lastStep.mirror` 의 `keys` 를 `['step_what','step_when','domino_what']` 으로 늘리고
라벨을 `지난 시간의 한 걸음과 첫 도미노` 로 바꾼다. **코드 변경 0**, 문안만으로 끝난다.
잃는 것은 위치다 — 도미노가 '다음 한 걸음' 바로 위가 아니라 '지난 걸음 결산' 위에 뜬다.
다만 두 되비추기가 한 상자에 모이면 참여자가 **위(지난 것)와 아래(다음 것)를 한눈에 대조**하게 되어
오히려 나을 수 있다.

**ⓑ 타입·렌더를 넓힌다(범위 확대 · 명시 승인 필요).**
`step.mirror` 를 정식 도입한다. 6·7회차에서도 "다음 한 걸음 위에 무언가를 되비추는" 일이 반복될 것 같으면
이쪽이 옳다. ADR-103 이 `back` 을 일반화한 것과 같은 논리다.
그 경우 **ADR 을 따로 세우고(ADR-109) 파일 목록에 셋을 명시**해야 한다.

**ⓒ 이 되비추기를 뺀다.**
`step.help` 가 이미 *"오늘 활동 5에 적으신 2주차 칸이 곧 이번 주입니다"* 로 출처를 지목한다.
도미노를 다시 보여 주지 않아도 참여자가 어디서 옮겨 오는지 안다.

**ⓐ를 권한다** — 범위를 지키면서 정보를 잃지 않는다.

## 3. 반박 ③  — 미등록 가드는 **넷**이다. 지시서는 둘만 적었다

### 사실

```
readModel.test.ts:294   expect(buildCheckinRead(5, ANSWERS_1, OPEN, 'self')).toEqual([]);
session2.test.ts:95     expect(getCheckinSession(5)).toBe(null);
session3.test.ts:49     expect(getCheckinSession(5)).toBeNull();
session4.test.ts:54     expect(getCheckinSession(5)).toBeNull();
```

지시서 §5·§6 은 `session3.test.ts` · `session4.test.ts` **둘만** 적었다.
`session2.test.ts` 와 `readModel.test.ts` 가 빠졌다. 5회차를 등록하면 **넷 다 즉시 레드**가 된다.

### 왜 반박인가

같은 누락이 4회차 때도 있었다. 그때 메모가 둘을 지목했고 실제로는 셋이었으며,
완료 보고서(2026-08-16)에 그 사실을 남겼다. **이번에도 같은 자리에서 같은 방식으로 빠졌다.**

`readModel.test.ts` 의 것은 형태도 다르다 — `getCheckinSession` 이 아니라 `buildCheckinRead` 를 쓴다.
문자열 검색으로 `getCheckinSession(5)` 만 훑으면 영원히 안 잡힌다.

### 제안

§5·§6 을 **넷**으로 고치고, 전부 `(6)` 으로 이어 쓴다(지우지 않는다 — 그 단언은 미등록 회차가
링크로 새어 나가지 않는다는 가드다).

**그리고 이 반복을 끝내자.** 회차를 등록할 때마다 가드가 흩어져 있어 매번 놓친다.
**가드를 한 파일로 모으는 것**(예: `registry.guard.test.ts` — "등록되지 않은 회차는 null 이고 read 도 빈 배열")
을 6회차 착수 전에 제안한다. 이번 범위에 넣을지는 지휘부 판단이다.

## 4. 보완수용 ①  — §7 "1~4회차 last_step_result 넷 그대로"는 **1회차를 포함할 수 없다**

`session1.ts` 에 `lastStep` 이 **0건**이다. 1회차는 첫 회차라 되비출 지난 걸음이 없다
(`step.lastStep?` 가 선택 필드인 이유가 이것이다).

§7 체크리스트와 §9 완주 조건의 `1~4회차` 를 **`2~4회차`** 로 정정한다.
그대로 두면 1회차에서 `undefined.options` 를 읽어 테스트가 터진다.

`session2·3·4` 는 넷(`했습니다`·`조금 했습니다`·`잊고 지냈습니다`·`하려다 막혔습니다`)임을 실측 확인했다.
저장값 보호 논지(ADR-91 R1)는 그대로 타당하다.

## 5. 보완수용 ②  — `점수` 를 공용 BANNED 에 넣으면 **3회차가 깨진다**

§8 금지 어휘에 `점수` · `평가` 가 있고, §9 는 *"§8 금지 어휘가 참여자 문안에서 0건"* 을 완주 조건으로 건다.

그런데 **3회차 문안에 `점수` 가 둘 있다**(주석 아님, 리터럴).

```
session3.ts:21  { key: 'gap_area', label: '오늘 다섯 영역에 점수를 매기셨지요. …' }
session3.ts:61  label: '오늘 다섯 영역에 점수를 매기셨지요. …'
```

이것은 워크북에서 참여자가 **실제로 점수를 매긴 활동**을 가리키는 말이고, 측정 도구의 이름이 아니다.
ADR-107(용어 통일) 검토에서도 같은 이유로 남기기로 판정했다.

### 제안

§8 금지어 검사를 **5회차 전용으로 스코프**한다. §7 의 ADR-108 잠금 블록은 이미
`koreanLiterals('session5')` 로 한정돼 있어 옳다 — **§9 의 문장만 "5회차 문안에서 0건" 으로 좁히면 된다.**

공용 `BANNED`(허락 어휘 여섯)에는 손대지 않는다.

**같은 이유로 `체크` 도 안전하다** — `session2.ts` 에 한 번 나오지만 **주석**이고,
`koreanLiterals` 가 주석을 걷어내므로 잡히지 않는다. 확인했다.

## 6. 보완수용 ③  — `summaryFields` 의 `from/to` 는 원래 **교체·변화** 전용이다

`index.ts` 의 타입 주석이 규칙을 명시한다.

> *"쌍(from→to)은 **교체·변화**를 뜻한다. 나란한 두 값(영역+바람)에는 쓰지 않는다 — **화살표가 거짓말을 한다.**"*

§3-12 의 `{ label: '만약 → 나는', from: 'trigger_if', to: 'trigger_then' }` 은
교체가 아니라 **조건 → 행동**이다.

다만 4회차가 이미 `{ label: '첫 도미노', from: 'domino_what', to: 'domino_effect' }`(인과)로
규칙을 한 번 넓혔고, 조건도 **방향이 참인 관계**라 화살표가 거짓말을 하지 않는다.

**수용하되**, `index.ts` 의 그 주석을 *"방향이 참인 관계(교체·인과·조건)에 쓴다. 나란한 두 값에는 쓰지 않는다"* 로
함께 고칠 것을 제안한다. 규칙과 실제가 어긋난 채로 두면 6·7회차에서 또 판단이 필요해진다.

## 7. 보완수용 ④  — 심화 ②의 두 칸이 **짝으로 안 읽힌다**

`deepen.fields` 에는 `pairText` 의 `connector` 같은 시각적 연결 장치가 없다.
지시서도 그 한계를 알고 *"라벨 둘을 가진 인접 텍스트 필드 두 개로 둔다"* 고 했다 — 이 판단 자체는 옳다.

문제는 **책 참조의 위치**다.

```
[0] label: '오늘 만든 신호를 이번엔 첫 도미노에 걸어 본다면 — 만약 (책 230~231쪽)'
[1] label: '나는'
```

`만약` 과 `나는` 사이에 `(책 230~231쪽)` 이 끼어 **짝 읽기가 끊긴다.**
화면에서는 두 입력칸이 세로로 놓이므로, 첫 칸 라벨이 책 참조로 끝나면 둘째 칸의 `나는` 이 남남으로 보인다.

### 제안

책 참조를 **둘째 필드 끝**으로 옮기거나(`'나는 (책 230~231쪽)'`), 심화 ②에서는 빼는 편이 낫다.
`pairText`(§3-3)에 이미 같은 쪽수 `(책 230~231쪽)` 이 붙어 있어 **한 카드에 같은 참조가 두 번** 나오기도 한다.

`(책 230~231쪽)` 중복은 §11 표에도 그대로 적혀 있다 — 의도인지 확인이 필요하다.

## 8. 수용 — 근거가 분명해 그대로 받는다

| 항목 | 확인 |
|---|---|
| §0 4회차 구조 재사용 | `back?: number`(상한 없음) · `Priors` · `neededBacks` · `pairText` 전부 실재 확인 |
| §2 `identity` 슬롯을 문항 1에 | `identity?: BlockBase & CheckinField` — **라벨 + 한 줄 + 되비추기** 가 정확히 그 모양. `SlotName` 에 `'identity'` 있음. 2회차가 같은 슬롯을 쓴다 |
| §2 `order` 네 슬롯 | 타입 유효. `areaPick` 없음도 정합(존재하는 슬롯만 담는다) |
| §2 `slotBoundaries` 기대값 | `[캡션만, 선+캡션, null, 선만]` — 규칙(면 첫 블록·group 전이·group 밖)과 **정확히 일치** |
| §2 신규 키 여섯 · `step_blocker` 재사용 | 키가 같아도 회차 행이 달라 덮어쓰지 않는다 — 봉투 분리(ADR-103)로 이미 증명된 성질 |
| §2 `domino_*` 와 `trigger_*` 분리 | 층이 다르므로 키도 갈리는 것이 옳다. 한 칸에 덮으면 이층 구조가 사라진다 |
| §3-3 두 칸 강제 | 3회차 습관 짝·4회차 도미노 짝과 같은 **구조 강제**. `connector` 를 가로(`→ 그러면`)로 둔 근거도 타당 |
| §3-4 `question` 보이는 선택 | `question?: BlockBase & CheckinField & { badge?: string }` — `badge: '선택'` 지원 확인 |
| §3-5 `max: 2` · `딱 맞는 말이 없음` | 3·4회차와 동일. ADR-91 C 정합 |
| §3-7 결산 다섯째 신설 | 1기 실측 근거가 구체적이고, 1~4회차 불변 원칙(ADR-91 R1)을 스스로 지켰다 |
| §3-8 실행 동행 상자 제외 | ADR-94 기준을 정확히 적용. **읽을 데이터가 없는 상자를 만들지 않는다** |
| §3-9 `blocker.help` 3회차 문안 복귀 | *"그 재료를 받는 회차가 지금이다"* — 4회차가 넘긴 약속을 5회차가 받는다는 논리가 옳다 |
| §3-10 `defaultOpen` 미설정 | 7회차만 true 라는 타입 주석과 일치 |
| §1-#1 단톡방 분리 · §1-#2 사진 미수령 | 채널 경쟁·인증 성격 변화 논거가 타당. `letter_line` 게이트로 코드 변경 0 |
| §1-#3 골든타임 미수령 | 위젯을 미리 만들지 않는 판단이 ADR-94 와 같은 계열 |
| §11 책 참조 | 형식(`문장부호 + 반각 공백 + (책 N~M쪽)` + 문자열 끝)이 2·3회차 실측과 일치 |
| §3-11 save·done 4회차 복제 | 타당 |
| ADR-108 을 `architecture.md` 행으로 | 4회차 정정 ① 과 일치 |
