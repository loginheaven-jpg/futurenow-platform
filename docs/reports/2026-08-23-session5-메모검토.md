## 0. 총평

**일곱 건 판정을 전부 확인했다. 재반박할 것이 없다.**

메모가 내린 결정 넷 — 마음 낱말 대안 채택 · `step` 되비추기 ⓐ · 금지어 5회차 스코프 ·
`from/to` 규칙 갱신 — 은 근거가 정확하고 소스와도 맞는다.
특히 **ⓑ를 택하지 않은 이유**(*"반복이 확인되지 않은 일반화는 ADR-94 기준에 걸린다"*)는
내가 ⓑ를 선택지로 올린 것보다 나은 판단이다. 나는 "6·7회차에서 반복될 것 같으면"이라고 조건을 달았는데,
**아직 모르는 것을 근거로 일반화하지 않는다**는 쪽이 그 기준에 더 충실하다.

다만 메모가 **새로 결정한 것 셋**(가드 통합 앞당김 · 기존 넷 삭제 · 2기 시점 재설정)에
검증 결과 보완이 필요하다. 그리고 **내가 제안한 낱말 하나를 스스로 정정한다.**

| 구분 | 건수 |
|---|---|
| **재반박** | 0 |
| **보완수용** | 5 |
| **수용** | 나머지 전부 |

**보완 다섯 중 둘(①②)은 착수 전에 정해야 한다.** 나머지 셋은 진행하며 반영해도 된다.

## 1. 보완수용 ①  — 가드 넷을 "삭제"하면 **단언 넷을 함께 잃는다**

### 사실

메모 §3 은 *"기존 넷은 **삭제한다.** 통합 파일이 같은 것을 더 강하게 지키므로 남기면 중복이고,
중복은 다시 어긋난다"* 고 했다. 원칙은 옳다. **그러나 그 넷은 단독 줄이 아니다.**

```
session2.test.ts:88  it('1~4회차는 객체, 미등록(5)은 null', () => {
              89      expect(getCheckinSession(1)?.sessionNo).toBe(1);
              90      expect(getCheckinSession(2)?.sessionNo).toBe(2);
              91      expect(getCheckinSession(3)).not.toBe(null);
              92      expect(getCheckinSession(4)?.sessionNo).toBe(4);
              95      expect(getCheckinSession(5)).toBe(null);
              96      expect(getCheckinSession(0)).toBe(null);          ← 경계 방어
              97    });

session3.test.ts:47      expect(getCheckinSession(3)).toBe(c);          ← 객체 동일성
session4.test.ts:52      expect(getCheckinSession(4)).toBe(c);          ← 객체 동일성

readModel.test.ts:294    expect(buildCheckinRead(5, ANSWERS_1, OPEN, 'self')).toEqual([]);
              295        expect(buildCheckinRead(7, ANSWERS_2, OPEN, 'facilitator')).toEqual([]);
              296        expect(readSelfHighlights(5, ANSWERS_1)).toBeNull();   ← 다른 함수
              297        expect(anonNoticeText(5)).toBe('');                    ← 다른 함수
```

메모의 통합 스케치는 `it` 셋이고 `getCheckinSession` 과 `buildCheckinRead` 만 다룬다.
그대로 삭제하면 **네 가지가 사라진다.**

| 잃는 것 | 왜 중요한가 |
|---|---|
| `getCheckinSession(3)).toBe(c)` · `(4)).toBe(c)` | **객체 동일성.** 레지스트리가 복사본이나 다른 객체를 돌려주면 이것만 잡는다. `sessionNo` 만 보면 통과한다 |
| `getCheckinSession(0)` | **경계 방어.** 0·음수가 어떤 회차로 해석되지 않는다 |
| `readSelfHighlights` · `anonNoticeText` | **읽기 경로가 넷**이다. 둘만 지키면 나머지 둘이 미등록 회차에서 어떻게 되는지 아무도 안 본다 |
| `buildCheckinRead(7, …, 'facilitator')` | **모드 둘**(self·facilitator)과 **훨씬 뒤 회차**를 함께 본다 |

### 제안 — 삭제하되 통합 파일이 이 넷을 **흡수**한다

```ts
// registry.guard.test.ts
it('레지스트리가 문안 파일 객체를 그대로 돌려준다', …)   // ← 객체 동일성 (toBe)
it('경계 밖은 null — 0 · 음수 · 다음 회차', …)           // ← 경계 방어
it('읽기 경로 넷이 미등록 회차에서 파손되지 않는다', …)   // ← buildCheckinRead(self·facilitator) · readSelfHighlights · anonNoticeText
```

이렇게 하면 메모의 *"더 강하게 지킨다"* 가 실제로 참이 된다.
지금 스케치대로면 **더 약해진다** — 그것이 이 보완의 요지다.

## 2. 보완수용 ②  — `REGISTERED = [1,2,3,4,5]` 는 **같은 양식 문제를 남긴다**

### 사실

메모 §3 스케치:

```ts
const REGISTERED = [1, 2, 3, 4, 5] as const;
const NEXT = 6;
```

메모 스스로 진단했다 — *"두 번 반복된 것은 사람 문제가 아니라 **양식 문제**다."* 옳다.
그런데 이 스케치는 **회차를 등록할 때 고쳐야 할 곳을 넷에서 둘로 줄일 뿐**이다
(`index.ts` 의 레지스트리 한 줄 + 이 상수 두 줄).

6회차 때 `index.ts` 만 고치고 이 파일을 잊으면 `다음 회차는 null` 이 실패한다 — **좋은 실패**다.
그러나 다른 시나리오는 못 잡는다. 오타로 `if (n === 7)` 을 써서 **6을 건너뛰고 7이 등록되면**,
`REGISTERED=[1..5]` 는 그대로 통과하고 `NEXT=6` 도 null 이라 통과한다. **구멍이 조용히 열린다.**

### 제안 — 목록을 **파생**시키고 연속성을 단언한다

```ts
// 등록 회차를 손으로 적지 않는다 — 손으로 적은 목록이 4·5회차에서 연속으로 어긋났다.
const PROBE = Array.from({ length: 12 }, (_, i) => i + 1);
const REGISTERED = PROBE.filter((n) => getCheckinSession(n) !== null);
const NEXT = REGISTERED.length + 1;

// 문안 파일은 명시한다 — 등록됐는데 목록에 없거나, 목록에 있는데 미등록인 경우를 잡는다.
const FILES = { 1: CHECKIN_SESSION_1, …, 5: CHECKIN_SESSION_5 };

it('1부터 빈틈없이 이어진다', () => expect(REGISTERED).toEqual(PROBE.slice(0, REGISTERED.length)));
it('등록 회차 수와 문안 파일 수가 같다', () => expect(REGISTERED.length).toBe(Object.keys(FILES).length));
it('레지스트리가 문안 파일 객체를 그대로 돌려준다', () => { for (const [n, o] of Object.entries(FILES)) expect(getCheckinSession(+n)).toBe(o); });
it('경계 밖은 null — 0 · 음수 · 다음 회차', …);
it('읽기 경로 넷이 미등록 회차에서 파손되지 않는다', …);
```

**얻는 것** — 회차를 등록해도 이 파일에서 고칠 것이 `FILES` 한 줄뿐이고,
빈틈(5를 건너뛴 6 등록)과 불일치(등록됐는데 파일 목록에 없음)를 둘 다 잡는다.

메모가 겨눈 *"양식 문제"* 를 끝까지 밀면 여기까지 가야 한다.

## 3. 보완수용 ③  — 메모 §3 의 **표와 결론이 서로 모순**이다

§3 은 먼저 이어 쓰기 안을 표로 적는다.

```
readModel.test.ts:294   buildCheckinRead(6, …) → []
session2.test.ts:95     getCheckinSession(6) === null
session3.test.ts:49     getCheckinSession(6) === null
session4.test.ts:54     getCheckinSession(6) === null
session5.test.ts        getCheckinSession(6) === null   ← 신설
```

그리고 세 문단 뒤에 *"기존 넷은 **삭제한다**"* 고 한다.

**둘은 함께 설 수 없다.** 표대로 `(6)` 으로 이어 쓰면 삭제할 것이 없고,
삭제하면 표의 다섯 줄이 전부 무의미해진다. `session5.test.ts` 신설 가드도
통합 파일이 있으면 바로 그 중복이다.

**통합 안 하나로 정리할 것을 제안한다.** §9 수용 기준은 이미 통합 쪽으로 적혀 있으므로
(`registry.guard.test.ts 로 통합되고 기존 넷이 삭제됐다`) **표를 지우는 편이 맞다.**

## 4. 보완수용 ④  — `믿음직함` 은 이 자리에 맞지 않는다 (내 제안을 정정한다)

**이것은 내가 올린 대안이다.** 다시 보니 틀렸다.

`믿음직하다` 는 **대상을 향한 평가어**다 — "그 사람이 믿음직하다", "장치가 믿음직하다".
나머지 다섯(`가뿐함` · `의욕` · `부담스러움` · `조바심` · `딱 맞는 말이 없음`)은 전부
**자기 상태**인데 하나만 대상 평가라 결이 어긋난다.

`이 시간을 마치고 나온 지금, 마음은 어떤가요?` 에 `믿음직함` 으로 답하면
"(내 설계가) 믿음직하다"로 읽히고, 목록에서는 대상이 생략돼 그 뜻이 전달되지 않는다.

### 제안

| 후보 | 1~4회차 충돌 | 판정 |
|---|---|---|
| **`단단함`** | 없음 | **권고.** 설계가 섰다는 자기 감각. 4회차 `든든함` 과 어감이 가까우나 **메모 §1 이 확정한 원칙**(문자열 기준을 지키되 어감은 겹쳐도 된다)에 정확히 부합 |
| `뿌듯함` | 없음 | 차선. 다만 아직 실행 전이라 '해냈다'는 결이 이르다 |
| `안심됨` | 없음 | 수동적이라 WILL 파트와 결이 어긋난다 |

**`단단함` 을 권한다.** 한 가지만 밝혀 둔다 — 3회차에 `담담함` 이 있어 **한 글자 차이**다.
다만 참여자는 한 회차 목록만 보고, 인도자 집계도 회차별이라 실사용에서 섞일 자리가 없다.
그래도 걸리시면 `뿌듯함` 으로 간다.

**최종 권고**: `가뿐함` · **`단단함`** · `의욕` · `부담스러움` · `조바심` · `딱 맞는 말이 없음`

## 5. 보완수용 ⑤  — §8 의 "저장값이 없어 안전하다"는 **성립하지 않는다**

### 사실

메모 §8: *"시점을 `2기 1회차 갈무리가 열리기 전` 으로 다시 잡는다.
**아직 `checkins` 행이 없으므로** 저장값 파손 위험이 없다. 9/20 전에 처리하면 된다."*

DB 실측이다.

| 차수 | `checkins` 행 | 인원 | 회차 |
|---|---|---|---|
| 예봄 1기 | **42** | 11 | 1·2·3·4·5 |
| 예봄 2기 | **0** | 0 | — |

**2기는 0이 맞다. 그러나 1기에 42행이 있고 그것은 사라지지 않는다.**
1~4회차 문안을 고치면 1기 참여자가 자기 갈무리를 다시 열 때, 그리고 인도자가 그 기록을 볼 때
바뀐 문안을 본다. 시점을 언제로 잡아도 이 42행은 그대로다 — **조건을 영원히 만족할 수 없다.**

### 그런데 결론은 맞다. 근거만 틀렸다

**추가는 안전하다.** ADR-91 R1 이 경고한 것은 옵션의 **제거·교체**다 —
저장된 값이 목록에서 사라지면 그 답이 화면에서 지워지기 때문이다.
다섯째를 **더하는** 변경은 기존 네 값을 하나도 건드리지 않으므로 유령이 생기지 않는다.
1기의 42행은 전부 그대로 표시된다.

### 제안

근거를 바꾸면 **9/20 마감이 사라진다.**

> ~~2기 1회차 갈무리가 열리기 전 (저장값이 없어 안전)~~
> → **아무 때나 가능. 다섯째를 더하는 것은 제거·교체가 아니므로 기존 저장값이 유령이 되지 않는다(ADR-91 R1 은 제거·교체에 대한 규칙이다).**

**실제 비용은 다른 데 있다** — 1~4회차 문안을 고치면 `copyBaseline.json` 의 리터럴 잠금이
즉시 레드가 되므로 baseline 을 함께 갱신해야 한다. 그것이 이 작업의 유일한 실질 비용이고,
시점과는 무관하다.

이 정정이 실무에 주는 차이: **없는 마감에 쫓기지 않는다.** 5회차를 먼저 마치고 편할 때 하면 된다.

## 7. 착수 판단

**보완 ①②는 착수 전에 정해야 한다.** 통합 파일의 내용이 달라지고, ①을 반영하지 않으면
"삭제했더니 커버리지가 줄었다"가 된다.

**③④⑤는 진행하며 반영해도 된다.** ③은 문서 정리, ④는 낱말 하나, ⑤는 이월 항목의 근거 문장이다.

기본안대로 가도 좋다면 아래로 진행한다.

```
① 통합 파일이 흡수할 단언 넷을 명시 — 객체 동일성 · 경계(0·음수) · 읽기 경로 넷 · 모드 둘
② REGISTERED 를 파생시키고 연속성·파일수 일치를 단언
③ 메모 §3 의 이어 쓰기 표를 지우고 통합 안 하나로
④ 마음 낱말 둘째를 '단단함' 으로
⑤ 이월 항목의 근거를 '추가는 제거·교체가 아니다' 로 바꾸고 9/20 마감을 뗀다
```

**①②에 대한 회신을 주시면 그대로 완주한다.**
