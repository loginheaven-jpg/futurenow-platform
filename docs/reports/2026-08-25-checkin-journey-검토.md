# 반박 4

## ① §5-1 ⑤ 익명 제안 실명 노출 — 참여자 약속 위반이자 확정 결정 뒤집기 ★★

### 지시서

> *"`suggestion_anon` 이 참이면 **이름을 가리지 않는다** — 이 화면은 이미 한 사람 화면이라 익명이 성립하지 않는다. 대신 `익명 요청` 표시를 단다."*

### 현행 코드가 정반대입니다

`readModel.ts:195-199`:

```ts
// 바라는 점 — 참여자의 익명 토글을 존중한다(지휘부 결정 2026-08-02).
//   익명이면 여기(이름이 붙는 자리)에서 빼고, 회차 단위 무기명 섹션이 따로 모은다.
if (isSelf || !flags.suggestionAnon) {
  pushText(boxBlocks, box.suggestion.label, text(answers, box.suggestion.key));
}
```

무기명 수집 경로가 **이미 있습니다** — `readAnonSuggestion()` · `anonNoticeText()`, 그리고 회차 현황 `page.tsx:94`가 그것을 씁니다.

### 참여자가 읽고 체크한 문안 (1~5회차 동일)

```
이름 없이 전달합니다. 다만 인원이 적은 차수에서는 글의 결로 짐작될 수 있습니다.
```

**약속한 것은 "짐작될 수 있다"이지 "시스템이 이름을 붙인다"가 아닙니다.** 지시서 방식은 짐작이 아니라 **확정 식별**입니다.

### 게다가 화면 A가 자기 안에서 모순됩니다

§5-1 ⑦이 `CheckinReadView`를 `audience='facilitator'`로 재사용하는데, `buildCheckinRead`가 **익명 제안을 이미 뺍니다.** 그러면 같은 화면에서

- ⑤ 인도자에게 남긴 말 → 익명 제안이 **이름과 함께 보임**
- ⑦ 회차별 전문 → 같은 문장이 **빠져 있음**

같은 화면 안에서 한 문장이 위에는 있고 아래는 없습니다.

### 논거 자체가 거꾸로입니다

*"한 사람 화면이라 익명이 성립하지 않는다"* → 그러므로 **거기 실으면 안 되는 것**입니다. 익명이 성립하는 자리는 차수 단위 무기명 섹션이고, 그것이 이미 존재합니다.

### 제안

**⑤에서 익명 제안을 뺍니다.** `need`·`contact_request`는 그대로 모으고, `suggestion`은 `!suggestionAnon`일 때만. 익명분은 기존 무기명 섹션이 계속 집니다. `readModel`의 판정을 그대로 재사용하면 코드가 오히려 줄고 ⑤·⑦이 일치합니다.

## ② §5-1 ② 종단 축 = `summaryFields[0]` 이 성립하지 않습니다 — **착수 차단** ★★

지시서는 *"각 회차 `summaryFields[0]` 을 뽑아 세로로 세운다"* + *"라벨은 `summaryFields` 원문이다. 새 문안을 만들지 않는다"* 라고 했습니다.

### 실물 대조

| 회차 | 지시서 표의 라벨 | 실제 `summaryFields[0]` | |
|---|---|---|---|
| 1 | 갈망 | `{ label:'갈망', from:'desire_from', to:'desire_to' }` | ✓ |
| 2 | **인생의 한 문장** | `{ label:'영역', key:'future_area' }` | **✗** — '인생의 한 문장'은 `[1]` |
| 3 | **간절한 영역** | `{ label:'지금 가장 바라는 것', key:'gap_want' }` | **✗** — 그런 라벨이 어느 인덱스에도 없음 |
| 4 | 이번에 시작할 프로젝트 | `{ label:'이번에 시작할 프로젝트', key:'project_name' }` | ✓ |
| 5 | 바꾼 환경 | `{ label:'바꾼 환경', key:'env_change' }` | ✓ |

**"새 문안을 만들지 않는다"고 해 놓고 표 자체가 원문이 아닙니다.**

### 더 무거운 것 — 축이 어긋납니다

`index.ts:31`이 확정한 종단 축은 `갈망1 → 한 문장2 → 영역3 → 원씽4 → 환경5` 입니다. 이것을 `summaryFields` 인덱스로 옮기면

| 종단 축 | 인덱스 |
|---|---|
| 갈망1 | s1**[0]** ✓ |
| 한 문장2 | s2**[1]** |
| 영역3 | s3**[0]** ✓ |
| 원씽4 | s4**[3]** (`{label:'인생의 원씽', key:'onething'}`) |
| 환경5 | s5**[0]** ✓ |

**`[0]`을 기계적으로 뽑으면 다섯 중 둘이 축에서 벗어납니다.** 4회차는 `이번에 시작할 프로젝트`(우당탕탕 프로젝트 계열)가 나오고 정작 `인생의 원씽`이 빠집니다. **이 화면의 존재 이유가 §1인데, 그 축이 화면에 안 서게 됩니다.**

### 제안

`journey.ts`에 **인덱스 표 다섯 줄**을 둡니다. 라벨은 여전히 `summaryFields`에서 읽으므로 "새 문안 0"은 지켜집니다.

```ts
/** 종단 축(index.ts Mirror.back 주석) → summaryFields 인덱스. 라벨·키는 문안이 준다. */
const AXIS_INDEX: Record<number, number> = { 1: 0, 2: 1, 3: 0, 4: 3, 5: 0 };
```

`journey.test.ts`가 이 표가 가리키는 라벨을 문안과 대조해 잠그면, 문안이 바뀔 때 여기가 먼저 레드가 됩니다.

**대안이 필요하면 지휘부가 축을 다시 지정해 주십시오** — 어느 쪽이든 `[0]` 규칙으로는 안 됩니다.

## ① 명단에 운영자가 섞입니다 — §2·§3 제약 안에서 못 고칩니다

### 실측

1기 `enrollments` = **11명**. 그중 `role='user'` **9명**, 나머지 **admin 1 · coach 1**.

### 필터가 없습니다

```sql
CREATE FUNCTION cohort_member_directory(p_cohort_id uuid) ...
  SELECT u.id, u.name FROM enrollments e JOIN users u ON u.id=e.user_id
  WHERE e.cohort_id = p_cohort_id;   -- role 필터 없음
```

`MemberRef = { userId, name }` — **`role`이 없습니다.** `Enrollment = { cohortId, userId, joinedAt }` — 여기도 없습니다. 코드베이스의 `role === 'user'` 용례는 **전부 게이트**(보는 사람의 역할)이지 명단 필터가 아닙니다.

### 결과

화면 B 격자에 **운영자 2명이 참여자 행으로** 뜹니다. 그들은 제출하지 않으므로

- 1~4회차 전부 `empty` → **`연속 미착수` 주 신호가 켜집니다**
- 4회차 작성 중 1건(운영자) → **`작성 중 방치` 주 신호도 켜집니다**

인도자가 "오늘 연락할 사람" 목록에서 **자기 자신과 동료 운영자**를 봅니다. §5-2가 든 세 용도 전부에 잡음이 됩니다.

### 기존 결손을 상속하는 것입니다

회차 현황 `page.tsx:34`도 `listCohortMembers`를 그대로 씁니다. **지시서의 잘못이 아니라 이미 있던 구멍입니다.** 다만 기존 화면은 상태를 나열할 뿐이고, 화면 B는 **신호를 켜고 연락 대상을 고르는 도구**라 대가가 다릅니다.

§5-2의 *"11명 × 7회차가 한 화면에 든다"* 는 **11이 운영자 포함 수라는 것을 지시서가 몰랐다는 방증**입니다.

### 판단 요청 — §2·§3이 셋 다 막습니다

| 안 | 내용 | 걸리는 제약 |
|---|---|---|
| ⓐ | `MemberRef`에 `role` 추가 | §3 *"이것이 유일한 계약 변경"* · RPC 수정 필요 → §2 |
| ⓑ | RPC에 role 필터 | §2 *"DB·RLS·RPC 0"* · 기존 화면 출력이 함께 바뀜(회귀) |
| ⓒ | 그대로 두고 알려진 결손으로 기록 | 화면 B의 용도가 반쯤 죽음 |

ADR-110에서 같은 문제를 `u.role='user'`로 풀며 *"이름이 아니라 역할로 거른다 — 이름 목록은 운영자가 바뀔 때마다 낡는다"* 라고 적었습니다. 같은 원칙이면 ⓐ 또는 ⓑ인데, 둘 다 §2·§3 완화가 필요합니다.

그리고 §1-1이 한 문장 안에서 두 수를 씁니다.

> *"**작성 중이 12건이다.** 제출 24건에 작성 중 **14건**"*

표 합계는 14(운영자 포함), 12는 필터된 수입니다. **12가 맞습니다**(실측 일치).

### §6의 "12건"도 정확하지 않습니다

`작성 중 방치` = `drafting` **이고 `closes_at` 지남**입니다. 5회차는 08-29 마감이라 아직 안 지났습니다.

```
마감 지난 작성 중 = 1회차 1 + 2회차 4 + 3회차 3 + 4회차 2 = 10건
5회차 작성 중 2건은 아직 마감 전 → 신호 아님
```

**실제 주 신호 대상은 10건입니다.** 결론(작성 중 방치가 가장 큰 무리)은 그대로이나, 근거 수를 보고서에 적을 때 이 구분이 필요합니다.

## ③ `summaryFields`의 pair 변형을 §8이 안 다룹니다

`SummaryField`는 유니온입니다.

```ts
{ label, key } | { label, from, to }
```

**1회차 `[0]`이 pair입니다** (`desire_from` → `desire_to`). §5-1 표의 1회차 값이 화살표를 보여 주므로 인지는 하고 있으나, **§8 테스트 목록에 그 갈래가 없습니다.** 한 줄 더합니다.

## ④ §9의 "화면 C 잠금"을 §8 테스트가 못 잡습니다

§8은 전부 `journey.ts` **순수 함수** 테스트이고, §9는 *"화면 C — 자신감·남긴 말·신호가 없다 **(테스트로 잠금)**"* 이라 합니다.

**순수 함수가 옳은 값을 돌려줘도 컴포넌트가 그것을 화면에 안 그리거나, 반대로 다른 경로로 그릴 수 있습니다.** ADR-109에서 정확히 그 실패를 겪었습니다 — 심화 `placeholder`가 문안에 선언돼 있는데 `CheckinCardClient`가 안 넘겨서 화면에 안 나왔고, **리터럴 잠금·`copyBaseline`·금지어 검사가 전부 통과**했습니다. 그때 세운 것이 **배달 검증**(`renderToStaticMarkup` 산출물 단언)입니다.

§8에 한 줄 더합니다.

```
□ 화면 C 렌더 산출물에 자신감 숫자·인도자에게 남긴 말·신호가 없다 (renderToStaticMarkup)
```

지시서 §8이 스스로 *"화면 분기라 타입이 안 잡는다"* 고 썼는데, **순수 함수 테스트도 안 잡습니다.**
