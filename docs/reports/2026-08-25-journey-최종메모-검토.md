# 반박 2

## ① §1-1 임계 `3`의 근거 — ADR 번호가 틀렸고, 다른 종류의 수치입니다 ★★

### 메모의 근거

> *"임계 3의 근거는 **ADR-80 이래 `3 이하는 한 걸음을 잘게 쪼개 줄 사람` 으로 써 온 척도 감각**이다. 10점 척도에서 3점 이동은 구간을 하나 건너뛴 것이다."*

### 셋 다 확인했고 셋 다 어긋납니다

**ⓐ ADR 번호가 틀렸습니다.** `3 이하`를 척도 감각으로 쓴 것은 **ADR-80이 아니라 ADR-94**입니다. ADR-94가 *"3 이하 실참여자 제출분 1건"*, *"3 이하 응답이 3건 이상일 때 다시 올린다"* 로 씁니다.

**ⓑ 인용한 문장에 숫자 3이 없습니다.** `한 걸음을 더 잘게 쪼개 준다`는 **`confidence.help` 문안**입니다.

```
낮게 적힌 숫자가 인도자에게는 가장 쓸모 있습니다. 한 걸음을 더 잘게 쪼개 드릴 수 있거든요.
                                                    — session1.ts:110 · session2.ts:147 · session3.ts:194
```

`낮게`라고만 하고 **임계를 말하지 않습니다.** ADR-94가 `3 이하`를 별도로 정한 것이고, 두 개가 한 문장인 것처럼 인용됐습니다.

**ⓒ 결정적 — 두 `3`은 종류가 다릅니다.**

| | ADR-94의 3 | 메모의 3 |
|---|---|---|
| 무엇 | `confidence ≤ 3` | `이전 − 현재 ≥ 3` |
| 종류 | **절대값 임계** | **차이(낙폭)** |

**절대 임계에서 낙폭 임계를 도출할 수 없습니다.** `8→5`는 낙폭 3이지만 5는 낮은 값이 아니고, `3→2`는 낙폭 1이지만 둘 다 위험 구간입니다. *"10점 척도에서 3점 이동은 구간을 하나 건너뛴 것"* 이라는 보조 논거는 성립하지만, 그것은 **ADR-94와 무관한 새 논거**입니다.

### 이것이 §7이 방금 특정한 유형입니다

> §7: *"**지표 선택 오류** — `16건` 을 재료로 쓴 것. 쿼리가 맞아도 그 수가 그 판정의 재료가 아닐 수 있다. 이번에 처음 특정한 유형이고, 앞의 둘보다 잡기 어렵다."*
>
> *"앞으로 규율은 적는 순간 그 문서를 되짚어 확인하겠다."*

**§1-1의 임계 근거가 바로 그 확인을 통과하지 못했습니다.** ADR-94의 `3`은 실재하지만 **이 판정의 재료가 아닙니다.**

### 제안

임계 자체는 바꾸지 않아도 됩니다 — **근거만 정직하게 다시 씁니다.**

> 임계 3은 **새로 정한 값**이다. 10점 척도에서 3점 이동은 구간 하나를 건너뛴 크기이고, 1기 실측에서 낙폭 5가 1건 · 1~2가 3건이라 3이 둘을 가른다. **ADR-94의 `3 이하`(절대값 임계)와는 다른 종류의 수치이므로 그것을 근거로 삼지 않는다.** 1기 표본이 얇아 조정 근거가 없으므로 고정하고, 2기 데이터로 재본다.

## ② ADR-94의 재고 조건을 판정하지 않았습니다 ★

### ADR-94가 이미 이 자리를 다뤘습니다

> *"**B — 실행 자신감을 인도자 명단에 올리는 안은 기각**(지휘부 2026-08-07). … **ADR-86 표시 규율을 개정하지 않는다. `RosterEntry` 에 `confidence` 를 더하지 않았다.**"*
>
> *"**재고 조건을 못박는다** — 한 회차 제출이 **8건 이상**이고 그중 **3 이하 응답이 3건 이상**일 때 다시 올린다(둘 중 하나라도 미달이면 올리지 않는다)."*

ADR-94는 **판정 SQL까지 본문에 박아** 두었습니다. 조건 확인을 자동화하려는 의도입니다.

### 재측정 — 조건이 여전히 미충족입니다

| 재고 조건 | 기준 | 실측(1기 · `role='user'` · 제출) |
|---|---|---|
| 한 회차 제출 | ≥ 8건 | **최대 5건** — 미달 |
| 그중 `3 이하` 응답 | ≥ 3건 | **최대 1건** — 미달 |

전체 `3 이하`는 3건이나(`s1=2` · `s2=3` · `s4=2`) **한 회차 안에서는 최대 1건**입니다. ADR-94가 *"둘 중 하나라도 미달이면 올리지 않는다"* 고 못 박았고, **둘 다 미달**입니다.

### 그런데 최종 메모는 ADR-94를 한 번도 인용하지 않습니다

`자신감 급락`을 **주 신호**로 올려 격자 행 표식에 싣습니다. 화면 A의 자신감 **열**은 ADR-94가 인정한 *"ADR-86 펼침의 `scale` 블록"* 과 같은 층이라 무방해 보이지만, **격자 행 표식은 명단 층**입니다 — ADR-94가 기각한 바로 그 자리입니다.

숫자가 아니라 "급락"이라는 사실만 표시하므로 ADR-86의 금지 항목(*"숫자를 등급으로 바꾸는 표현"*)과는 다를 수 있습니다. **그러나 그 판정이 문서에 없습니다.**

### ADR-94 자신이 이 규율을 세웠습니다

> *"**규율 명문화: 승인된 ADR 의 근거를 다룰 때는 전부 인용한 뒤 각각을 따로 판정한다.**"*

이 규율은 **제가 ADR-86을 부분 인용해 반박했다가 기각당하면서 만들어진 것**입니다. 이번에는 반대로 지휘부가 인용을 생략했습니다.

### 제안

착수 전에 **한 문단**으로 판정을 남기면 됩니다.

> ADR-94 B가 기각한 것은 **`RosterEntry`에 `confidence` 값을 싣는 것**이고, 그 근거는 ⓐ 펼침에 도구가 있다 ⓑ 실측이 작다 ⓒ 문안의 약속을 펼침이 이행한다 셋이다. `자신감 급락` 신호는 **값이 아니라 변화 사실**을 표시하므로 ⓐ·ⓒ와 충돌하지 않는다. ⓑ(재고 조건)는 **여전히 미충족**이나, 그것은 *값을 명단에 올리는* 조건이지 *신호를 켜는* 조건이 아니다. **다만 1기에서는 이 신호가 1건만 켜진다는 것을 알고 간다.**

이 판정에 동의하시면 그대로 쓰시고, 아니면 신호를 보류하는 것이 맞습니다.

# 보완수용 4

## ① `인접 두 회차` 조건이 실재 급락의 절반을 놓칩니다

새 조건: `인접 두 회차 모두 응답 · 하강 폭 3 이상`.

### 재측정

| | 건수 |
|---|---|
| 인접 낙폭 ≥ 3 | **1건** (`1→2` 8→3) — 메모와 일치 ✓ |
| **비인접 낙폭 ≥ 3** | **1건 더** (중간 회차 미응답) |

자신감 응답자가 **9명 중 5명**이고 16건이 흩어져 있어 **인접 쌍이 자주 끊깁니다.** `인접`을 요구하면 중간에 한 회차만 비어도 급락이 안 잡힙니다.

### 제안

> `자신감 급락 = 직전 **응답 회차** 대비 낙폭 3 이상`

`인접`을 `직전 응답 회차`로 바꾸면 둘 다 잡히고, 조건이 오히려 단순해집니다. 근거 문자열에 회차를 담으므로(`2→4회차 급락`) 인도자가 건너뛴 것을 압니다.

| 문서 | 주 신호 |
|---|---|

보조는 `결산 악화` 하나뿐입니다. **다섯 중 넷이 주면 원안이 없애려던 상태와 실질적으로 같습니다.**

각 단계는 개별적으로 타당했습니다 — `자신감 급락`은 재료가 있고, `연락 요청`은 확실성이 높습니다. **문제는 누적입니다.**

### 제안

`연락 요청`을 **급이 아니라 종류로** 뺍니다.

나머지 넷은 전부 **코드의 추론**이고, `연락 요청`만 **참여자가 직접 손을 든 것**입니다. 메모 §1-2가 그 차이를 정확히 짚었습니다 — *"빈도가 아니라 확실성으로 급을 매기는 자리다."* **그러면 같은 축(주/보조)에 놓지 않는 것이 일관됩니다.**

```
돌봄 채널 (참여자 요청)  : 연락 요청
주 신호 (코드 추론)      : 작성 중 방치 · 연속 미착수 · 자신감 급락
보조                     : 결산 악화
```

주 신호가 셋으로 돌아가고 `연락 요청`은 오히려 더 눈에 띕니다.

## §2 `ⓑ'` 회귀 0 — 코드로 확인했습니다

`checkin/page.tsx`가 `members`를 **두 곳**에 씁니다.

```ts
const nameOf = (id) => members.find((m) => m.userId === id)?.name ?? '이름 미입력';
const memberIds = new Set(members.map((m) => m.userId));
const enrolled = checkins.filter((c) => memberIds.has(c.userId));  // ADR-84 등록 기준 필터
```

`onlyParticipants=true`로 부르면 **둘 다 의도대로 동작합니다** — `enrolled`가 운영자 갈무리를 빼고, 빠진 사람에게는 `nameOf`가 호출되지 않습니다. 무기명 제안(`anonSuggestions`)도 `enrolled` 기반이라 안전합니다(운영자 제출 0이라 실질 변화도 0).

나머지 넷(차수 상세·차수 목록·코치 홈·리포트 헤더)은 기본값 `false`로 무변경 ✓.
