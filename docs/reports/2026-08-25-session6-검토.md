# 반박 3

## ① §2-3 `save.notice2` 생략 — 전제가 틀렸고 §2-2와 자기모순입니다 ★

### 실측

1~5회차 전수:

```
s1~s5  save.notice1  언제든 다시 열어 고쳐 쓸 수 있습니다 · 다음 시간 24시간 전까지
s1~s5  save.notice2  적으신 내용은 인도자와 운영자가 읽습니다.
s2~s5  share.notice  이번 한 걸음은 다음 시간을 열 때 이름과 함께 나눕니다.
s1     share         (없음)
```

### 무엇이 틀렸나

**§2 서두의 전제**는 *"네 곳이 '다음 시간까지'라는 기한 위에 서 있다"* 입니다. **그런데 `notice2`에는 기한이 없습니다.** 기한은 `notice1`에 있고 §3.6이 이미 거기서 뺐습니다. `notice2`는 마지막 회차에서도 그대로 성립합니다.

더 무거운 것은 **§2-2와의 모순**입니다.

> §2-2: *"그러나 **열람 범위 고지는 남긴다** — 토글이 사라진다고 누가 읽는지까지 사라지면 안 된다."*

**§2-2가 지키겠다고 선언한 그것을 §2-3이 지웁니다.**

지시서가 `share.notice`를 열람 고지로 본 듯합니다. 그러나 실제 `share.notice`(2~5회차)는 *"다음 시간을 열 때 이름과 함께 나눕니다"* — **나눔 고지**입니다. 열람 범위 고지는 `notice2` 쪽입니다.

### 결과

**6회차만 카드 전체의 열람 주체를 안 밝히는 유일한 카드**가 됩니다. §3.5의 `share.notice`는 90일 한 걸음 **한 칸**에 대한 고지일 뿐, 마음·정체성·심화·마지막 한마디를 덮지 않습니다. 개인정보 동의(`열람 주체: 본인, 소속 그룹 인도자, 운영자`)와도 어긋납니다.

### 제안

`notice2`를 선택으로 만드는 **타입 변경은 그대로 두되**(향후 여지), **6회차는 `notice2`를 유지**합니다. 문안 한 줄이고 §2-3의 렌더 작업(`:328`·`:628`)이 사실상 사라집니다.

## ② §3.5 `share.notice`가 사실과 다릅니다

```
share: { notice: '적으신 90일 한 걸음은 인도자와 나만 봅니다.' }
```

**운영자도 봅니다.** ADR-77 §4.3이 열람 범위를 '운영자 포함'으로 확정하면서 `StartGuide`·`ResponseRunner`·갈무리 1~5회차 `notice2`·`LetterPhotos`·동의서를 **일부러 '인도자와 운영자'로 정직하게 갱신**했습니다.

이것은 **모집 카드 8과 같은 오류의 재발**입니다(2026-08-24 보고, 미조치). 그때는 모집 자료였고 이번엔 갈무리 카드입니다. 같은 실수가 두 번째로 문안에 들어오고 있습니다.

### 제안

```
share: { notice: '적으신 90일 한 걸음은 인도자와 운영자가 봅니다.' }
```

## ③ §1-4의 스타일 기준이 실물에 없습니다 — **착수 차단**

> §1-4: *"상자 스타일은 기존 `MirrorLine`과 같은 계열(**왼쪽 골드 세로선 · 표면1 배경**)"*

### 실측

`MirrorLine`(`CheckinCardClient.tsx:71-78`)은 **상자가 아닙니다.**

```tsx
function MirrorLine({ caption, value }: { caption: string; value: string }) {
  return (
    <div style={{ marginBottom: 'var(--space-3)' }}>
      <div className="t-caption" style={gray}>{caption}</div>
      <div className="t-body" style={{ color: 'var(--color-text-secondary)' }}>{value}</div>
    </div>
  );
}
```

테두리·배경·세로선이 **하나도 없습니다.** 파일 전체를 훑어도 골드 세로선 패턴은 없습니다. 존재하는 상자는 둘뿐입니다.

| 줄 | 패턴 |
|---|---|
| `:281` · `:570` | `accent-soft` 배경 (표지 강조 · 마지막 칸) |
| `:296` · `:581` | `surface-1` + hairline 테두리 |

### 왜 착수를 막나

**"같은 계열"과 괄호 안 명세가 서로 다른 것을 가리킵니다.** 어느 쪽을 따라도 지시 위반이 되고, `design_system.md` 확정 전 임의 디자인 금지(CLAUDE §8)라 제가 정할 수도 없습니다.

### 판단 요청

| 안 | 내용 |
|---|---|
| ⓐ | `MirrorLine` 실물대로 — **상자 없이** 줄만 쌓기 |
| ⓑ | **`surface-1` + hairline 상자**(`:296`·`:581` 계열) — **권장** |
| ⓒ | 골드 세로선을 **신설** |

ⓑ를 권합니다 — 이미 있는 패턴이고 §1-4의 *"하나의 상자 안에 줄을 쌓는다"* 취지에 맞습니다.

## ③ §3.5 `companion.help`가 ADR-102가 지운 어휘를 되살립니다

```
help: '이 과정에서 만난 분이든 원래 알던 분이든 상관없습니다. 이름 한 칸이 90일을 지탱합니다.'
```

`copyRegression.test.ts:71`이 **`'좋은 말이든 아니든 상관없습니다. 그냥 자주 나오는 말이면 됩니다.'`** 를 *"심화 — 옛 문안 넷이 모두 사라졌다"* 목록에 넣어 못 박고 있습니다.

`상관없습니다`는 BANNED 리터럴 여섯에 없어 **테스트는 통과합니다.** 그러나 ADR-102 진취 전환이 걷어낸 허락 어휘 계열이고 **문형까지 거의 같습니다**(`~든 ~든 상관없습니다`).

(`~어도 되고 ~어도 됩니다` 역시 같은 계열이라 피합니다.)

## 설계 판단도 동의합니다

- `Mirror`를 건드리지 않고 `MirrorSet`을 **얹는** 것
- `resolveMirror`를 **재사용**해 앵커·trim·`empty` 규칙을 상속시키는 것
- `MirrorSet` 항목에 `empty`를 두지 **않는** 것(다섯 줄 중 셋이 비면 결손 목록이 됨)
- 새 슬롯을 만들지 않고 `question`·`purpose`·`identity`에 모양으로 배정하는 것(ADR-90)
- 코어에 다중 회차 조회 메서드를 만들지 **않는** 것(ADR-94 — 반복 미확인)
- B → 중간 확인 → A 순서와 그 이유(A의 테스트가 B 없이는 컴파일되지 않음)
