## 0. 단계 2·3을 한 커밋에 담았다 — 사유

메모 §10 은 2(계약)와 3(코어 구현)을 나눠 두었으나 **분리하면 DoD 를 만족할 수 없다.**
`SupabaseCoreContext implements CoreContext`([core/context.ts:220](../../src/core/context.ts#L220))이므로
인터페이스에 메서드를 더하는 순간 클래스가 그것을 구현하지 않아 `tsc` 가 깨진다.

단계 2 만 커밋하면 **"tsc 0"을 못 채우고, 채운 척하려면 선택 메서드(`?`)로 만들어야 하는데
그건 계약을 느슨하게 만드는 설계 후퇴다.** 그래서 함께 간다. 보고는 지시대로 **계약 델타 중심**이다.

## 2. RPC 4 → 계약 3 대응표 (지시 3)

### 2.1 대응

| # | DB 함수 | 계약 메서드 | 호출자 | 비고 |
|---|---|---|---|---|
| 1 | `member_state(p_uid DEFAULT auth.uid())` | **`getMyMemberState()`** | 화면(본인) | 인자를 **넘기지 않는다** — 함수 기본값이 `auth.uid()`. 남의 상태는 운영자만, 그 게이트는 함수 안 |
| 2 | `list_membership_queue(p_expiring_days DEFAULT 30)` | **`listMembershipQueue(expiringDays?)`** | `/admin/approvals` | 대기 + 만료 임박 **한 벌**. `bucket` 열이 가른다 |
| 3 | `decide_membership(p_user_id, p_decision, p_valid_until, p_note)` | **`decideMembership({…})`** | `/admin/approvals` 액션 | 가드 전량 RPC 내부 |
| 4 | **`member_can_assess(p_uid, p_kind)`** | **없음 (의도)** | **서버 강제 전용** | §2.2 |

### 2.2 `member_can_assess` 는 왜 계약에 없는가 — 명시

**별도 메서드가 아니고, `MemberState` 에서 파생시키지도 않는다.** 셋째 자리다.

> **`member_can_assess` 는 응시 시작 경로의 서버 강제 장치이고, 단계 5에서 그 RPC 안에서 호출된다.**
> 화면이 부를 일이 없으므로 계약 표면에 올리지 않는다.

화면이 "이 항목이 열려 있는가"를 그리는 것은 **표시**이고, `MemberState` 하나만 있으면 그릴 수 있다.
그 매핑(`cohort`→둘 다 · `individual`→상시만 · 나머지→없음)은 **단계 5에서 앱 레이어의 순수 함수**로
두고, 단계 4의 진실표가 그것과 `member_can_assess` 를 **같은 픽스처로 함께** 잠근다.

이 배치가 발주서 §4.4 의 *"단일 순수 판정 함수 + 서버 강제 두 겹"* 을 채우는 방식이다.
**계약에 올리면 안 되는 이유**가 하나 더 있다 — 계약 메서드가 되는 순간 화면이 그것을 호출해
"버튼을 감추는 것"으로 안전을 삼으려는 유혹이 생긴다. §4.4 가 *"화면에서 버튼을 감추는 것은
안전장치가 아니다"* 라고 못 박은 자리다.

### 2.3 계약이 4가 아니라 3인 이유 (초안 §3-② · 이미 수용됨)

`list_membership_queue` 하나가 대기·만료 임박 두 갈래를 함께 돌려주므로
`listPendingMemberships` + `listExpiringMemberships` 2메서드가 **1메서드로 합쳐졌다.**
한 화면이 두 번 왕복하지 않고, RPC 도 4를 넘지 않는다.

## 3. 판정 비복제 — 무엇을 TS에 두었고 무엇을 두지 않았나 (지시 1)

| 판정 요소 | 위치 | TS 에 사본 |
|---|---|---|
| 우선순위 `held > cohort > 저장 > pending` | `member_state()` | **없음** |
| `cohort` 산출(`enrollments ⋈ cohorts`) | 〃 | **없음** |
| 만료 산출(`valid_until` < 오늘) | 〃 | **없음** |
| 만료 시계(KST) | `membership_today()` | **없음** |
| 유효기간 기본 개월수 | `membership_default_months()` | **없음** |
| 응시 가부 매핑 | `member_can_assess()` | **없음**(단계 5에서 표시용 순수함수 신설 · 단계 4가 함께 잠금) |

**TS 에 새로 생긴 판단은 하나뿐이고 판정이 아니다.**

```ts
function toMemberState(v: unknown): MemberState   // 경계 검증
```

DB 가 계약 밖 문자열을 내면 조용히 오타입으로 흘러 화면이 엉뚱한 분기를 타는 대신 **여기서 멈춘다.**
CLAUDE §9 의 "DB 는 느슨, 코드 경계는 엄격"에 해당한다. 값의 뜻을 해석하지 않고 **집합 소속만** 본다.

## 4. 상수 비복제 실증 (지시 2)

`listMembershipQueue` 가 돌려주는 `defaultValidUntil` 을 승인 화면이 그대로 쓴다.
**라이브 실측(읽기 전용·롤백)**:

```
default_valid_until = 2027-08-26     -- 오늘(2026-08-26) + 12개월
```

**`12` 라는 숫자가 TS 어디에도 없다.** IA §12-2 가 확정되면 `membership_default_months()` 한 곳만 고치면
승인 화면 기본값과 자동 전이가 **함께** 움직인다. 두 곳을 고칠 일이 생기지 않는다.

## 6. 라이브 배선 검증 — 열 이름 1:1 대조

계약 매퍼가 실제 RPC 응답과 맞는지 라이브에서 확인했다(읽기 전용 · `BEGIN…ROLLBACK` · **이름·이메일·전화 미조회**).

| 검증 | 실측 |
|---|---|
| `list_membership_queue` OUT 열 | `bucket,user_id,name,email,forum_name,forum_phone,signup_note,status,valid_until,created_at,default_valid_until` — **매퍼와 1:1** |
| 반환 행 수 | **2** (`pending` 2계정) — 정확 |
| `bucket` 값 | `pending` 만(만료 임박 0 — 체험 2행은 `valid_until` NULL 이라 창에 들지 않는다) |
| `default_valid_until` | `2027-08-26` |
| `forum_phone` 채워진 행 | **0** (`/signup` 수집은 단계 5) |
| `member_state(운영자)` | `pending` — 백필과 일치 |

### 6.1 열 이름 하나가 어긋난다 — 매퍼가 잇는다 (조치 불요 판단)

RPC 의 OUT 열 이름은 `status` 인데 담기는 값은 저장값이 아니라 **판정**(`member_state`)이다.
계약 이름은 뜻에 맞게 `state` 로 두고 매퍼 한 줄이 잇는다.

**고치지 않는다** — `RETURNS TABLE` 의 OUT 이름은 `CREATE OR REPLACE` 로 바꿀 수 없어 `DROP` +
재생성 마이그레이션이 필요하다. 지휘부가 `membership_on_cohort_archived` 의 EXECUTE 잔여에 대해
*"이것 때문에 마이그레이션을 하나 더 만들지 않는다"* 고 판정한 것과 **같은 급**이다.
그 파일을 다시 손댈 일이 생기면 함께 정리한다. **ADR-122 에 적는다.**
