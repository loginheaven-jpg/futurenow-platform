## 2. §4.2 판정 — 핵심

### 2.1 실측이 뒤집은 전제

발주서 §4.2 는 *"차수 회원 여부는 `enrollments` 가 이미 알고 있다"* 고 썼다. **`enrollments` 는 그것을 모른다.**

라이브 실측(2026-08-26):

| code | 이름 | status | 인원 |
|---|---|---|---|
| HMT7Z | 퓨처나우2026예봄1기 | active | 11 |
| ZR4KB | 퓨처나우2026예봄2기 | active | 9 |
| **JOINF** | **체험 진단** (예약 차수 · ADR-63) | active | **4** |
| **TRASH** | **휴지통** (소프트 삭제 · ADR-84) | active | **1** |
| **QKN2H** | **test** | active | **2** |

`enrollments` 는 `(cohort_id, user_id, joined_at)` 셋뿐이고 `cohorts` 에는 **차수의 성격을 가르는 컬럼이 없다.** 다섯 개가 전부 `status='active'` 다.

따라서 `EXISTS(enrollments)` 로 판정하면:

- **휴지통에 버린 사람이 차수 회원이 되어 진단 응시 자격을 얻는다.** 정확히 반대다.
- 체험 진단 참가자 4명이 세미나 회원이 된다 — IA §5.1 의 자격 근거("세미나 등록")를 만족하지 않는다.

지금 이 셋을 가르는 유일한 표식은 **코드 문자열**이다. `GENERAL_CODE = 'JOINF'` 는 앱층 상수로 존재하지만(`src/app/_screens/entry/general.ts`), **휴지통은 코드에 상수조차 없다** — `CohortDetailClient` 주석의 한국어 "휴지통"뿐이고, 이동 대상은 `listAllCohorts()` 전체에서 운영자가 눈으로 골라 누른다.

ADR-110 이 `cohort_seats_taken` 에서 세운 규칙이 그대로 걸린다 — **"이름이 아니라 역할로 거른다. 이름 목록은 운영자가 바뀔 때마다 낡는다."** 코드 문자열 화이트리스트는 정확히 그 이름 목록이다.

### 2.2 저장과 산출을 상태마다 나눈다

다섯을 한 축으로 보면 답이 나오지 않는다. 출처가 다르기 때문이다.

| 상태 | 진실의 출처 | 처리 |
|---|---|---|
| `cohort` 차수 회원 | `enrollments ⋈ cohorts` — **이미 DB 에 있다** | **산출.** 저장하지 않는다 |
| `pending`·`individual`·`expired`·`held` | **운영자의 결정.** 어디에도 없다 | **저장.** 저장 외에 방법이 없다 |

**선결 전제 — `cohorts.kind`**

```sql
cohorts ADD COLUMN kind text NOT NULL DEFAULT 'seminar'
  CHECK (kind IN ('seminar','general','trash'))
```

- 이것은 **차수 소속의 이중 기록이 아니다.** 차수의 성격은 차수의 사실이고 `cohorts` 가 그 유일한 주인이다. 발주서 §11-9 가 금지한 것은 "이 사람이 차수 회원인가"를 복사하는 것이고, 그 사실의 주인은 여전히 `enrollments` 하나다.
- 백필: `JOINF`→`general`, `TRASH`→`trash`, 나머지→`seminar`(`QKN2H` test 는 §9 질의 ②).
- 부수 효과 — **ADR-63 예약 차수 보호와 ADR-84 이동 대상 목록이 코드 문자열 대신 구조적 사실을 보게 된다.** 지금 `deleteCohortAction` 이 `cohort.code === GENERAL_CODE` 로 막는 자리가 `kind==='general'` 이 된다.

**판정 규칙(우선순위 있는 단일 규칙)**

```
member_state(uid) =
  1. held        ← 저장된 상태가 held 이면 무조건 이긴다
  2. cohort      ← EXISTS(enrollments ⋈ cohorts WHERE kind='seminar' AND status='active')
  3. 저장된 상태  ← individual | expired | pending
  4. pending     ← 행이 없으면
```

- **`held` 를 `cohort` 위에 둔 이유**: 보류는 운영자가 사람을 보고 내린 판단이고 진단 응시를 막는 것이 목적이다. `cohort` 가 이기면 차수에 등록된 순간 보류가 무력화된다 — 운영자가 막은 사람을 코드 한 줄로 뚫는 길이 생긴다.
- **`expired` 를 `cohort` 아래 둔 이유**: 유효기간은 IA §5.1 상 **개인 회원의 자격 근거**다. 차수 회원의 근거는 세미나 등록이지 기간이 아니다.

### 2.3 이중 기록을 **타입으로** 막는다

저장 테이블의 CHECK 에 **`cohort` 를 넣지 않는다.**

```sql
memberships.status CHECK (status IN ('pending','individual','expired','held'))
```

규칙으로 "차수 소속을 저장하지 마라"를 두면 지켜지는지 매번 사람이 봐야 한다. enum 에서 빼면 **저장할 경로 자체가 없다.** ADR-121 이 `ValueCard` 에서 `category` 를 뺀 것과 같은 사고이고(발주서 §3.4 · 불변식 8), 발주서 §11-8·§11-9 를 문법이 강제한다.

### 2.4 이 방식이 IA §12-3(수료자 전이)을 절반 구현한다 — 그리고 절벽 하나를 만든다

술어에 `status='active'` 를 넣었으므로, 인도자가 1기를 `archived` 로 넘기는 순간 그 11명은 자동으로 `cohort` 에서 벗어난다. IA §12-3 권고("승인 없이 개인 회원 자동 전이")의 앞쪽 절반이다.

**그러나 뒤쪽 절반이 없으면 그날 11명이 조용히 잠긴다.** 저장 행이 없으므로 규칙 4번이 걸려 전원 `pending` 이 되고, `pending` 은 발주서 §4.1 표에서 응시 ✕ · **기존 결과 열람 —** 다. 수료 다음 날 자기 리포트를 못 연다.

- **1차 범위에서 아직 발화하지 않는다** — 실측 5개 차수 전부 `active` 이고 2기는 9/20 시작이다.
- 그러나 **규칙은 지금 정해야 한다.** §9 질의 ①.

## 3. S-1 설계안

### 3.1 스키마 — 새 마이그레이션 1개(불변식 15 · 기존 파일 무수정)

```sql
memberships (
  user_id       uuid PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  status        text NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending','individual','expired','held')),  -- cohort 없음(§2.3)
  valid_until   date,              -- individual 유효기간. IA §12-2 확정 전까지 NULL 허용
  decided_by    uuid REFERENCES users(id),
  decided_at    timestamptz,
  decision_note text,              -- 보류 사유 = 내부 메모(§4.5). 사용자에게 보이지 않는다
  signup_note   text,              -- 가입 경위(선택 · 민감 채널 아님)
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
)

cohorts       ADD COLUMN kind text NOT NULL DEFAULT 'seminar'
                CHECK (kind IN ('seminar','general','trash'))   -- §2.2
user_contacts ADD COLUMN forum_name  text                        -- §4.1
              ADD COLUMN forum_phone text
```

**권한은 `value_assessments` 선례를 그대로 따른다** — 이 프로젝트는 default privileges 로 신규 public 테이블에 `authenticated` 전권을 자동 부여하므로 **GRANT 가 아니라 REVOKE 가 본체다.** `GRANT SELECT` 만 남기고 `INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER` 를 회수한다. **TRUNCATE 회수를 빠뜨리면 RLS 밖이라 로그인 사용자가 표를 비울 수 있다**(`20260826120000` 의 명시적 교훈).

RLS: `SELECT` 는 본인 또는 `is_admin`. **쓰기 정책은 두지 않고 DEFINER RPC 로만**(ADR-80 · D1 선례).

### 3.2 RPC 넷

| 함수 | 성격 | 가드 |
|---|---|---|
| `member_state(p_uid uuid) → text` | `STABLE SECURITY DEFINER` · **판정의 유일한 구현** | 본인 또는 `is_admin` 외에는 `auth.uid()` 강제 |
| `member_can_assess(p_uid, p_kind text) → boolean` | 위를 부르는 얇은 층. `p_kind='journey'\|'standing'` | — |
| `decide_membership(p_user_id, p_decision, p_valid_until, p_note)` | 승인·보류·만료 | `is_admin` · **`p_user_id = auth.uid()` 이면 예외** · 결정 화이트리스트 · `FOR UPDATE` 행잠금 · 멱등 가드 |
| `list_pending_memberships()` | 승인 큐(운영자) | `is_admin`. 대조 키 + **만료 임박 30일** 동시 반환 |

`decide_membership` 은 `decide_coach_application`(ADR-24 · `20260628095527`)의 가드 여섯을 계승한다 — 내부 `is_admin` 명시(DEFINER 가 RLS 를 우회하므로), 화이트리스트, `FOR UPDATE`(동시 이중 결정 차단), 멱등 가드, 단일 트랜잭션. **자기 자신 차단은 그 함수에 없던 것을 더한 것**이고 발주서 §4.2 가 명시적으로 요구했다.

`set_user_role` 은 **한 줄도 건드리지 않는다.** `20260629100002`(users 테이블 UPDATE 회수 + 비-role 컬럼만 재부여)의 보호 범위 밖에서 새 표를 만드는 설계라 자가승격 표면이 넓어지지 않는다.

### 3.3 계약 — `CoreContext` 4메서드

```ts
// contracts/domain.ts
export type MemberState = 'pending' | 'individual' | 'cohort' | 'expired' | 'held';

// contracts/core-context.ts — 회원 상태(S-1)
getMyMemberState(): Promise<MemberState>;                    // 본인 — member_state()
listPendingMemberships(): Promise<MembershipApplication[]>;  // 운영자 — 대조 키 포함
listExpiringMemberships(days: number): Promise<MembershipRow[]>;
decideMembership(input: {
  userId: string;
  decision: 'individual' | 'held' | 'expired';
  validUntil?: string | null;
  note?: string | null;
}): Promise<void>;
```

`MemberState` 는 `Role` 과 **별도 타입이고 서로 섞이지 않는다**(발주서 §4.2 · §11-8). 코어는 이 넷을 `SupabaseCoreContext` 에 얹기만 하고 진단 어휘를 모른다(CLAUDE §2).

계약 변경은 발주서 §1 로 사전 승인됐다. **계약 이탈 0.**

### 3.4 §4.4 — 판정 함수가 둘이 되는 문제와 그 잠금

발주서 §4.4 는 *"단일 순수 판정 함수 + 서버 강제 두 겹"* 이라 했다. 문자 그대로 하면 **TS 순수 함수와 SQL 이 같은 규칙을 각자 구현**하게 되고, 이 저장소가 반복해서 데인 자리다(ADR-112 `CARE_TONE` · ADR-114 활력 임계 · ADR-119 문안 드리프트 — 전부 "사본이 둘"이 원인이었다).

**제안 — 구현은 하나, 진실표도 하나.**

- **판정(상태 산출)은 SQL 한 곳**에만 둔다. `member_state()` 가 유일한 구현이고 화면은 `getMyMemberState()` 로 **읽는다.** 다시 계산하지 않는다.
- **TS 순수 함수는 다른 일을 한다** — `assessmentAccess(state, kind)` 는 *상태 → 어떤 항목이 열리는가·문구는 무엇인가* 의 **표시 매핑**이다. 판정의 사본이 아니다.
- 둘이 만나는 지점(상태별 응시 가부)은 **하나의 진실표 픽스처**로 잠근다. TS 는 vitest 에서 직접, SQL 은 이미 있는 `tests/rls.integration.test.ts` 에서 — 단일 트랜잭션 + `ROLLBACK`, `RUN_RLS_INTEGRATION=1` 옵트인 하네스를 그대로 쓴다. `value_assessments` 가 N-5 에서 쓴 방식이다.

이것이 §4.4 의 **문언에서 벗어나는 유일한 지점**이고, 취지("화면마다 조건을 흩뿌리면 언젠가 새는 곳이 생긴다")에는 더 맞는다고 판단한다. 문언대로 TS 에도 판정을 복제하라는 지시라면 그대로 따르겠다 — §9 질의 ④.

## 4. §4.3 대조 키 — 급소 처리

### 4.1 저장 위치 — 불변식 13 을 지키려면 `memberships` 가 아니라 `user_contacts`

포럼 연락처는 **계정 전화번호와 다를 수 있다**(§4.3 이 이름에 대해 그렇게 명시했고 연락처도 같다). `user_contacts.phone` 에 덮어쓰면 안 되고, 그렇다고 승인 큐 테이블에 전화번호를 두면 **불변식 13(전화번호는 `user_contacts` 격리 · `getPhone` 게이트)이 깨진다.**

→ `user_contacts` 에 `forum_name`·`forum_phone` 을 더한다. 기존 `contacts_self` / `contacts_admin_read` 정책이 **그대로 적용된다**(본인 + 운영자만, 인도자 전면 차단). ADR-76 이 `address`·`bank_account` 를 같은 방식으로 얹은 선례가 정확히 이것이다. 가입 경위는 민감 채널이 아니므로 `memberships.signup_note`.

### 4.2 마스킹은 **서버에서** 한다

`010-****-1234` 를 SQL 이 만들지 TS 가 만들지 갈렸는데 **서버 컴포넌트에서 순수 함수로** 마스킹하기를 권한다.

- 전체 값이 **브라우저 번들에 실리지 않는다**(서버 경계에서 잘린다) — SQL 마스킹과 노출 위험이 같다.
- 순수 함수라 단위테스트가 쉽다. 자릿수·국제번호·짧은 번호 경계를 못 박을 수 있다.
- 전체 노출이 필요하면 기존 `getContactDetail`(ADR-76 · `assertContactAccess`)을 지난다. **새 게이트를 만들지 않는다.**

### 4.3 `/signup` 에 숨은 함정 — 이 필드가 유실되는 경로가 있다

`src/app/signup/SignupClient.tsx` 는 `supabase.auth.signUp()` 후 **세션이 있을 때만** `setContact`·`recordConsent`·`createCoachApplication` 을 부른다. 세션이 없는 분기(이메일 확인 대기)에서는 안내만 띄우고 **아무것도 저장하지 않는다.**

실측: `auth.users` 23행 전원 `confirmation_sent_at IS NULL` → **이메일 확인이 꺼져 있어 이 분기는 한 번도 발화한 적이 없다.** 오늘은 안전하다. 그러나 §4.3 이 못 박은 것이 *"나중에 필드를 추가해도 이미 들어온 신청 건은 영원히 대조할 수 없다"* 이고, 확인 메일을 켜는 순간 **승인 큐가 대조 키 없는 행으로 차기 시작한다.**

→ 대조 키를 `signUp(options.data)` 메타데이터로도 실어 `handle_new_user` 트리거가 함께 박게 한다.

**`coachApply` 를 metadata 로 신뢰하지 않기로 한 결정(S3 §3.4)과 충돌하지 않는다** — 그것은 **권한을 주는 값**이라 위조가 곧 승격이었고, 이것은 **운영자가 눈으로 대조할 재료**라 위조하면 승인이 반려될 뿐 아무 권한도 생기지 않는다. 이 구분을 근거로 삼는다.

### 4.4 개인정보 동의 문안이 걸린다

`src/app/_consent/consent.ts` 의 `PRIVACY_CONSENT` 는 수집 항목을 열거한다(`이름, 전화번호, 이메일, 성별, 생년, 체크 응답 (선택: 주소, 입금 계좌)`). 포럼 이름·연락처를 더하면 **수집 항목이 실제로 늘어난다.**

그런데 같은 파일 주석이 ADR-107 때 세운 규율을 담고 있다 — *"버전을 올리면 진행 중인 1기 참여자 전원이 다음 방문에서 재동의 화면을 만난다. 동의의 **내용**이 바뀔 때만 올린다."* 이번엔 내용이 바뀐다.

문제는 **비대칭**이다: 포럼 대조 키는 `/signup` 경로에서만 수집되고 `/join`(차수 회원) 경로에는 없다. `CONSENT_VERSION` 을 올리면 **해당 없는 22명이 2기 진행 중에 재동의 화면을 만난다.** IA §12-5 가 이미 이 영역을 미확정으로 남겨 두었다 — §9 질의 ③.

## 5. 승인 화면 · `/pending` · 통지

### 5.1 승인 화면 — 경로는 시안이 정했다

시안 P4 가 **`/admin/approvals`** 로 그렸다. 발주서 §4.5 는 "`/admin` 하위"라고만 했고 IA §2.2 신설 목록에는 이 경로가 없다. `/admin` 접두사 안이라 `PROTECTED_PREFIXES` 무영향이므로 **시안을 따른다**(§8 정합 확인 대상).

열 구성은 발주서 §4.5 그대로 — 신청자 · 계정 이메일 · **포럼 이름·연락처(마스킹)** · 가입 경위 · 신청일 · 승인/보류. 승인 시 유효기간 + 근거 메모, 부여자·부여일 자동. **만료 임박(30일) 목록을 같은 화면에.**

### 5.2 `/pending` — 보호 접두사에 넣지 않는다

`PROTECTED_PREFIXES` 에 `/pending` 을 더하면 불변식 17(matcher 커버리지) 근처를 건드리게 되고, 무엇보다 **대기자는 이미 인증된 사용자**라 미들웨어 인증 게이트가 할 일이 없다. `/pending` 자체는 비보호로 두고 페이지에서 세션을 확인한다(미인증이면 `/login`).

§4.6 의 네 문장 중 **"대개 얼마나 걸리는가"는 IA §12-4 미확정이라 문안을 쓸 수 없다** — §9 질의 ⑤.

**딥링크 착지**: 대기자가 진단 경로에 닿으면 `redirect('/pending?returnTo=…')`. `returnTo` 는 반드시 `safeReturnTo` 를 지난다. 현 화이트리스트는 갈무리·가치 카드 **네 형태뿐**이라 `/home/assessments`·`/my/values` 를 **짝 맞춰** 추가해야 한다(파일 주석의 "한쪽만 있으면 나중에 반드시 어긋난다" 원칙 · IA §원칙 2 도 같은 말을 한다).

### 5.3 승인 통지 — **이 저장소에는 메일 발송 수단이 없다**

§4.7 이 "저장소 현황을 확인하고 가장 적은 것을 새로 들이는 쪽"을 지시했다. 확인 결과:

- `package.json` 의존성에 **메일 라이브러리 0개**(Resend·nodemailer·SES 없음).
- Supabase Auth 발신 실측 **0건**(`auth.users` 23행 전원 `confirmation_sent_at IS NULL`).
- **ADR-79 가 이미 이 벽에 부딪혔다** — *"이메일 발송(Resend 도메인 미검증)으로 자가 비번 재설정이 막힌 회원을"* 운영자가 임시 비밀번호로 직접 복구하게 만들었다. 메일을 우회한 것이 이 저장소의 확립된 선례다.
- `/reset` 은 `resetPasswordForEmail` 을 부르지만 실제 도달 여부는 검증된 바 없다(enumeration 방지로 동일 안내를 띄워 실패해도 화면상 구분되지 않는다).

| | 안 | 새로 드는 것 | 판단 |
|---|---|---|---|
| (a) | Resend + Edge Function | 의존성 · 도메인 검증 · 함수 배포 | ADR-79 가 막힌 그 벽. 도메인 검증이 선결이고 우리 손 밖 |
| (b) | Supabase Auth 커스텀 SMTP | **SMTP 자격증명(코드 0줄)** | 기존 `/reset` 도 함께 살아난다. 다만 **임의 문안 발송 API 가 없다** — 승인 통지를 Auth 템플릿에 끼우는 형태가 된다 |
| **(c)** | **메일 없음 · 인앱 + 운영자 수동** | **0** | ADR-79 선례와 동형. §4.7 의 "없으면 사람이 다시 오지 않는다"를 정면으로 어긴다 |

**권고**: 1차는 **(c)로 배선하되 통지 훅을 함수 하나로 격리**한다(`notifyMembershipDecided`). 지금은 인앱 표시 + 운영자 수동, SMTP 가 서면 그 함수 안만 갈면 된다. **메일이 없다는 이유로 S-1 을 멈추지 않는다.** §9 질의 ⑥.

## 6. 백필 — 23계정 중 손댈 것은 4개

`memberships` 는 신규 표라 전원 무행 = `pending` 이 되므로 **백필하지 않으면 23명 전원이 잠긴다.**

| role | 계 | 세미나 차수 등록 → **산출 `cohort`** | 체험/test 만 | 휴지통만 | 무등록 |
|---|---|---|---|---|---|
| user | 20 | **16** | 2 | 1 | 1 |
| coach | 1 | 1 | — | — | — |
| admin | 2 | 1 | 1 | — | — |

- **18명은 행이 필요 없다** — `member_state()` 가 `cohort` 를 산출한다. 이것이 판정 산출 방식의 실질적 이득이다.
- 손댈 것은 **`role='user'` 4계정**: 체험/test 2 · 휴지통 1 · 무등록 1.
  - 휴지통 1 → `held`(소프트 삭제 상태의 정직한 표현. 응시 ✕ · 열람 —)
  - 체험/test 2, 무등록 1 → **§9 질의 ②**(`pending` 으로 두면 체험 진단을 이미 마친 사람이 잠긴다)
- `admin` 1명(체험만)은 산출로 `cohort` 가 아니지만 운영자 화면은 `role` 이 연다. 다만 **`role` 과 `state` 가 갈리는 첫 사례**이므로 응시 게이트가 `role='admin'` 을 예외로 둘지 정해야 한다.
  → **권고: 예외를 두지 않는다.** 운영자도 응시하려면 상태가 있어야 한다. 예외는 나중에 반드시 구멍이 된다.

## 7. §7.2 부품 부재 — **재판정(정정)**

**첫 판단을 정정한다.** 발주서 §7.2 는 "design_system v4 가 아직 오지 않았다"며 승인 큐 표·상태 배지·PC 브레이크포인트를 부재로 들었고 나는 그에 따라 "`/admin` 승인 큐는 기능 골격으로 두고 v4 도착 후 입힌다"고 판단했다. **그러나 시안 실물이 발주서와 같은 시각에 도착해 있었다.**

| 파일 | 내용 |
|---|---|
| `docs/tasks/퓨처나우_통합웹사이트_시안_v1.3.html` | 모바일 프레임 **7종** — A 공개 홈 · B 로그인 홈 · C 내 여정 · **D 딥링크 게이트** · E 전체 메뉴 시트 · **F 진단 홈** · **G 승인 대기 안내** |
| `docs/tasks/퓨처나우_PC시안_v1.1.html` | PC 화면 **4종** — P1 공개 홈 · P2 인도자 콘솔 · P3 참여자 화면 · **P4 운영 콘솔 가입 승인(`/admin/approvals`)** |

**S-1 이 필요로 하는 화면 셋이 전부 시안에 있다** — `/pending`(G) · 승인 큐 표(P4) · 상태 배지·마스킹 표기(P4 의 `010-****-1234`, `명단 대조 안 됨` pill).

따라서 방침을 바꾼다:

- **`/admin/approvals` 도 기능 골격이 아니라 시안대로 구현한다.** CLAUDE §8 의 "확정 전 임의 디자인 금지"는 **임의** 디자인을 막는 것이고, 지휘부가 확정해 전달한 시안이 있으면 그것이 근거다.
- **색·수치는 시안에서 직접 읽어 잠근다** — ADR-106(모집 랜딩)·ADR-112(돌봄 배너)가 세운 방식 그대로. 시안 HTML 과 `globals.css` 를 스냅숏 사본 없이 직접 대조한다. 원본이 코드 밖 문서라 사본을 만들면 진실이 셋이 된다.
- 시안이 **토큰 밖 hex 를 쓰면 대비를 실측해 토큰으로 치환한다**(ADR-113 선례 — 시안 초록 3.99:1 미달 → `--color-success` 4.93:1).

**여전히 남는 부재 — 지휘부 전달 요청**

| 부품 | 왜 시안으로 못 메우나 |
|---|---|
| **PC 브레이크포인트 수치** | `design_system.md` §11 이 "**미규정**"으로 명시. 시안은 결과 화면이지 기준선이 아니다 |
| **날짜 입력**(유효기간 부여) | 공용 12종에 없다. `<input type="date">` 원시 요소는 브라우저 기본 스타일이 그대로 나와 §8 에 걸린다. **새로 발견해 추가 보고하는 항목** |
| 단일행 입력(≤60자) | 승인 근거 메모·`/signup` 포럼 이름. `TextArea` 우회는 가능하나 결이 다르다 |

## 8. 상위 문서·발주서·시안 충돌 — 3건

사용자 지시대로 **IA 확정본이 우선**한다는 전제로 판정했다.

| # | 충돌 | 판정 |
|---|---|---|
| ① | **시안 둘이 `/s/2`·`/s/3`·`/login?returnTo=/s/3` 을 쓴다.** IA §0 이 `/s/[n]` 딥링크 신설을 **명시적으로 폐기**했다("이미 있다. `/c/[code]/[session]`(ADR-89)이 같은 일을 한다") | **IA 우선. `/c/{code}/{n}` 로 읽는다.** 시안 D(딥링크 게이트)를 문자 그대로 구현하면 `safeReturnTo` 화이트리스트(`/^\/c\/[A-Za-z0-9]{4,8}\/[1-9][0-9]?$/`)가 `/s/3` 을 **거부해 returnTo 가 조용히 null 이 되고**, 인증 후 원래 자리로 못 돌아간다 — 그 시안의 핵심 기능이 죽는다 |
| ② | **`/admin/approvals`** — 시안 P4 의 경로. IA §2.2 신설 목록에 없다 | **시안을 따른다.** `/admin` 접두사 안이라 불변식 17 무영향. IA §2.2 표에 추가 필요(문서 정합) |
| ③ | 발주서 §7.2 "design_system v4 가 아직 오지 않았다" vs 시안 실물 존재 | **§7 재판정** 참조. v4 문서는 아직이나 화면 시안은 있다 |

①은 구현 방식이 갈리는 지점이라 **명시적 확인을 청한다**(§9 질의 ⑦로 올리지 않고 IA 우선 원칙으로 이미 판정했으나, 시안이 두 곳에서 일관되게 `/s/` 를 쓰므로 의도된 개명일 가능성을 배제하지 못한다).

## 9. 판단 필요 — 6건

| # | 질의 | 막히는 지점 | 내 권고 |
