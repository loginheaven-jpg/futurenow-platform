```
적용    005825 < 092730 < 141012 < 142335 < 150546        < 234713
```

**각 파일 머리에 적용 버전을 적어 두었다** — 대조가 파일 안에서 끝나게 한다.
`db reset` 으로 클린 재적용 시 파일명 순서가 곧 적용 순서가 되며, 순서가 같으므로 결과가 동일하다.

## 3. 계약 델타 — **추가가 대부분이나 "0 변경"은 아니다**

지휘부가 확인을 요청한 항목이라 **정확히 적는다.**

### 3.1 추가 (신규)

| 파일 | 추가 |
|---|---|
| `domain.ts` | `MemberState` · `AssessmentKind` · `MembershipDecision` · `MembershipQueueRow` · `NewsPost` · `LibraryTier` · `LibraryItem` · `ContactMessage` — **타입 8** |
| `core-context.ts` | `getMyMemberState` · `listMembershipQueue` · `decideMembership` · `recordSignupIntake` · `listNews` · `getNews` · `upsertNews` · `deleteNews` · `listLibrary` · `signLibraryFile` · `submitContact` · `listContactMessages` · `markContactHandled` — **메서드 13** |
| `domain.ts` | `ConsentType` 에 `'forum_match'` **값 1 추가**(유니온 확장) |

### 3.2 ⚠ 기존 시그니처 변경 — **5메서드, 4줄**

**"기존 시그니처 0 변경"은 사실이 아니다.** S-2 가 가치 카드 5메서드의 `cohortId` 를 넓혔다.

```
getMyValueAssessment(cohortId: string)        → (cohortId: string | null)
saveMyValueProgress({ cohortId: string })     → { cohortId: string | null }
finalizeMyValue(cohortId: string, …)          → (cohortId: string | null, …)
patchMyValue({ cohortId: string })            → { cohortId: string | null }
```

- **발주서 §3 이 명시적으로 승인한 변경**이다(`cohortId: string | null`).
- **호출자 관점에서는 하위 호환이다** — 기존에 `string` 을 넘기던 코드는 그대로 컴파일된다.
  좁아진 것은 **구현자 쪽**(null 을 다뤄야 한다)이고 구현체는 `SupabaseCoreContext` 하나다.
- `tsc` 0 이 그 사실을 증명한다 — 기존 호출부가 하나라도 깨졌으면 여기서 잡혔다.

**그 밖의 기존 메서드는 한 줄도 바뀌지 않았다.**

## 4. 이번 턴 추가 — `/admin` 미처리 문의 건수

`/admin` 헤더 바로 아래에 한 줄. **운영자가 어차피 승인 큐를 보러 오는 자리**에 숫자를 놓는다.

- `AdminMembers` 에 `notices` 슬롯 하나를 더했다(`headerActions` 와 같은 형태).
- **0건이면 줄을 그리지 않는다** — 늘 떠 있는 `0` 은 읽히지 않고 자리만 차지한다.
- 조회 실패는 조용히 빈 배열 — 카운터가 안 되는 것과 본부가 안 열리는 것은 심각도가 다르다.
- 문구가 현재 상태를 정직하게 말한다: **"목록 화면은 준비 중입니다"**.

## 5. 딥링크 검증표 — 발주서 §10 7조합 + S-2·S-3

**두 층으로 나눠 채웠다.** 세션이 필요한 행은 QA 계정이 아직 없어 RPC·RLS 층으로 증명했고,
**그 차이를 표에 명시한다**(지휘부 지시).

### 5.1 미인증 — **실브라우저**(Vercel 프리뷰)

| 진입 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `/my/values` | `/login` + returnTo | 로그인 폼 · `returnTo=/my/values` | **PASS**(브라우저) |
| `/home/assessments` | 〃 | 로그인 폼 · `returnTo=/home/assessments` | **PASS**(브라우저) |
| `/admin/approvals` | 〃 | 로그인 폼 · `returnTo=/admin/approvals` | **PASS**(브라우저) |
| `/c/{code}/values` | **기존 동작 유지** | `NEXT_REDIRECT;replace;/login?returnTo=%2Fc%2FDKAAA%2Fvalues;307` | **PASS**(브라우저) |
| `/about` · `/library` · `/contact` · `/news` | 공개 렌더 | 각각 `퓨처나우 소개`·`자료실`·`문의`·`소식` | **PASS**(브라우저) |

판정은 불변식 19대로 **본문 민감 콘텐츠 0 + 리다이렉트 목적지**로 했다.
`/pending` 은 앞서 **200 + `NEXT_REDIRECT`** 로 서빙됨을 관측했다 — `fetch` 200 만 봤다면 오독했을 자리다.

### 5.2 인증 상태 — **RPC·RLS 층**(세션 미보유 · 12/12 PASS)

| # | 진입 · 상태 | 기대 | 실측 | 층 |
|---|---|---|---|---|
| 2 | `/my/values` · 승인 대기 | `/pending`(오류 아님) | `pending` · 응시 차단 | RPC |
| 3 | `/my/values` · 개인 회원 | 정상 진입 | `individual` · 응시 허용 · **개인 행 실제 생성** | RPC |
| 4 | `/my/values` · 만료 | 응시 차단 · **열람 가능** | `expired` · 42501 · **기존 행 열람 O** | RPC |

> **차이를 숨기지 않는다.** ⑵의 행들은 **브라우저에서 돌지 않았다.** 상태 게이트·RPC 강제는
> 증명됐으나, 그 상태의 사용자가 실제 화면에서 무엇을 보는지(리다이렉트 목적지·본문)는
> 아직 재지 않았다. **QA 계정이 오면 이 표의 ⑵ 부분만 따로 돌려 별도 보고한다.**
>
> 계정을 임의로 만들지 않은 이유: 지금까지 지켜 온 **"픽스처 잔여 0"** 이 깨진다.
> 상주 QA 계정은 그 규칙의 **명시적 예외**로 `docs/reports/README.md` 규율에 이미 적어 두었다.

## 8. main 병합 전 확인이 필요한 것

| # | 항목 | 왜 병합 전인가 |
|---|---|---|
| **A** | **DB 는 이미 프로덕션에 적용돼 있다** | 마이그레이션 다섯이 `main` 병합 **전에** 라이브에 적용됐다. 즉 **`main` 이 아직 모르는 스키마 위에서 운영 중**이다. 지금 `main` 을 배포하면 새 표를 쓰지 않을 뿐 깨지지는 않으나(추가만 했고 기존 것을 바꾸지 않았다), **`cohorts` UPDATE 권한 회수와 `handle_new_user` 변경은 기존 경로에 닿는다.** 병합이 늦어질수록 이 간극이 길어진다 |
| **B** | `handle_new_user` 가 이미 바뀌어 있다 | 지금 `/signup` 으로 가입하면 트리거는 대조 키를 받을 준비가 됐지만 `main` 의 폼은 그것을 보내지 않는다. **무해**(NULL 가드)하나 병합 전까지 대조 키가 쌓이지 않는다 |
| **C** | `cohorts` 테이블 UPDATE 권한 회수 | `main` 의 `updateCohort` 는 5컬럼만 쓰므로 안전하다. **확인은 했으나 병합 후 실브라우저로 한 번 더 볼 것을 권한다**(차수 이름 변경·마감) |
| **D** | QA 계정 | 병합 전에 딥링크 표 ⑵를 브라우저로 마치는 것이 안전하다. 다만 **막지는 않는다** — RPC 층은 증명됐다 |
| **E** | 2기 일정 | 9/20 시작. 병합·검증 여유는 있으나 **`/signup` 대조 키가 병합돼야 신규 가입자부터 쌓인다** |

**권고**: A·B 때문에 **병합을 미루는 것이 오히려 위험하다.** 코드와 DB 가 갈라진 채로 두는 기간이
길어질수록 `main` 배포와 라이브 스키마의 간극이 커진다. 감사 후 이른 병합을 권한다.
