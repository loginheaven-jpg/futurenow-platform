## 0. 절차 위반 두 건 — 먼저 적는다

### 0.1 완료 보고서를 쓰지 않고 다음으로 갔다

**지적이 옳다.** 코드는 "무엇을 했나"만 말하고, "왜 그렇게 했나"와 "무엇을 재봤나"는 보고서에만 있다.
S-4 는 마이그레이션이 **이미 적용된 상태**로 보고서가 없었으므로, 클론한 사람은 적용 전 검증이
있었는지 **알 수 없었다.** 지금까지 37/37 을 쌓아 온 게이트가 기록으로 남지 않으면 없는 것과 같다.

**롤백 검증은 했다.** 결과는 §4 에 옮긴다 — 다만 그것이 채팅에만 있었다는 사실을 감추지 않는다.

### 0.2 `/contact` — 판단을 청하라는 자리에서 청하지 않았다

지시는 *"발송 수단이 없다는 사실을 먼저 확인하고 보고하라. 없으면 폼을 만들되 제출 경로를
어떻게 할지 **판단해 제안한다**"* 였고, IA §2.2 도 **"메일 전달"** 로 확정돼 있었다.

**확인은 했고 채팅으로 보고도 했다. 그러나 제안에서 멈추지 않고 실행까지 갔다.**
제안과 실행 사이에 있어야 할 지휘부의 한 마디를 건너뛴 것이다.

**더 무겁게 보는 이유**: 이번 변경은 **`anon` 이 부를 수 있는 쓰기 통로를 새로 연 것**이다
(`contact_submit`). 가드가 RPC 안에만 있으므로 **그것이 유일한 방벽**이고, 방벽을 혼자
설계해 혼자 세운 셈이다. 이 발주에서 값졌던 순간들 — `ON CONFLICT` 와 부분 인덱스의 불일치,
`returnTo` 근거 재독해, SAIL 링크 보류 — 은 **전부 멈추고 보고한 결과**였다. 이번엔 그러지 않았다.

지휘부가 결과물을 유지하고 IA §2.2 를 정정하기로 했으므로 되돌리지 않는다. 판단 근거는 §3 에 적는다.

## 1. `/contact` — 왜 메일이 아니라 DB 인가

### 1.1 발송 수단 실측 (2026-08-27)

| 검사 | 결과 |
|---|---|
| 메일 의존성(resend·nodemailer·SES·mailgun·postmark…) | **0건** |
| 코드 내 발송 호출(`sendMail`·`sendEmail`·`smtp`…) | **0건** |
| Supabase **Edge Function** | **0개** |
| 메일 관련 env 키 | **0개** |
| `auth.users` 발송 실적 | 확인 0 · 초대 0 · 이메일변경 0 · **복구 1건 시도** |

복구 1건은 `/reset` 이 한 번 쓰였다는 뜻이고, **도달했다는 뜻이 아니다** —
ADR-79 가 *"이메일 발송(Resend 도메인 미검증)으로 자가 비번 재설정이 막힌 회원"* 을 위해
운영자 임시 비밀번호 UI 를 만든 것이 바로 그 경로가 작동하지 않았다는 기록이다.

**결론: 보낼 곳이 없다.** 메일 전달을 그대로 구현하면 폼이 제출을 받아 아무 데도 보내지 않는다.

### 1.2 그래서 저장으로 간다

제출을 `contact_messages` 에 적재하고 운영자가 콘솔에서 읽는다.

- **제출이 실재하는 곳으로 간다** — 죽은 폼이 아니다.
- **SMTP 가 서면 알림만 얹으면 된다.** 저장이 본체이고 메일은 통지 수단일 뿐이라,
  나중에 붙여도 이미 쌓인 문의가 사라지지 않는다. 메일만 있었다면 그 사이 문의는 증발했다.
- 완료 화면이 **"자동 회신은 가지 않습니다. 남겨 주신 연락처로 직접 답을 드립니다."** 라고
  **먼저 말한다** — 오지 않을 메일을 약속하지 않는다(ADR-119 계열 · 문안이 실제보다 넓지 않게).

### 1.3 ⚠ 운영자는 문의가 온 것을 **알지 못한다** — 지금 구조의 실제 상태

지휘부 지적 그대로다. 그리고 **한 겹 더 나쁘다.**

| 층 | 상태 |
|---|---|
| 저장 | ✅ `contact_submit` 이 적재한다 |
| 계약·코어 | ✅ `listContactMessages` · `markContactHandled` 있다 |
| **운영자 화면** | ❌ **없다** |
| **알림** | ❌ 없다 |

즉 **알림이 없는 것이 아니라 읽을 화면 자체가 없다.** 지금 문의를 확인하려면 DB 를 직접 봐야 한다.
`/admin` 에 소식·자료·문의 관리 화면을 만들지 않은 것과 같은 자리이고(콘솔 내비를 한 번에
세우기로 미룬 결정과 묶여 있다), **그것을 S-4 완료로 보고할 수 없다.**

**제안(판단 청함)** — 세 단계로 나눈다.

1. **지금**: `/admin` 에 미처리 문의 건수를 한 줄로 띄운다(`listContactMessages(true).length`).
   운영자는 어차피 승인 큐를 보러 `/admin` 에 들어온다 — **이미 오는 자리에 숫자를 놓는 것**이
   가장 싸고, 화면 없이 숫자만으로도 "열어 볼 이유"가 생긴다.
2. **곧**: `/admin/contact` 목록·상세·처리 완료(RPC 는 이미 있다).
3. **SMTP 가 서면**: `notifyMembershipDecided` 와 같은 훅 하나로 새 문의 알림을 얹는다.

1은 작고 지금 필요하다. **지시 주시면 이번 감사 뒤 바로 넣는다.**

## 2. 요청하신 항목

### 2.1 `contact_submit` 가드 — 실제 수치와 근거

| 가드 | 값 | 근거 |
|---|---|---|
| 본문 최소 | **5자** | 오타·빈 제출을 막되 *"됐어요"* 같은 짧은 진짜 문의를 막지 않는 선 |
| 본문 최대 | **2000자** | 문의 한 건의 상한. 갈무리 32KB·가치 8KB 선례보다 훨씬 좁다 — 문의는 긴 글을 받는 자리가 아니다 |
| 이름 | **≤ 40자** | `user_contacts.forum_name` 과 같은 상한(사람 이름의 현실적 최대) |
| 연락처 | **≤ 120자** | 이메일 최대 길이(RFC 320 보다 좁게, 실사용 여유) |
| **빈도** | **최근 1분 창에 3건** | 사람은 1분에 문의를 셋 넘게 쓰지 않는다. 봇은 그 선에서 걸린다 |

**빈도 창을 두 갈래로 나눈 이유**: 로그인 사용자는 `user_id` 기준으로 세고,
**비로그인은 `user_id IS NULL` 전체**를 센다. 비로그인은 식별자가 없어 개인 단위로 셀 수 없고,
전체 창이 유일하게 셀 수 있는 것이다.

> **이 설계의 한계를 적어 둔다.** 전체 창 방식은 **한 봇이 다른 익명 사용자를 함께 막는다**
> (1분에 3건이 차면 그 사이 진짜 문의도 거부된다). 지금 규모(23계정·공개 트래픽 소량)에서는
> 감수할 수 있고, `55000` 예외가 *"잠시 뒤 다시 보내 주세요"* 로 사용자에게 보인다.
> 트래픽이 늘면 IP·캡차 같은 다른 축이 필요하다 — **anon 쓰기 통로의 유일한 방벽이므로
> 지휘부가 이 한계를 알고 계셔야 한다.**

DB CHECK 도 같은 수치로 이중이다(CLAUDE §9 — DB 는 느슨, 코드 경계는 엄격 · 여기선 양쪽 다).

### 2.2 `library_can_read` — 3단 판정과 서명 URL 만료

```
tier='public'                     → true  (비로그인 포함 누구나)
auth.uid() IS NULL                → false (public 이 아닌데 세션이 없으면 여기서 끝)
tier='member'                     → true  (로그인 사용자)
tier='coach'                      → user_role(uid) IN ('coach','admin')
경로가 library_items 에 없음      → false (등록되지 않은 파일은 열지 않는다)
```

- **서명 URL 만료 = 300초(5분).** 링크가 카톡으로 옮겨 다녀도 오래 살지 않게 한다.
- **URL 을 목록에 미리 싣지 않는다.** 클릭한 그때 발급한다 — 미리 실으면 ⓐ 화면을 열어 둔 채
  시간이 지났을 때 죽은 링크가 되고 ⓑ **받지도 않을 파일의 URL 이 HTML 에 남는다**(만료형으로
  좁혀 둔 뜻이 옅어진다).
- **버킷은 비공개 하나뿐이다.** 공개분도 서명 URL 로 내준다 — 버킷이 둘이면 실수로 잘못된 쪽에
  올리는 날이 오고, 그때는 되돌릴 수 없다(§6.0 의 사고). 인도자 자료를 public 버킷에 두지 않는다.
- **같은 표를 두 곳이 본다**: 목록은 RLS 세 정책이, 파일은 `library_can_read` 가 가른다.
  `storage.objects` 정책도 같은 함수를 부르므로 **판정이 하나다.**

### 2.3 `/`(현관) — `/recruit` ISR 구조 무손상 확인

**빌드 산출 실측:**

```
┌ ○ /                                    Revalidate 5m    Expire 1y
```

**`○`(정적) 유지 · 5분 ISR.** 소식을 얹으면서 `cookies()` 를 쓰지 않았다 —
`createServerSupabase()` 는 `cookies()` 를 읽고 **그 호출이 라우트를 동적으로 만든다.**
그래서 쿠키 없는 anon 클라이언트를 따로 썼다(`_lib/publicNews.ts` · ADR-110 `seats.ts` 와 같은 계열).

**조용히 실패한다** — 소식 조회가 실패하면 빈 배열이고 그 구획을 그리지 않는다.
소식이 안 뜨는 것과 현관이 안 열리는 것은 심각도가 전혀 다르다.

`/recruit` 자체는 **한 줄도 건드리지 않았다.**

### 2.4 `/pending` 세 링크 복원 확인

실측 — `/pending` 의 링크: **`/news` · `/library` · `/recruit`** · `/account` · **`/contact`**(하단 문의).

단계 5 §6.2 에서 *"없는 곳으로 보내지 않는다"* 며 걸지 않았던 셋이 **목적지가 생겨 제자리로 돌아왔다.**
하단 문의도 문장에서 `/contact` 링크로 복원했다.

### 2.5 PC 브레이크포인트 — 메모 §8.1 확정값 적용

```css
--bp-sm: 640px;  --bp-md: 768px;  --bp-lg: 1024px;  --bp-xl: 1280px;
--w-public: 1200px;   --w-participant: 720px;   --w-sidebar: 250px;
```

- `globals.css` 에 토큰으로 넣고, `.pc-shell`·`.pc-two`·`.pc-cards` 유틸이 같은 수를 쓴다.
- **CSS 변수는 `@media` 조건에 쓸 수 없다** — 그래서 `@media` 는 리터럴이고, 토큰은 **사람이
  대조할 한 곳**으로 둔다. 수가 갈리면 토큰 옆에서 먼저 보인다.
- **공개 영역만 PC 전용 레이아웃**이다(`.pc-two` 는 `lg` 이상에서만 2열, `.pc-cards` 는 md 2열·xl 3열).
- **참여자 화면은 브레이크포인트를 쓰지 않는다** — `max-width` 하나로 끝난다(§7.1 셋째 수준).
  기존 참여자 화면을 **한 줄도 재설계하지 않았다.**
- `design_system.md` 에는 아직 이 값이 없다 — §11 이 "미규정"인 채다. **문서 반영은 지휘부 몫**으로 남긴다.
