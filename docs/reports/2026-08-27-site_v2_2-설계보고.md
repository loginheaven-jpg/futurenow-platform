### ① 지휘부 오류 — `taken` 과 `remaining` 을 뒤집어 읽었다

`cohort_seats_taken('ZR4KB') = 7` 과 `/recruit` 의 **`남은 자리 3`** 은 **같은 상태의 두 표현**이다.
`seatsRemaining = intake.seats(10) − taken` 이므로 `10 − 7 = 3`. 지휘부가 이것을
*"자동 집계가 살아 있다는 두 번째 증거"* 로 병합 보고 §4에 덧붙이려 했으나 **일어나지 않은 변화**였다.

**증거는 `taken 5 → 7` 하나뿐이다**(ADR-110 실측 2026-08-24 → 병합일).
**지휘부가 낸 값 7은 정확했다. 틀린 것은 그것을 무엇과 비교했는가다.**

### ② 클코1 오류 — 편입 커밋 수를 24로 적었다. 실측 **26**

`git rev-list --count 9664f9a..98f780f` = **26**.
`2026-08-27-site_v2-main병합-완료.md` §1과 병합 커밋 `6cf1201` 메시지에 **24**로 박혔다.

**원값을 지우지 않는다** — 병합 커밋 메시지는 이력에 고정돼 있고, ADR-121 검증 수치 정정과 같은
처리를 한다(정정 주를 달되 덮어쓰지 않는다). 본 보고가 그 정정 주다.

### 재발 방지 — 수치는 홀로 서지 못한다

두 오류의 뿌리가 같다. **집계값이 근거·방향 없이 홀로 적히면 다음에 읽는 사람이 재구성한다.**
앞으로 보고서의 집계 수치는 **`taken=7 / 정원 10 → 남은 3`** 처럼 근거와 방향을 같은 줄에 적고,
커밋 수는 **산출 명령을 함께** 적는다(`git rev-list --count A..B` = 26).

## 2. 갈무리 선례 — 무엇을 그대로 옮기고 무엇이 다른가

발주 §4가 *"새로 설계하지 않는다"* 고 했다. 실측으로 대조했다.

| 항목 | 갈무리(`checkin-photos`) | **피드(`feed-photos`)** | 판단 |
|---|---|---|---|
| 버킷 | `public=false` | **동일** | 그대로 |
| 상한 | 3 MiB · `image/jpeg` | **동일** | 그대로 |
| 리사이즈 | 장변 2000px · jpeg 0.85 (`LetterPhotos.processImage`) | **동일** | 그대로 |
| 경로 | `{cohort}/{user}/{session}/{uuid}.jpg` | `{cohort}/{user}/{uuid}.jpg` | **회차가 없다**(3단→2단) |
| INSERT | 본인 경로 + 그 차수 멤버 | 본인 경로 + `feed_can_access` | 동치 |
| **SELECT** | 본인 **OR** 코치 **OR** 운영자 | **같은 기수 전원** + 코치 + 운영자 | **더 넓다** |
| **DELETE** | 본인 OR 운영자 (**코치 불가**) | 본인 OR **코치** OR 운영자 | **코치 추가** |
| 정리 | Storage API 경유만(ADR-87) | **동일** | 그대로 |
| UPDATE | 정책 없음 | **동일** | 그대로 |

> **선례를 그대로 옮길 수 없는 두 줄이 있다.** 갈무리는 **혼자 쓰는 방**이고 피드는 **함께 보는 방**이다.
> 발주 §3.3이 세운 벽이 여기서 **정책 차이**로 나타난다 — SELECT 를 넓히는 것은 선례 이탈이 아니라
> 선례가 지키려던 것(갈무리의 사적 성격)을 **지키기 위해** 두 버킷을 가르는 일이다.
> DELETE 에 코치를 더한 것은 발주 §5.3(*"인도자는 자기 기수 글을 지울 수 있다 — 부적절 게시 대응"*) 이행이다.

## 3. 테이블 골격 — 4개

### 3.1 `feed_posts`

```sql
CREATE TABLE public.feed_posts (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  cohort_id  uuid NOT NULL REFERENCES public.cohorts(id) ON DELETE CASCADE,
  author_id  uuid NOT NULL REFERENCES public.users(id)   ON DELETE CASCADE,
  body       text NOT NULL DEFAULT '' CHECK (char_length(body) <= 2000),
  photo_path text CHECK (photo_path IS NULL OR char_length(photo_path) <= 300),
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz,
  deleted_by uuid REFERENCES public.users(id) ON DELETE SET NULL,
  -- 사진만 올려도 게시된다(§3.1 · 카톡 예시 06:12). 다만 둘 다 비면 빈 글이다.
  CONSTRAINT feed_posts_not_empty CHECK (char_length(btrim(body)) > 0 OR photo_path IS NOT NULL)
);
CREATE INDEX feed_posts_cohort_time_idx ON public.feed_posts (cohort_id, created_at DESC) WHERE deleted_at IS NULL;
CREATE INDEX feed_posts_mine_idx        ON public.feed_posts (cohort_id, author_id, created_at DESC) WHERE deleted_at IS NULL;
```

**없는 컬럼이 설계다.**

| 없는 것 | 이유 |
|---|---|
| `title` · `category` · `tags` | §3.1 *"본문 하나뿐이다"* 를 **규칙이 아니라 구조로** 강제 |
| `updated_at` · 수정 RPC | 카톡에 수정이 없다. 마찰을 늘리지 않는다 |
| `like_count` 등 집계 컬럼 | 집계는 질의로. 저장하면 **사본이 둘**이 되고 §3.2의 "좋아요 수 정렬" 유혹이 생긴다 |
| `session_no` | 갈무리와 피드를 잇는 컬럼을 두지 않는다(§3.3 금지 방향) |

### 3.2 `feed_comments`

```sql
CREATE TABLE public.feed_comments (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id    uuid NOT NULL REFERENCES public.feed_posts(id) ON DELETE CASCADE,
  author_id  uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  body       text NOT NULL CHECK (char_length(btrim(body)) BETWEEN 1 AND 1000),
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz,
  deleted_by uuid REFERENCES public.users(id) ON DELETE SET NULL
);
CREATE INDEX feed_comments_post_idx ON public.feed_comments (post_id, created_at) WHERE deleted_at IS NULL;
```

**`parent_id` 컬럼이 없다.** §3.4의 *"댓글은 1단"* 을 화면이 아니라 **스키마가** 보장한다.
컬럼이 있으면 언젠가 누가 채운다.

**`cohort_id` 를 복사하지 않는다.** 댓글의 기수는 원글이 알고 있고, 그 주인은 하나여야 한다
(`architecture.md` §11-9). 정책은 아래 `feed_post_accessible` DEFINER 헬퍼로 원글을 본다 —
정책끼리 테이블을 직접 참조하면 RLS 재귀가 생긴다(CLAUDE §5, `is_admin` 패턴과 같은 계열).

### 3.3 `feed_reactions`

```sql
CREATE TABLE public.feed_reactions (
  post_id    uuid NOT NULL REFERENCES public.feed_posts(id) ON DELETE CASCADE,
  user_id    uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  emoji      text NOT NULL CHECK (emoji IN ('👏','🙏','💪','❤️')),
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (post_id, user_id)     -- 한 사람 한 반응. 교체는 되고 누적은 안 된다
);
```

PK 가 `(post_id, user_id)` 인 이유 — 한 사람이 여러 이모지를 쌓을 수 있으면 그 수가 곧 점수가 되고,
그것이 §3.2가 막으려는 것이다. **응원이지 채점이 아니다.**

### 3.4 `news_comments`

```sql
CREATE TABLE public.news_comments (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id    uuid NOT NULL REFERENCES public.news_posts(id) ON DELETE CASCADE,
  author_id  uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  body       text NOT NULL CHECK (char_length(btrim(body)) BETWEEN 1 AND 1000),
  created_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz,
  deleted_by uuid REFERENCES public.users(id) ON DELETE SET NULL
);
```

피드 댓글과 **합치지 않는다**(§7-5 계열). 스코프 축이 다르다 — 피드는 기수, 소식은 전체.
한 표에 담으면 정책이 분기하고, 분기하는 정책은 새는 정책이다.

## 4. 판정 헬퍼 — `SECURITY DEFINER` 둘

```sql
-- 피드의 열람 자격과 게시 자격은 **하나다**(§5.1 표에서 두 열이 동일).
--   판정을 한 함수에 둔다 — 화면마다 조건을 흩뿌리면 언젠가 새는 곳이 생긴다(IA §5.8).
CREATE FUNCTION public.feed_can_access(p_cohort_id uuid, p_uid uuid DEFAULT auth.uid())
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT p_uid IS NOT NULL AND (
    public.is_admin(p_uid)
    OR EXISTS (
      SELECT 1 FROM public.cohorts c
       WHERE c.id = p_cohort_id
         AND c.kind = 'seminar'    -- 휴지통·체험·test 차수는 피드가 없다(§5.1)
         -- status 를 보지 않는다: 수료(archived) 기수도 피드가 산다(§5.1 확정 ③)
         AND (c.coach_id = p_uid OR public.is_cohort_member(c.id, p_uid))
    ));
$$;

CREATE FUNCTION public.feed_post_accessible(p_post_id uuid, p_uid uuid DEFAULT auth.uid())
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT EXISTS (SELECT 1 FROM public.feed_posts p
                  WHERE p.id = p_post_id AND public.feed_can_access(p.cohort_id, p_uid));
$$;
```

**`kind='seminar'` 를 넣고 `status` 를 뺀 것이 이 함수의 전부다.**

- `kind` 를 빼면 **휴지통에 버린 사람이 피드를 읽는다** — S-1이 `enrollments` 단독 판정에서
  겪은 그 결함(IA §5.4 정정)이 그대로 재현된다. `is_cohort_member` 는 `enrollments` 만 보므로
  **단독으로는 여기서 쓸 수 없다.**
- `status` 를 넣으면 **1기 피드가 마감과 함께 죽는다** — 발주 확정 ③에 정면으로 어긋난다.
  기존 `is_cohort_member` 가 `status` 를 보지 않는 것이 여기서는 **정확히 맞다.**

**1기 인도자 참여**(확정 ④)는 `c.coach_id = p_uid` 가 처리한다 — `archived` 여도 `coach_id` 는 남는다.

## 5. RPC 골격

### 5.1 쓰기 — 전부 DEFINER (§5.3 *"테이블 직접 쓰기 권한 0"*)

| RPC | 가드 |
|---|---|
| `feed_post_create(cohort_id, body, photo_path) → uuid` | `feed_can_access` · 본문·사진 동시 공백 거부 · **`photo_path` 접두사가 `{cohort_id}/{auth.uid()}/` 인지 검사**(경로 위조 차단) |
| `feed_post_delete(id)` | 본인 **OR** 그 기수 인도자 **OR** 운영자 → `deleted_at`·`deleted_by` 기록(soft) |
| `feed_comment_create(post_id, body) → uuid` | `feed_post_accessible` · **원글이 삭제됐으면 거부** |
| `feed_comment_delete(id)` | 본인 OR 그 기수 인도자 OR 운영자 → soft |
| `feed_react(post_id, emoji) → text` | `feed_post_accessible` · 같은 이모지 재호출 = **취소**, 다른 이모지 = **교체** |
| `news_comment_create(post_id, body) → uuid` | 로그인 · **발행된 글만**(초안에 댓글이 붙지 않게) |
| `news_comment_delete(id)` | 본인 OR 운영자 OR **그 소식 작성자**(§10-4 회신) |

**빈도 상한을 두지 않는다.** `/contact`(ADR-123 ②)는 `anon` 이 부르는 통로라 RPC 안 가드가
유일한 방벽이었지만, 피드는 **인증된 기수 멤버만** 부른다. 상한을 걸면 *"팔굽혀펴기 25개씩 3세트"* 를
세 줄로 나눠 쓰는 사람이 막히고, 그 마찰이 §3.1이 금지한 바로 그것이다.

### 5.2 읽기 — 판정이 필요한 것만 DEFINER

| RPC | 반환 · 가드 |
|---|---|
| `feed_my_cohorts()` | 내가 피드를 가진 기수(`kind='seminar'`, 멤버 또는 코치). **활성 우선·최근순** — 기본 선택이 여기서 정해진다(§5.1) |
| `feed_list(cohort_id, before, limit, mine)` | `feed_can_access` 가드 · 글 + 작성자명 + `photo_path` + 댓글수 + 반응요약(jsonb) + 내 반응. `mine=true` 가 §6.1 "내 걸음만" |
| `feed_comments(post_id)` | `feed_post_accessible` 가드 |
| `feed_flow(cohort_id, days)` | **코치·운영자 전용** — 날짜별 게시 건수만 |
| `feed_quiet(cohort_id, days)` | **코치·운영자 전용** — 최근 `days` 일 미게시자 목록 |

> **`feed_flow`·`feed_quiet` 는 참여자가 호출해도 거부한다.** 화면에서 감추는 것은 안전장치가
> 아니다(IA §5.8). 발주 §6.2가 요구한 *"참여자에게 이 정보가 새지 않는지 회귀 테스트로 잠근다"* 를
> **RPC 가드 + 통합테스트 단언**으로 이행한다.

### 5.3 삭제된 글은 어떻게 보이는가

§5.3이 soft delete 를 요구한 이유는 *"답글이 고아가 되지 않게"* 다. 그런데 soft delete 를
그냥 두면 **운영자가 지운 부적절한 본문이 테이블 직접 조회로 여전히 읽힌다.**

| 층 | 처리 |
|---|---|
| RLS `SELECT` | `deleted_at IS NULL AND feed_can_access(cohort_id)` — **직접 조회로는 안 보인다** |
| `feed_list`(DEFINER) | 삭제분을 **본문 없는 묘비**로만 낸다(`body=NULL`·`photo_path=NULL`·`deleted=true`) |

댓글 맥락은 살고 본문은 사라진다. **사진은 묘비로 남기지 않는다** — 바이트를 실제로 회수한다(§6).

## 6. 사진 — 버킷과 정리

```sql
INSERT INTO storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
VALUES ('feed-photos','feed-photos', false, 3145728, array['image/jpeg'])
ON CONFLICT (id) DO NOTHING;
```

정책 4종은 §2 표대로. **DB 트리거로 `storage.objects` 를 건드리지 않는다** —
`storage.protect_delete()` 가 직접 DELETE 를 막고, 그 트리거가 붙어 있으면 **차수 삭제 자체가
통째로 막힌다**(ADR-87 보정 2의 실측). 정리는 전부 앱의 Storage API 경로다.

**한 게시에 사진 1장**(§4). 클라이언트 리사이즈는 `LetterPhotos.processImage` 를 공용으로 올려
두 화면이 **같은 함수**를 쓴다 — 값을 두 번 적으면(2000px·0.85) 언젠가 갈린다.

**서명 URL 은 서버 응답에 싣지 않는다.** `feed_list` 는 `photo_path` 만 내고, 브라우저가
보이는 페이지 분량만 `createSignedUrls` 로 일괄 발급한다(`LetterPhotos` 와 같은 방식).
S-4 §2.2의 *"목록에 미리 싣지 않는다"* 를 지키면서 **사진은 인라인으로 보인다** —
클릭해야 보이는 사진은 카톡이 아니다.

**삭제 시 바이트 회수** — `feed_post_delete` 호출 **전에** 앱이 Storage API 로 먼저 지운다
(ADR-87 순서). 차수 하드삭제·참여자 제거 경로에도 같은 절을 단다. **§9-② 참조.**

| 라우트 | 내용 |
|---|---|
| **`/feed`** (신설) | 입력창 **맨 위 상시 노출**(접히지 않음) → 날짜 구분선 + 시간순(오늘이 위) → **더 보기** 버튼. "내 걸음만" 토글. 기수 전환은 **여럿일 때만** 노출 |
| `/coach/cohort/[id]` (증축) | 피드 요약 구획 — 최근 7일 흐름 · 조용한 분 목록. **색·순위·경고 없음** |

**게시 후 화면이 이동하지 않는다**(§3.1) — 서버 액션 후 그 자리에서 목록 맨 위에 붙는다.

### 8.1 경로 보호

| 항목 | 처리 |
|---|---|
| `PROTECTED_PREFIXES` | **`'/feed'` 추가** — 최상위 신설 접두사. `PROXY_MATCHER` 는 **한 글자도 건드리지 않는다**(불변식 17). 접두사 추가는 **넓히는 방향**이라 커버리지가 깨지지 않는다 |
| `safeReturnTo` | `/^\/feed$/` 추가 — **라우트와 같은 커밋에서**(§8 마지막 줄 · S-3 판정 ②) |

§8 실브라우저 표의 *"미인증 `/feed` → `/login?returnTo=/feed`"* 는 이 둘이 함께 있어야 성립한다.
`loginRedirectSearch` 는 **경로만** 싣고 쿼리는 버리므로 `?cohort=` 는 전파되지 않는다 —
기본 기수로 착지한다. **이 동작을 그대로 둔다**(`af6576d` 의 토큰 미전파 근거는 여전히 유효하다).

## 9. 실측 중 발견한 것 셋 — 조치 없이 보고한다

### ① 하단 탭이 **아예 없다**

발주 §6.3 — *"1차에서 피드 자리를 선점해 두었는지 확인하고, 없으면 이번에 넣는다."*

**선점되어 있지 않다. 하단 탭바라는 부품 자체가 없다** — `position:fixed`·`bottom-0` 실측 **0건**.
내비는 `AppHeader`(variant 3종) 하나뿐이다.

그런데 §7-9가 *"design_system에 없는 부품을 임의로 만들지 않는다"* 를 금하고, 탭바는
IA §9의 v4 요청 목록에도 없다. **불변식 20과 §6.3이 정면으로 만난다.**

> **판단: 탭바를 짓지 않는다.** `/feed` 진입은 기존 표면으로 낸다 —
> 통합 홈 역할 카드 아래 바로가기 · 차수 홈 · `AppHeader` 홈 아이콘.
> **탭바는 §12 부재 부품 목록에 올린다.**
> 근거 — 9/21 아침에 필요한 것은 **탭바가 아니라 링크**다. 인도자는 카톡으로 받은 `/feed` 를 누르거나
> 홈에서 한 번 탭한다. 탭바를 임의로 지으면 design_system v4 가 도착했을 때 **두 번 짓는다.**

### ② `deleteCohortAction` 이 사진을 회수하지 않는다 — **문서-코드 드리프트(기존)**

`20260802100200` 주석은 이렇게 적혀 있다:

> *"차수 하드삭제: `deleteCohortAction` 이 같은 방식으로 먼저 지운다."*

**실제 코드에는 그 절이 없다**(`src/app/coach/cohort/[cohortId]/actions.ts:14-22` — `getCohort` →
체험 차수 방어 → `deleteCohort`). 사진 회수는 `removeCohortMemberAction`(:90-100)에만 있다.

**1차 이전부터 있던 드리프트이고 2차가 만든 것이 아니다.** 다만 피드 사진이 같은 구멍을
물려받으므로 그대로 둘 수 없다. **조치는 완주 단계에서 하되, 범위를 명시한다** —
피드 사진 회수 절을 넣으면서 **같은 자리에 갈무리 사진 회수 절도 함께** 넣는다(한 줄 옆이다).
주석이 이미 그렇게 하기로 적어 둔 일이라 사양 변경이 아니라 **미이행분 이행**이다.

### ③ `my_cohorts()` 가 아직 코드 문자열로 거른다

`WHERE ... c.code <> 'TRASH'` — ADR-110이 세운 *"이름이 아니라 역할로 거른다. 이름 목록은 낡는다"* 와
ADR-122가 신설한 `cohorts.kind` 의 **미적용 잔여**다.

**이번 범위에서 건드리지 않는다.** 피드는 자체 `feed_my_cohorts()` 로 `kind='seminar'` 를 본다.
`my_cohorts()` 수정은 참여자 홈 전체가 물린 경로라 별도 발주 사항이다. **기록만 남긴다.**

## 10. 발주 §9 미확정 4건 — 회신

| # | 항목 | 회신 |
|---|---|---|
| 1 | **조용한 분 기준** | **3일 수용.** 단 RPC 파라미터로 두고 기본값 3(운영 중 조정 가능). 인도자 화면 전용 · 색·정렬·순위 없음 · *"3일째 소식이 없어요"* 라는 **사실 문장**으로만 |
| 2 | **이모지 종류** | **4개: 👏 🙏 💪 ❤️.** 한 사람 한 반응(교체·토글). 개수 정렬 금지. 4개는 한 줄에 들어가고 고르는 데 시간이 들지 않는다 |
| 3 | **1기 초기 상태** | **안내 글을 시스템이 넣지 않는다.** 대신 **빈 상태 문안**을 화면에 둔다. 자동 삽입 글은 작성자가 없어 삭제·반응의 주체가 모호해지고, §3.1의 *"인도자 아침 첫 글"* 문화와도 어긋난다 — **첫 글은 사람이 쓴다** |
| 4 | **소식 댓글 삭제** | 본인 + 운영자 + **그 소식 본문 작성자.** 피드에서 인도자가 자기 기수 글을 지우는 것과 대칭이다 |

### 10.5 신규 질의 하나 — `held`(보류) 계정의 피드 쓰기

IA §5.4 표는 **진단 응시**와 **결과 열람**만 다룬다. 피드는 그 축에 없다.

- **발주서대로 가면**: 보류 계정도 기수 멤버면 피드에 쓴다(별도 게이트 없음).
- **권고**: 읽기 유지 · **쓰기 차단.** 보류는 운영자의 유일한 계정 단위 차단 수단인데
  피드 쓰기가 열려 있으면 차단이 반쪽이 된다.
- **반대 근거도 적는다**: 피드는 카톡 대체이고, 쓰기 차단은 사실상 **대화방에서 내보내는 일**이다.
  무게가 진단 차단과 다르다.

> **회신이 없으면 발주서대로 간다**(게이트를 더하지 않는다). S-4 `/contact` 에서 *"제안하라"* 는
> 지시를 제안에서 멈추지 않고 실행까지 간 것이 절차 위반이었다. **같은 자리에서 두 번 넘어지지 않는다.**
