지시: *"빌드 id를 먼저 확보하라(위양성 선례 2회)."* 확보하려 했으나 **이번 빌드에는 그 마커가 없다.**

| 상태 | `READY` (`buildingAt` → `ready` 39초) |

| 별칭 | `futurenow-platform-git-feat-site-v2-2-chois-projects-6fad4da6.vercel.app` |

> **왜 빌드 id 가 없는가.** 1차까지는 HTML 에 `/_next/static/<buildId>/_ssgManifest.js` 가 있어
> 거기서 빌드 id 를 읽었다. 이 빌드는 **turbopack** 이라 청크가 **내용 해시**로 나가고
> (`/_next/static/chunks/12am21qpm4n9x` 형태) `<buildId>` 경로 세그먼트가 아예 없다.
> `get_deployment` 응답에도 buildId 필드가 없다. **없는 것을 있다고 적지 않는다.**
>
> **대신 더 강한 방법으로 위양성을 배제했다** — 검사를 **불변 배포 URL**(`…-mv41b7q25-…`)로 돌렸다.
> 그 호스트는 이 배포 하나만 가리키므로 **별칭이 옛 빌드를 서빙하는 위양성이 구조적으로 불가능하다.**
> 그리고 별칭과 배포 URL 의 응답이 **같은지 대조**해 별칭도 이 빌드를 서빙 중임을 확인했다(§1).

> **다음 발주에 넘길 항목**: 빌드 신원을 코드가 스스로 노출하게 두는 편이 낫다
> (`NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA` 를 응답 헤더나 `/api/version` 에 싣는 식).
> 지금은 배포 id + 커밋 SHA + 불변 URL 세 값으로 신원을 확정한다.

## 1. 검사 ① 미인증 `/feed` → `returnTo` — **PASS**

배포 URL·별칭 **둘 다** 같은 결과 → 별칭이 이 빌드를 서빙 중이다.

| # | 검사 | 실측 | 판정 |
|---|---|---|---|
| ①-1 | `/feed` 미인증 | **307** → `/login?returnTo=%2Ffeed` | **PASS** |
| ①-2 | **민감 쿼리 미전파** | `/feed?access_token=SHOULD_NOT_LEAK&cohort=abc` → **307 → `/login?returnTo=%2Ffeed`** (토큰·cohort **둘 다 탈락**) | **PASS** |
| ①-3 | 로그인 화면 실렌더 | HTTP 200 · `returnTo` 페이로드 존재 · `SHOULD_NOT_LEAK` **0회** | **PASS** |
| ①-4 | `/feed` 본문 민감 콘텐츠 | 본문 **15 bytes** · '동행'·'걸음' **0회** | **PASS** |

①-2 가 이번 검사의 값진 부분이다. `loginRedirectSearch` 가 **pathname 만** 받으므로
`access_token` 이 구조적으로 실릴 수 없다는 설계(S-3 · `af6576d` 근거 보존)가 **프로덕션 응답에서
확인**됐다. 단위테스트는 함수를, 이 검사는 **배포된 미들웨어**를 증명한다.

①-4 는 불변식 19 의 형태 확인이다 — 여기서는 **미들웨어 307** 이라 본문이 비어 있다.
(`/pending` 처럼 서버 컴포넌트 `redirect()` 로 200 + `__NEXT_REDIRECT` 가 오는 경로와 다르다.)

## 2. 검사 ② 기수 격리 — **PASS (실계정 23 전수 · 70/70)**

브라우저 세션이 없어 **화면으로는 못 봤다**(§4). 대신 **라이브 프로덕션 데이터**에서
실계정 23개를 전부 역할 시뮬레이션해 `feed_can_access` 와 `feed_my_cohorts()` 를 쟀다.
픽스처가 아니라 **실제 사람·실제 기수**다. 읽기 전용이고 전 과정 `ROLLBACK` 했다.

| 검사 | 대상 | 결과 |
|---|---|---|
| 비-세미나 차수 미노출 | 23계정 × `QKN2H`(test)·`TRASH`·`JOINF`(general) | **23/23 · 누출 0** |
| 세미나 차수 접근 = 기대 | 23계정 × `HMT7Z`(1기)·`ZR4KB`(2기) | **46/46** |
| 라이브 피드 글 0건 | 검증이 실데이터를 만들지 않았다 | **PASS** |
| **합계** | | **70 PASS / 0 FAIL** |

기대값 규칙: `admin` = 전체 접근(설계상 §5.1), 그 외 = **등록했거나 담당일 때만**.
한 계정도 어긋나지 않았다.

**대표 사례** — 1기에만 등록된 참여자는 `HMT7Z` 접근 `true` / `ZR4KB` 접근 **`false`**,
목록에도 1기만 뜬다. 어느 기수에도 없는 계정은 **둘 다 `false`** 이고 목록이 비어 있다.

> **`kind` 필터가 라이브에서 값을 냈다.** `QKN2H`(test)에는 참여자가 둘 있고 `TRASH` 에도 하나
> 있는데, 세 차수 모두 `status='active'` 다. `kind` 를 보지 않았다면 **그 사람들이 피드를 얻었을
> 것이다.** 이것이 설계 보고 §3.1 이 말한 그 자리이고, 이제 실계정으로 확인됐다.

**남은 층**: 화면에 다른 기수 글이 실제로 0건인지는 세션이 필요하다(§4). 다만
글 자체가 아직 0건이라 지금 화면으로 봐도 얻을 정보가 없다 — **글이 생긴 뒤에 의미가 생기는 검사**다.
