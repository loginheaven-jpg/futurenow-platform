## 0. 정정 하나를 먼저 적는다 — **빌드 id 는 사라지지 않았다. 자리를 옮겼다**

2차 §0에서 *"turbopack 전환으로 빌드 id 마커가 사라졌다"* 고 적었고 그것이 T-3(`/api/version`)의
근거였다. **그 진술은 과했다.**

| 내가 확인한 것 | 참/거짓 |
|---|---|
| `/_next/static/<buildId>/…` 경로 세그먼트가 없다 | **참** |
| `get_deployment` 응답에 buildId 필드가 없다 | **참** |
| **그러므로 빌드 id 마커가 없다** | **거짓** |

RSC flight 페이로드에 **`"b":"<buildId>"`** 가 있다. 병합 직전 프로덕션 응답을 읽다가 눈에 띄어
세 배포에서 대조했다 — **전부 다르다.**

```
futurenow-platform.vercel.app (병합 전)  → avEl5Xd3l-npTmsZ5isjc
프리뷰 ff90e44                            → M5QP6rcw5j5HBIM_ndS4_
프리뷰 d09f1d0                            → _4U_9SYJe8lzEthlDjle6
```

**두 곳을 보고 없다고 단정했다.** 세 번째 자리를 찾지 않았다.

### 0.1 그래도 `/api/version` 은 필요하다 — 이유는 다른 것이다

정정이 T-3을 무르지 않는다. 다만 **근거를 바꾼다.**

| | buildId(`"b"`) | `/api/version` |
|---|---|---|
| 배포마다 다른가 | ○ | ○ |
| **커밋 SHA 를 아는가** | ✕ | **○** — 저장소와 직접 대조된다 |
| **`deploymentId` 를 아는가** | ✕ | **○** — Vercel API 와 맞물린다 |
| 읽는 법 | HTML 안 이스케이프된 flight 페이로드를 정규식으로 | `GET` 한 번, JSON |

**옛 근거**(*"마커가 없다"*)는 틀렸고 **새 근거**(*"마커가 있어도 커밋·배포 id 를 말하지 못한다"*)가
맞다. 이번 병합에서 실제로 그 차이가 값을 냈다 — §2를 보라.

> **틀린 근거로 옳은 것을 만들 수 있다.** 그래도 근거는 고쳐 적는다. 그러지 않으면 다음 사람이
> *"turbopack 은 빌드 id 를 안 준다"* 를 사실로 믿고 다른 판단에 쓴다.

## 4. 이 회차가 남긴 것

### 4.1 결함 둘은 화면층에서 나왔다

| 어디서 | 무엇 |
|---|---|
| 리포트 패널 | **A의 해석이 B의 기록에 써지는 경로** — 표시가 아니라 데이터 오염 |
| 갈무리 `?edit=1` | **고쳐 쓰기가 닫혀 있었다** — 1기 45건 제출분의 유일한 수정 통로 |

**둘 다 단위·통합·DB 검증이 잡지 못했다.** 전부 옳게 동작했기 때문이다 —
판정 함수도 서버도 정확했고 깨진 것은 **상태 수명** 하나였다.
2차에서 화면층을 *"미완"* 으로 비워 둔 판단이 세 번째로 값을 냈다.
