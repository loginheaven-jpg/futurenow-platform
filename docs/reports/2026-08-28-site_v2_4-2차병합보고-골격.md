> **이 문서는 아직 보고가 아니다.** 최박사 승인 전에 **실행만 남기려고** 미리 짜 둔 틀이다.
> `⟪⟫` 는 실행 뒤 채운다. 병합이 끝나면 이 파일을 **정본 보고서로 이름을 바꿔** 낸다
> (`2026-08-28-site_v2_4-2차병합보고.md`) — 골격을 그대로 두면 다음 사람이 보고서로 읽는다.

- **선행 조건**: F-5 **B행(실기기) 통과** + 지휘부 감사 + **최박사 승인**

## 0. 실행 순서 (이대로 한다)

```
1) git branch --show-current          # main 직접 커밋 금지 — 확인이 막는다(CLAUDE §11)
2) git checkout main && git merge --ff-only origin/main
3) git merge --no-ff feat/site-v2-4 -F <메시지 파일>
4) npx tsc --noEmit && npx vitest run && npx next build     # push 전에 병합본을 다시 잰다
5) git push origin main
6) node scripts/postdeploy.mjs <병합 해시 짧은형>            # 배포 대기 + 실브라우저 5건
7) git ls-remote origin main                                # 원격 조회가 증거다
```

> **4번을 건너뛰지 않는다.** 병합 자체가 무언가를 깨뜨릴 수 있고, 그것을 push 뒤에 알면 늦다.
> **6번은 손으로 `curl` 을 치지 않는다** — 1~3차에서 별칭 응답으로 **위양성을 두 번** 냈다.
> 스크립트가 **배포 신원이 기대 커밋과 같아진 뒤에야** 5건을 잰다.

### 커밋 수 — **명령과 기준선을 미리 박는다**

1~3차에서 커밋 수가 **두 번 갈렸고(24/26 · 9/8) 둘 다 범위 차이**였다.
그래서 값을 재기 전에 **기준선과 명령을 여기 고정**한다 — 아침의 값이 논쟁 없이 서게.

**기준선은 `6a59cb0` 이다** — 1차 병합 보고 커밋이자 **지금의 `origin/main`** 이다.

```
$ git rev-parse --short origin/main                        → 6a59cb0   (기준선 확인. 다르면 멈춘다)

$ git rev-list --count 6a59cb0..⟪병합해시⟫                  → ⟪ ⟫   (병합 커밋 포함)
$ git rev-list --count --no-merges 6a59cb0..⟪병합해시⟫      → ⟪ ⟫   (실작업 커밋)
```

**둘의 차는 정확히 1**이어야 한다(`--no-ff` 병합 커밋 하나). 다르면 범위가 틀린 것이다.

> **⚠️ `1bb05f3..` 로 재지 않는다.** `1bb05f3` 은 1차 **병합 커밋**이고 그 뒤에
> **`6a59cb0`(1차 병합 보고)이 `main` 에 하나 더 올라가 있다.** 그래서 기준선을 그리로 잡으면
> 그 한 개가 더 세어진다. **밤중 실측으로 재현했다**:
>
> ```
> $ git rev-list --count 1bb05f3..origin/feat/site-v2-4   → 22
> $ git rev-list --count 6a59cb0..origin/feat/site-v2-4   → 21   ← 이쪽이 맞다
> ```
>
> **1 차이가 곧 지난 두 번의 논쟁이었다.** 기준선을 적어 두는 것이 그것을 끝낸다.
