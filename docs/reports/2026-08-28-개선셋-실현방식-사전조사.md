# 최박사 개선 셋 — 실현 방식 사전 조사 (착수 전)

> **범위 규율**: 지휘부 판정 전이므로 **저장소 코드 0줄 변경**이다. 이 문서와, 저장소 밖
> scratchpad 에서 돌린 읽기 전용 프로브가 전부다. 프로브는 **자격 값을 출력하지 않는다** —
> 쿠키 이름·만료·속성만 찍었다.
>
> 대상은 **운영**(`https://future.yebom.org`) · QA 참여자 계정 · Pixel 7 뷰포트.

---

## 0. 결론 먼저

| # | 최박사 요청 | 실측 결론 |
|---|---|---|
| ① | 로그인 암호를 로컬에 저장 | **저장할 필요가 없다.** 세션은 이미 **400일** 유지되고 있었다. 지휘부 릴레이 의견이 맞다 |
| ② | 반응 아이콘 복수 선택 | **UI 문제가 아니라 스키마 문제다.** `PRIMARY KEY (post_id, user_id)` 가 한 사람 한 개를 강제한다. 계약·마이그레이션·RPC·화면 **네 층**이 함께 움직인다 |
| ③ | 뒤로가기 연타에 팝업 | **로그아웃이 아니었다.** 뒤로 두 번이면 `/login` 화면에 닿는데 **세션은 그대로 살아 있다.** 로그아웃처럼 보였을 뿐이다 |

**①과 ③은 한 뿌리일 가능성이 높다** — §4.

## 1. ① 로그인 유지 — 이미 되고 있다

### 실측 (운영, QA 참여자로 로그인 직후)

```
sb-zdoytzmvcafcebytttrm-auth-token.0   400.00일 뒤 만료   httpOnly=false sameSite=Lax secure=false path=/
sb-zdoytzmvcafcebytttrm-auth-token.1   400.00일 뒤 만료   httpOnly=false sameSite=Lax secure=false path=/
```

**세션 쿠키가 아니라 영속 쿠키다.** 브라우저를 닫아도 남는다(400일은 Chrome 의 쿠키 수명 상한이라,
사실상 *"만료로는 끊기지 않는다"* 는 뜻이다). `src/proxy.ts` 가 매 요청에서 `getUser()` 로
토큰을 갱신하고 그 쿠키를 응답에 다시 실으므로, 쓰는 동안에는 갱신이 계속 돈다.

### 지휘부 릴레이 의견에 대한 답 — **맞다**

*"비밀번호 자체를 저장하는 것과 로그인 상태를 유지하는 것은 다른 일"* 이라는 지적이 정확하다.
그리고 실측이 한 걸음 더 말한다 — **로그인 상태 유지는 이미 켜져 있다.**
그러므로 최박사가 원하시는 *"다시 칠 필요가 없다"* 는 결과에는 **자격을 어디에 저장하는 설계가
전혀 필요 없다.** 앱이 비밀번호를 들고 있는 길은 규율(§10 · 불변식 13 계열)과 어긋날 뿐 아니라
**목적에도 불필요하다.**

### 그러면 왜 다시 치게 되셨나 — 후보 셋

1. **`/login` 화면을 보고 로그아웃으로 읽으셨다** — ③에서 실물로 확인했다. 가장 유력하다(§4).
2. 다른 브라우저·시크릿 창으로 여셨다(카톡 인앱 브라우저 ↔ 크롬은 쿠키가 별개다).
3. 리프레시 토큰 회전 실패 — 이번 실측에서는 재현되지 않았다.

### 브라우저 비밀번호 관리자 쪽 — 거의 다 돼 있다

[LoginForm.tsx](src/app/login/LoginForm.tsx#L54-L95) 는 이미 진짜 `<form>` + `type="submit"` +
`autoComplete="email"` / `autoComplete="current-password"` 다. 이것이 OS·브라우저 관리자가
저장·자동입력을 제안하는 표준 조건이다.

**빠진 것은 `name`·`id` 속성뿐이다.** 일부 안드로이드 관리자(삼성 인터넷 · 구형 WebView)가
`autocomplete` 보다 `name` 을 먼저 본다. **앱은 아무것도 저장하지 않으면서** 자동입력 적중률만
올리는, 규율과 충돌 없는 유일한 손질이다. (판정 사항 — 착수하지 않았다.)

## 2. ② 반응 복수 선택 — 네 층이 함께 움직인다

이모지 넷은 이미 있다: `👏` `🙏` `💪` `❤️` — **박수와 기도 둘 다 존재한다.**
막는 것은 화면이 아니라 **표의 기본키**다.

| 층 | 지금 | 복수 선택이 되려면 |
|---|---|---|
| **표** | `feed_reactions` `PRIMARY KEY (post_id, user_id)` | PK 에 `emoji` 를 더한다 → **새 마이그레이션**(불변식 15 — 적용된 파일은 못 고친다) |
| **RPC** | `feed_react` — *"같은 이모지는 취소, **다른 이모지는 교체**"*, `ON CONFLICT … DO UPDATE SET emoji` | 교체가 아니라 **토글**로. 반환도 하나가 아니라 목록으로 |
| **목록 RPC** | `RETURNS TABLE(… my_reaction text)` | `text[]` |
| **계약** | `myReaction: FeedEmoji \| null` ([domain.ts:356](src/contracts/domain.ts#L356)) | `FeedEmoji[]` — **불변식 3: `/contracts` 변경은 지휘부 승인 후에만** |
| **화면** | `FeedClient` 가 단일 값으로 낙관적 갱신 | 집합으로 |

참조 규모: `myReaction`/`my_reaction` **8곳 · 5파일**, `feed_react` 계열 **5파일**
(통합테스트 `tests/feed.integration.test.ts` 포함).

**주의할 것 하나** — 반응 집계(`reactions`)에는 *"정렬에 쓰지 않는다"* 는 주석이 달려 있다
(불변식 11 · 순위를 만들지 않는다). 복수 선택은 합계를 키우므로, **숫자가 커질수록 순위처럼 읽히지
않게** 하는 판단이 함께 필요하다. 기능이 아니라 규율 쪽 질문이다.

## 3. ③ 뒤로가기 연타 — **로그아웃이 아니다**

### 실물 확인 (운영 · Pixel 7)

사람이 실제로 걷는 길로 쌓고 되돌렸다: 현관 `/` → `/login` → 로그인 → `/home` → `동행` → `/feed`.

```
뒤로 1회: /home
뒤로 2회: /login      ← 여기서 "로그아웃됐다" 로 보인다
뒤로 3회: /
뒤로 4회: blank       ← 사이트 이탈
뒤로 5회: 그대로 — 스택 끝

연타 뒤 sb-* 쿠키 2개 잔존 · /home 요청 → /home  →  세션 살아 있음 · 로그아웃 아님
```

### 왜 그렇게 되나 — 원인 둘이 겹친다

1. **`/login` 이 이미 로그인한 사람을 되돌려 보내지 않는다.**
   [page.tsx](src/app/login/page.tsx) 는 세션을 보지 않고 폼을 그대로 그린다.
2. **로그인 성공이 `router.push` 다**(`replace` 가 아니다) —
   [LoginClient.tsx:34](src/app/login/LoginClient.tsx#L34). 그래서 `/login` 이 히스토리에 남는다.

`signOut()` 호출 지점은 저장소 전체에 **단 하나**, [LogoutButton.tsx:17](src/app/_screens/LogoutButton.tsx#L17) 뿐이다.
뒤로가기는 그것을 부르지 않는다. **안드로이드 뒤로가기와 세션 종료가 묶여 있는 것이 아니다** —
지휘부가 짚어 준 가설은 실물로 **부정**됐다.

### 팝업(최소/종료)에 대한 사실

- **현재는 PWA 가 아니다.** `manifest` 파일도 서비스 워커도 없다(전수 확인).
- 브라우저 탭에서 **마지막 뒤로가기를 가로채 "최소화"하는 방법은 없다.** 최소화는 설치형 앱의
  개념이고, 웹은 이탈 시 커스텀 다이얼로그를 띄울 수 없다(`beforeunload` 는 브라우저 기본 문구뿐이며
  뒤로가기 이탈에는 대개 뜨지도 않는다).
- 가능한 근사는 **history sentinel** — `pushState` 로 한 겹을 깔아 두고 마지막 뒤로가기를 받아
  확인 시트를 띄우는 방식. 다만 *"종료"* 는 진짜로 나가는 것까지가 한계이고 *"최소화"* 는 의미가 없다.
- **그런데 §3 의 실물 확인이 말하는 것은, 최박사가 겪으신 문제의 대부분이 팝업 없이 사라진다는 것이다** —
  `/login` 이 로그인한 사람을 홈으로 돌려보내기만 해도 *"로그아웃된 것 같다"* 는 경험이 없어진다.

## 4. ①과 ③은 한 뿌리일 수 있다

①의 *"다시 로그인해야 한다"* 와 ③의 *"로그아웃이 일어난다"* 가 **같은 화면 하나**를 가리킨다 —
뒤로가기로 닿은 `/login`. 세션은 살아 있는데 로그인 폼이 보이니 다시 치신 것이고,
다시 치면 실제로 들어가지므로 *"역시 로그아웃이었구나"* 로 굳는다.

**그래서 순서를 제안한다** — `/login` 의 인증 리다이렉트(+`replace`) 하나를 먼저 놓고
그 뒤에 ①·③ 이 여전히 남는지 최박사께 다시 여쭙는 편이 낫다. 두 요청 모두 그 한 수로 사라질 수 있다.
(제안이고, **착수하지 않았다.**)

## 6. 측정 도구를 먼저 측정했다 — 이번에도 한 번 걸렸다

첫 프로브가 **`page.goBack()` 의 반환값**으로 판정했더니 *"1회 만에 스택 끝"* 이라고 나왔다.
`history.length` 가 5인데 말이 안 됐다. 원인은 **App Router 의 클라이언트 뒤로가기가 문서
내비게이션이 아니라서** `goBack()` 이 `null` 을 준다는 것이다 — **이동은 했는데 "못 갔다"로 읽혔다.**

반환값 대신 **URL 로 판정**하도록 고친 뒤에야 `/feed → /home → /login → / → 이탈` 이 나왔고,
그것이 최박사 증언과 맞는다. **틀린 도구를 그대로 믿었다면 *"뒤로가기는 두 번이면 끝난다"* 라고
보고할 뻔했다.** §11 의 *측정 도구를 먼저 측정한다* 가 이번에도 값을 했다.

## 7. 부수 관찰 — 판정 사항 아님, 기록만

세션 쿠키가 **`secure=false`** 로 설정된다(브라우저 클라이언트가 `document.cookie` 로 심기 때문).
`httpOnly=false` 는 브라우저 클라이언트가 읽어야 하므로 구조상 그렇다.

**실질 위험은 좁다** — 운영은 `http → https` **308** 이고 `Strict-Transport-Security: max-age=63072000`
(2년)이 걸려 있어, 노출 창은 *그 기기가 이 도메인에 생애 처음 평문으로 닿는 순간* 뿐이다.
다만 **좁은 것과 없는 것은 다르므로** 기록해 둔다. 5차 UI 체계 작업 때 함께 볼 만하다.

## 8. 5차 예고 둘 — 받아 적어 둔다

최박사가 예고하신 큰 것 둘을 그대로 옮긴다.

1. **회원 레벨 문제.**
2. **전반적인 UI 체계** — *"전반적으로 design system 을 손봐야 한다, 현재 UI 체계가 엉망이다."*

②는 `design_system.md` 가 v7 까지 **회차마다 덧붙는 방식**으로 자라 온 것과 무관하지 않을 것이다
(§9.7 부품 15 · §11 부채 목록 · 골드 대비 A안 · 본문 크기 골드 글자색 부재 등이 그 자국이다).
어제 붙인 `tests/designParts.test.ts` 가 **부품 목록과 실물을 묶어 두었으므로**, 5차에서 체계를
다시 세울 때 *"문서에는 있는데 코드에는 없는"* 항목부터 걸러진다. 그 정도가 지금 해 둘 수 있는 준비다.
