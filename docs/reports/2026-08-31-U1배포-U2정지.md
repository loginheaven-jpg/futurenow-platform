## 1. ① OG 고정 — **예상한 「남는 것」이 생기지 않았습니다**

지휘부가 *이미 카톡이 물고 있는 옛 URL 은 404 로 남는다* 고 하셨는데, **살릴 수 있었습니다.**

라이브 태그가 이랬습니다:

```
https://future.yebom.org/recruit/opengraph-image.png?opengraph-image.2ekk20w6t2w34.png
```

**해시가 파일명이 아니라 쿼리**였습니다. 정적 파일은 쿼리를 무시하므로, 이미지를
`public/recruit/opengraph-image.png` — **지금 배포된 것과 같은 경로**에 두면 옛 링크가 그대로 삽니다.

**운영 실측(배포 후)**:

```
og:image  https://future.yebom.org/recruit/opengraph-image.png     ← 해시·쿼리 없음
옛 카톡 URL(쿼리 포함)  200 · image/png · 76,926B                    ← 그대로 산다
```

`public/` 은 경로가 곧 URL 이라 **앞으로 파일을 어디로 옮겨도 이 URL 은 안 바뀝니다.**
`alt` 문장은 `opengraph-image.alt.txt` 에서 코드 상수로 옮겼습니다(사본을 만들지 않습니다).

## 4. ⑤ U-2 — **§2 의 전제가 무너집니다**

지시대로 U-0 도구로 먼저 쟀고, **수를 믿지 말라는 경고가 맞았습니다.**

### 대상 13파일이 **두 종류**입니다

**A. `SiteGnb` — 진짜 껍데기 상단바 (3)**

```
/home/HomeScreen.tsx · /home/assessments/AssessmentsScreen.tsx
/my/cohorts/[cohortId]/CohortHomeScreen.tsx
```

**B. `AppHeader` — 화면 제목 바 (10)** · 전부 **화면마다 다른 제목**을 싣습니다

```
/account            variant="root"  title="내 정보"          action=HeaderActions
/feed               variant="sub"   title="피드"             backHref="/home"
/pending            variant="sub"   title="승인 신청"
/my/values          variant="flow"  title={VALUE_TOOL}
/my/cohorts         variant="root"  title="내 기수"          action=HeaderActions
/my/cohorts/[id]/checkin/[session]  variant="sub" title="회차별 갈무리" backHref={`/my/cohorts/${id}`}
/my/cohorts/[id]/journey            variant="sub" title="여정 기록"     backHref={…}
/my/cohorts/[id]/report             variant="sub" title="내 리포트 신뢰" backHref="/my/cohorts"
/my/cohorts/[id]/values             variant="flow" title={VALUE_TOOL} subtitle={cohort.name}
/_consent/ConsentGate.tsx           variant="root" title="개인정보 동의"
```

**껍데기는 화면마다 다른 제목과 뒤로 목적지를 알 수 없습니다.**
그대로 걷으면 **제목 10개와 뒤로 목적지 5개가 사라집니다** — `/join` 에서 걸린 벽과 같고 규모가 큽니다.

### 그리고 더 무거운 것 하나 — `variant="flow"`

`AppHeader` 정의가 이렇게 적고 있습니다.

> `variant='flow'` : 제목 + (선택)부제만. 로고·뒤로·홈·액션 없음 —
> 진입 선형 플로우(진단)용, **일부러 출구 없음**.

`/my/values` 와 `/my/cohorts/[id]/values` 가 그것입니다.
**껍데기가 메뉴를 달면 「일부러 없앤 출구」가 되살아납니다.** 규칙 2를 지키려다 설계 의도를 깹니다.

### §1 목록도 셋 어긋납니다

- §0 의 **17화면** → 실측 **13파일**
- **`/home/assessments` 가 §1 목록에 없습니다** — 실제로는 `SiteGnb` 를 그립니다(A군)
- `/c/[code]/[session]`·`/c/[code]/values` 는 **지금 무헤더**라 이관이 아니라 **신설**입니다

## 5. 판단 필요 — 안 셋

**(가) 제목 바를 본문의 첫 요소로 내린다.** 껍데기는 상단바만 그리고, 화면은
`<PageTitle title=… back=…/>` 같은 얇은 부품을 본문 맨 위에 둔다.
→ **새 부품이 필요**하고 `design_system` 에 「제목 바」 항이 없어 불변식 20 입니다.

**(나) A군 3화면만 이번에 걷고 B군 10은 U-4 로.**
→ 안전하나 회원 영역이 갈린 채 남습니다.

**(다) 라우트별 제목·뒤로 표를 껍데기가 든다.** 제목과 뒤로는 **라우트의 성질**이므로
표 하나에 모으고 껍데기가 읽는다. 동적 세그먼트는 함수로 담는다.
`flow` 화면은 표에 **「출구 없음」 표시**를 두어 껍데기가 메뉴를 달지 않는다.
→ **제 안은 (다)** 입니다. 규칙 1을 지키면서 기능을 하나도 잃지 않고,
   제목·뒤로가 **한 곳**에 모여 사본이 생기지 않습니다. 새 시각 요소도 만들지 않습니다.
   다만 **껍데기가 라우트를 아는 것**이 맞는지는 지휘부 판단입니다.

**§3(메뉴 시트 껍데기 승격)은 (가)(나)(다) 어느 쪽이든 할 수 있습니다.**
`buildMemberSheet` 가 이미 자료를 한 곳에서 만들고 있어 layout 이 그것을 부르면 됩니다.
공개 껍데기에도 같은 부품을 물리면 **모바일 메뉴 부재**가 함께 닫힙니다.
