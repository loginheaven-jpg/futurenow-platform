# 완주 보고 — 조회 실패 ≠ 행 부재 (ADR-179)

---

## 0. 한 줄

`loadCurrentUser` 가 `users` 조회의 **`error` 를 안 보고 있었습니다.**
그래서 **조회가 실패한 것과 행이 없는 것이 같은 길로 흘렀고**, 실패해도 `role: 'user'` 가 나가서
**코치·운영자가 조용히 참여자로 내려앉았습니다.**

---

## 1. 새 관용구를 들이지 않았습니다 — **빠진 자리를 이웃에 맞췄습니다**

바로 이웃한 여섯이 이미 그렇게 합니다.

```
getPhone 실패 · setPhone 실패 · getContactDetail 실패 · setContact 실패
recordConsent 실패 · listMyConsents 실패     ← 전부 if (error) throw new CoreError(...)
loadCurrentUser                              ← 이 한 줄만 빠져 있었다
```

**행이 없는 것은 그대로 뒀습니다** — 가입 트리거 직후에 실제로 그렇고, **그때는 오류가 아닙니다.**

### 1.1 `null` 을 내지 않은 이유 — 되돌이

실패에 `null` 을 내면 게이트가 `/login` 으로 보내는데,
`/login` 은 세션이 살아 있으면 **다시 그 화면으로 돌려보냅니다**(`login/page.tsx` 소건 1-가).
**고리가 됩니다.** 던지면 고리가 없고, 무엇이 잘못됐는지가 드러납니다.

**계약은 안 건드렸습니다** — `currentUser(): Promise<CoreUser | null>` 그대로입니다(불변식 3).

---

## 2. ★★ 앞선 제 보고를 정정합니다

ADR-176 §7 ⒞ 에 「**서버 게이트 26곳이 사실상 발화하지 않는다**」고 적었습니다. **과장이었습니다.**

정본을 읽으니 프록시는 `VERIFIED_UID_HEADER` 를
**⑴ 들어오는 요청에서 먼저 지우고**(위조 방어 · 불변식 17)
**⑵ 세션이 있을 때만** 세웁니다.

| 상황 | 헤더 | `currentUser` | 게이트 |
|---|---|---|---|
| 미인증 | **없음** | `getUser()` 폴백 → `null` | **정상 발화** |
| 인증됨 | 있음 | 신원 확정 | 안 도는 것이 **옳다** |

**게이트는 죽지 않았습니다.** 안 도는 것은 **인증된 사람뿐**이고 그때 안 도는 것이 맞습니다.
**진짜 결함은 죽은 게이트가 아니라 「실패와 부재의 혼동」**이었고, 그것이 이번에 고친 것입니다.

## 3. ★★ 감사가 **제 처방의 실제 피해**를 잡았습니다 — 함께 고쳤습니다

`ResponseRunner.submit()` 에 **`catch` 가 없었습니다.**

```
async function submit() {
  setSubmitting(true);
  try { … } finally { setSubmitting(false); }   ← catch 없음
}
```

async 이벤트 핸들러의 예외는 **에러 경계로 가지 않고 처리되지 않은 거절**이 됩니다.
**참여자가 진단을 다 풀고 제출했는데 단추 잠금만 풀리고, 아무 문구도 없이 응답이 저장되지 않습니다.**

**이것은 원래 있던 결함입니다** — 저장 자체가 실패해도 같았습니다. 이번 변경이 **그 창을 넓혔습니다.**

**처방** : 잡아서 담아 두고 **렌더에서 다시 던집니다.** 기존 경계(`app/error.tsx`)가 받습니다 —
**새 화면도 새 문안도 만들지 않았습니다**(불변식 20).

**왜 「조용히 넘어가기」가 아닌가** : `saveResponse` 는 `user_id` 를 **그대로 넣습니다.**
`null` 로 저장하면 **로그인한 참여자의 응답이 익명으로 귀속**됩니다. 그러니 **보이게 실패**해야 옳습니다.

**답은 잃지 않습니다** — 500ms 디바운스로 로컬에 계속 저장되고 복원 경로가 있습니다(잠금이 그 타이머를 잽니다).

---

## 4. ★ 손대지 않은 것 — **새 성질이 아니어서**입니다

던진 문안이 `X 실패: <원문>` 이라 액션 봉투를 타고 화면에 닿을 수 있습니다.
**그런데 그것은 이미 있는 부류입니다.**

- `values` 화면은 **오늘도** `saveMyValueProgress 실패: <원문>` 을 경고색으로 그립니다(실측).
- 여과(`surface`)를 둔 곳은 **`feed` 와 `news` 둘뿐**입니다.
- 오류 문자열을 화면에 그리는 자리 : `feed` · `values` · `contact` · `library` · `join` · `signup` · `news` · `admin/approvals` · `CreateCohort`.

**제 변경은 열두 개 넘는 기존 출처에 하나를 더할 뿐 새 부류를 만들지 않습니다.**
그래서 **한 파일만 고쳐 불균형을 만들지 않고** 부류로 보고합니다(§7-1).
문안 신설은 최박사 결재 사안이므로 임의로 만들지 않았습니다.

## 5. 잠금을 물려 봤습니다

| 변이 | 결과 |
|---|---|
| 옛 모양으로 되돌림(실패를 삼킨다) | **붉어짐** |
| 부재까지 오류로 바꿈(가입 직후가 깨진다) | **붉어짐** |
| 실패에 `null` 을 냄(되돌이 위험) | **붉어짐** |
| 원인 문자열을 삼킴 | **붉어짐** |
| `submit` 의 `catch` 를 도로 없앰 | **붉어짐** |
| 렌더 재던짐 제거(잡기만 하고 끝) | **붉어짐** |
| 잡고 아무것도 안 함(삼킴) | **붉어짐** |
| 자동 로컬 저장 제거 | **붉어짐** (창을 좁힌 뒤) |

**셋을 각각 먹여서 갈랐습니다** — 오류 · 부재 · 정상. 「있는가」가 아니라 **값**입니다.

### 5.1 그중 둘이 처음에 안 물어 고쳤습니다

| 안 문 잠금 | 왜 | 고침 |
|---|---|---|
| 「자동 저장이 있는가」 | **수동 중간저장에 같은 이름이 있어** 통과(⑬) | **디바운스 타이머 안**만 본다 |
| `submit` 창 | **중첩 블록의 닫는 괄호**에서 일찍 닫힘(⑨-a) | **함수 자신의 들여쓰기**로 닫는다 |

### 5.2 ★ 행동 창이 없는 것을 적어 뒀습니다

vitest 환경이 `node` 이고 `@testing-library/react` 가 없어 **클릭을 흉내 낼 수 없습니다.**
그래서 `submit` 은 **구조로** 쟀고, **환경이 바뀌면 그 잠금이 울도록** 해 뒀습니다 —
그때 구조 잠금을 행동 잠금으로 바꾸면 됩니다(⑨-c).

## 7. 판단을 청합니다

1. **오류 원문이 화면에 닿는 부류**(§4) — 여과가 `feed`·`news` 둘에만 있습니다.
   한 곳에 여과를 두고 전부가 그것을 쓰게 하려면 **사용자 문안이 필요**하고 그것은 결재 사안입니다.
2. **`error.tsx` 의 「다시 시도」** — Next 16 정본은 `reset()` 이 **서버 컴포넌트를 다시 부르지 않는다**고 적습니다
   (감사 인용). 서버에서 던지는 실패가 늘어난 지금, 그 단추가 약속하는 복구가 실제로 일어나는지
   **확인이 필요합니다.** 화면 부품이라 임의로 고치지 않았습니다(불변식 20).
3. **운영자 실측**은 여전히 막혀 있습니다(QA 운영자 계정 없음) — case 4 는 단위 잠금으로만 확인했습니다.
