## 1. 반박③ — 내 측정이 틀렸다. 원인을 남긴다

자신감이 4~5건이 아니라 **제출 24건 중 16건(67%)** 이다. 재측정으로 확인했다.

**원인은 내 쿼리다.**

```sql
count(*) FILTER (WHERE answers->>'confidence' ~ '^[0-9]+$')
```

`answers->'confidence'` 는 전부 **`number` 타입**으로 저장돼 있다. `->>` 로 뽑아 정규식을 걸면 상당수가 탈락한다. **데이터가 없다고 본 것이 아니라 내 도구가 걸러낸 것이다.**

이것이 이번 라운드에서 가장 나쁜 오류다. 내가 §1-1 에 *"실측이 설계를 바꿨다"* 고 써 놓고 **잘못 잰 값으로 신호 규칙을 강등**했다. 사실 대조 누락과 달리 이건 **틀린 근거로 설계를 바꾼 것**이라 그 결정이 하류로 번진다.

**규율로 남긴다.**

> JSONB 값을 셀 때는 **저장 타입을 먼저 확인한다**(`jsonb_typeof`). `->>` + 정규식은 타입이 확인된 뒤에만 쓴다.

### 1-1. 따라 바뀌는 것 셋

**§1-1 문장 정정.** *"실행 자신감 응답이 제출 24건 중 4~5건뿐"* → **`제출 24건 중 16건(67%)`**. *"원안의 자신감 하강 신호는 재료가 없어 대부분 작동하지 않는다"* 를 **삭제한다.**

**§5-1 ③ 정정.** *"실측상 이 열의 대부분이 `—` 다"* → 반대다. **대부분이 숫자다.** `—` 표기 규칙은 그대로 두되(미응답을 0으로 오해하지 않게), 근거 문장을 지운다.

**§6 신호 재판정.** `자신감 하강` 을 **주 신호로 올린다.**

### 1-2. 신호 규칙 최종

| 신호 | 조건 | 급 | 1기 재료 |
|---|---|---|---|
| **작성 중 방치** | `drafting` 이고 `closes_at` 지남 | 주 | **10건** |
| **연속 미착수** | 열린 회차 2회 연속 `empty` | 주 | 있음 |
| **자신감 하강** | 두 회차 연속 하강(양쪽 응답 있을 때만) | **주** | 16건 |
| 연락 요청 | `contact_request` | 보조 | **0건** |
| 결산 악화 | `했습니다` → `잊고 지냈습니다` | 보조 | 0건 |

**`연락 요청` 을 주에서 보조로 내린다.** 1기 실측 0건이다. 급을 나눈 이유가 *"다섯을 다 강조하면 아무것도 강조되지 않는다"* 였는데, 재료가 없는 것을 주에 두면 그 자리가 낭비된다. **켜지면 그때 눈에 띄게 하면 된다** — 조건은 그대로 두고 표시 급만 내린다.

주 신호가 셋이 됐다. 넷을 넘기지 않는다.

## 2. 반박② — 축을 재지정한다

`summaryFields[0]` 규칙이 성립하지 않는다. 실물을 확인했다.

| 회차 | `[0]` | 종단 축이 원하는 것 | 인덱스 |
|---|---|---|---|
| 1 | 갈망 | 갈망 | **0** ✓ |
| 2 | 영역 | **인생의 한 문장** | **1** |
| 3 | 지금 가장 바라는 것 | 지금 가장 바라는 것 | **0** ✓ |
| 4 | 이번에 시작할 프로젝트 | **인생의 원씽** | **3** |
| 5 | 바꾼 환경 | 바꾼 환경 | **0** ✓ |

**`[0]` 을 기계적으로 뽑으면 다섯 중 둘이 축에서 벗어난다.** 4회차는 `이번에 시작할 프로젝트`(우당탕탕 계열)가 나오고 정작 `인생의 원씽` 이 빠진다. **이 화면의 존재 이유가 종단 축인데 그 축이 안 선다.**

지시서 표의 3회차 라벨(`간절한 영역`)도 실제 원문(`지금 가장 바라는 것`)이 아니었다. *"새 문안을 만들지 않는다"* 고 해 놓고 표 자체가 원문이 아니었다.

**`AXIS_INDEX` 를 승인한다.**

```ts
/** 종단 축(index.ts Mirror.back 주석: 갈망1 → 한 문장2 → 영역3 → 원씽4 → 환경5)
 *  → 각 회차 summaryFields 인덱스. 라벨·키·값은 전부 문안이 준다 — 여기는 '어느 것' 만 정한다.
 *  회차 문안이 바뀌면 journey.test.ts 가 먼저 레드가 된다. */
const AXIS_INDEX: Record<number, number> = { 1: 0, 2: 1, 3: 0, 4: 3, 5: 0 };
```

**테스트로 잠근다.** 이 표가 가리키는 라벨이 예상 문자열과 같은지 단언한다 — `갈망` · `인생의 한 문장` · `지금 가장 바라는 것` · `인생의 원씽` · `바꾼 환경`. 문안이 바뀌거나 `summaryFields` 순서가 바뀌면 여기가 먼저 잡힌다.

**6·7회차는 발주 시 이 표에 한 줄씩 더한다.** 6회차 지시서에 그 항목을 넣는다.

**§5-1 ② 표의 라벨을 실제 원문으로 고친다.**

## 3. 반박① — 익명 제안을 ⑤에서 뺀다

`readModel.ts:195` 가 이미 `isSelf || !flags.suggestionAnon` 로 거르고 있고, 그 주석이 **지휘부 결정 2026-08-02** 를 명시한다. 무기명 수집 경로(`readAnonSuggestion`·`anonNoticeText`)도 이미 있고 회차 현황이 그것을 쓴다.

**내 지시가 확정 결정을 뒤집었고, 참여자에게 한 약속도 어겼다.**

> 이름 없이 전달합니다. 다만 인원이 적은 차수에서는 글의 결로 짐작될 수 있습니다.

**약속한 것은 "짐작될 수 있다"이지 "시스템이 이름을 붙인다"가 아니다.** 지시서 방식은 짐작이 아니라 확정 식별이다.

그리고 화면 A 가 자기 안에서 모순됐다 — ⑤는 이름과 함께 보이고 ⑦(`buildCheckinRead`)은 같은 문장을 빼므로, **한 화면에서 위에는 있고 아래는 없다.**

**논거도 거꾸로였다.** *"한 사람 화면이라 익명이 성립하지 않는다"* → 그러므로 **거기 실으면 안 되는 것**이다.

**조치.** ⑤에서 `need` · `contact_request` 는 그대로 모으고, `suggestion` 은 `!suggestionAnon` 일 때만. **`readModel` 의 판정을 그대로 재사용한다** — 코드가 줄고 ⑤·⑦이 일치한다. `익명 요청` 표시도 두지 않는다.

## 4. 보완① 명단 role 필터 — ⓑ 채택, §2 를 완화한다

1기 `enrollments` 11명 중 `role='user'` 9명, `coach` 1 · `admin` 1 이다. `cohort_member_directory` 에 role 필터가 없고 `MemberRef` 에 `role` 이 없다.

**그대로 두면 화면 B 에서 운영자 둘이 참여자 행으로 뜨고, 그들이 제출하지 않으므로 주 신호가 켜진다.** 인도자가 "오늘 연락할 사람" 목록에서 자기 자신을 본다.

**ⓑ(RPC 에 role 필터)를 채택하고 §2 의 `RPC 0` 을 완화한다.**

근거가 셋이다.

**ⓐ는 계약을 넓히고도 문제를 못 닫는다.** `MemberRef` 에 `role` 을 더해도 RPC 가 돌려주지 않으면 값이 안 온다. 결국 RPC 를 고쳐야 하므로 계약 변경이 **덤으로 붙을 뿐**이다.

**ⓒ는 화면 B 의 용도를 반쯤 죽인다.** 이탈 발견·소그룹 편성·연락 대상 고르기 셋 다 잡음을 탄다.

**ADR-110 이 같은 문제를 `u.role='user'` 로 이미 풀었고** *"이름이 아니라 역할로 거른다 — 이름 목록은 운영자가 바뀔 때마다 낡는다"* 를 적었다. **같은 원칙을 여기에도 적용한다.**

**다만 회귀를 주의한다.** `listCohortMembers` 는 회차 현황(`checkin/page.tsx:34`)도 쓴다. RPC 를 고치면 **그 화면의 명단도 함께 줄어든다.**

**그것이 옳은 변화다** — 회차 현황에서도 운영자가 참여자 행으로 뜰 이유가 없다. 다만 **의도된 변화이므로 보고에 명시하고 회귀 테스트로 잠근다.**

```
□ cohort_member_directory 가 role='user' 만 돌려준다
□ 회차 현황 명단이 9명이다 (11 → 9, 의도된 변화)
□ 화면 B 격자 행이 9다
□ 운영자·인도자 계정으로 조회해도 자기 행이 명단에 없다
```

인도자 본인이 명단에서 빠지는 것이 맞다 — **명단은 코칭 대상이지 참가자 목록이 아니다.**

## 6. 보완③④ — 테스트 두 줄

**③ pair 변형.** `summaryFields` 가 `{label, key} | {label, from, to}` 유니온이고 **1회차 축이 pair 다**(`desire_from` → `desire_to`). §8 에 한 줄 더한다.

```
□ 종단 축 — pair 변형(1회차)이 from → to 형태로 조립된다
```

**④ 배달 검증.** §9 가 *"화면 C — 자신감·남긴 말·신호가 없다(테스트로 잠금)"* 이라 했는데 §8 은 전부 순수 함수 테스트다. **순수 함수가 옳은 값을 내도 컴포넌트가 다른 경로로 그릴 수 있다.**

ADR-109 가 정확히 그 실패였다 — 심화 `placeholder` 가 선언돼 있는데 렌더가 안 넘겨서 화면에 안 나왔고, 리터럴 잠금·`copyBaseline`·금지어 검사가 **전부 통과**했다. 그때 세운 것이 **배달 검증**이다.

```
□ 화면 C 렌더 산출물에 자신감 숫자·인도자에게 남긴 말·신호가 없다 (renderToStaticMarkup)
```

**§8 이 스스로 "화면 분기라 타입이 안 잡는다"고 썼는데, 순수 함수 테스트도 안 잡는다.** ADR-109 의 교훈이 여기서 두 번째로 값을 낸다.

## 10. 이번 라운드 기록

**반박 넷 중 셋이 내 오류이고, ③은 성격이 특히 나쁘다.**

지금까지 내 오류는 대개 **사실 대조 누락**이었다 — 소스를 안 보고 기억으로 쓴 것들이다. 그건 발행 전 확인으로 막힌다.

③은 다르다. **소스를 봤고 DB 도 쿼리했는데 도구가 틀렸다.** 그리고 그 값으로 §1-1 에 *"실측이 설계를 바꿨다"* 고 적고 신호 규칙을 강등했다. **틀린 근거가 설계 결정으로 굳고 하류로 번지는 경로**이며, 결론이 그럴듯해 아무도 근거를 다시 보지 않는다.

클코1 이 재측정하지 않았으면 `자신감 하강` 이 보조로 굳었을 것이고, 1기에서 가장 재료가 두꺼운 신호를 못 쓰게 됐을 것이다.

**앞으로 DB 실측을 근거로 설계를 바꿀 때는 그 쿼리 자체를 보고에 싣겠다.** 값만 적으면 도구의 오류가 보이지 않는다.

그리고 **모집 카드 8 열람 범위 문구**가 세 번째 보고다. 이번 범위 밖이나 지휘부가 별건으로 처리하겠다.
