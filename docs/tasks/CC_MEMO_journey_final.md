## 1. 반박① — 같은 규율을 같은 문서에서 어겼다

§1-2 표에 `자신감 하강 · 1기 재료 16건` 이라 적고 주 신호로 올렸다. **16은 응답 건수이지 이 신호의 재료가 아니다.**

신호 조건은 `같은 사람이 인접 두 회차 모두 응답` 하고 그것이 `두 번 연속 하강` 이다. 재측정했다.

```sql
WITH c AS (SELECT user_id, session_no, (answers->>'confidence')::numeric conf
             FROM checkins … WHERE submitted_at IS NOT NULL
               AND jsonb_typeof(answers->'confidence')='number'),
pairs AS (SELECT a.user_id, a.session_no s1, a.conf c1, b.conf c2
            FROM c a JOIN c b ON b.user_id=a.user_id AND b.session_no=a.session_no+1)
SELECT count(*) FROM pairs p1 JOIN pairs p2
    ON p2.user_id=p1.user_id AND p2.s1=p1.s1+1
 WHERE p1.c2<p1.c1 AND p2.c2<p2.c1;
```

| 항목 | 값 |
|---|---|
| 응답 | 16건 · **응답자 5명** |
| 판정 가능한 연속 쌍 | 10 |
| 하강 쌍 | 4 (`1→2` 8→3 · `3→4` 8→6 · `2→3` 7→6 · `2→3` 8→7) |
| **두 회차 연속 하강** | **0건** |

**그리고 같은 §1-2 에서 `연락 요청` 을 0건이라는 이유로 강등했다.** 둘 다 발생 0건인데 하나는 올리고 하나는 내렸다. 기준이 서로를 부정한다.

**§10 이 그것을 막으려던 규율이었다** — *"쿼리 자체를 보고에 싣겠다."* 값(16)만 적어서 **그 수가 신호 조건과 무관하다는 것이 보이지 않았다.** 원인은 도구가 아니라 지표 선택이지만 실패 유형은 같다.

**규율을 좁힌다.**

> DB 실측으로 **설계를 바꿀 때**는 쿼리와 함께 **"그 수가 이 판정의 재료가 맞는가"** 를 한 줄로 적는다.

### 1-1. ⓑ 채택 — 조건을 하강 폭으로 바꾼다

```
자신감 급락 = 인접 두 회차 모두 응답 · 하강 폭 3 이상
```

**1기 실측에 1건 있다**(`1→2` 8→3, 낙폭 5). 재료가 실재한다.

그리고 이게 더 나은 신호다. **급락 한 번이 완만한 두 번보다 인도자에게 중요하다.** 8에서 3으로 떨어진 사람은 그 주에 무언가 있었던 것이고, 7에서 6으로 두 번 내린 사람보다 먼저 봐야 한다.

임계 3의 근거는 **ADR-80 이래 `3 이하는 한 걸음을 잘게 쪼개 줄 사람` 으로 써 온 척도 감각**이다. 10점 척도에서 3점 이동은 구간을 하나 건너뛴 것이다. 1기 표본이 얇아 조정 근거가 없으므로 고정한다.

**이름을 `자신감 하강` 에서 `자신감 급락` 으로 바꾼다.** 조건이 바뀌었으므로 이름도 맞춘다.

### 1-2. `연락 요청` 을 주로 되돌린다

부기가 옳다. **`contact_request` 는 참여자가 명시적으로 손을 든 유일한 신호이고 나머지는 전부 코드의 추론이다.**

0건인 것은 재료가 없는 것이 아니라 아직 아무도 요청하지 않은 것이다. **켜지는 순간 가장 확실하다.**

**빈도가 아니라 확실성으로 급을 매기는 자리다.** 내가 빈도로 정한 것이 틀렸다.

### 1-3. 신호 규칙 최종

| 신호 | 조건 | 급 | 근거 |
|---|---|---|---|
| **연락 요청** | `contact_request` | 주 | 참여자가 직접 손을 든 유일한 신호 |
| **작성 중 방치** | `drafting` 이고 `closes_at` 지남 | 주 | 1기 10건. 시작했고 막힌 사람 |
| **연속 미착수** | 열린 회차 2회 연속 `empty` | 주 | |
| **자신감 급락** | 인접 두 회차 응답 · 낙폭 3 이상 | 주 | 1기 1건 |
| 결산 악화 | `했습니다` → `잊고 지냈습니다` | 보조 | 1기 0건 |

주가 넷이다. 상한으로 둔다 — **다섯째가 생기면 급을 다시 나눈다.**

## 2. 반박② — ⓑ' 를 채택한다

호출부를 확인했다. **다섯이고 내가 하나만 셌다.**

| 호출부 | 용도 |
|---|---|
| `checkin/page.tsx:34` | 회차 현황 명단 |
| `cohort/[cohortId]/page.tsx:37` | 차수 상세 |
| **`report/[responseId]/page.tsx:44`** | **PDF 헤더 이름 조회** |
| `coach/cohorts/page.tsx:32` | 차수 목록 |
| `coach/page.tsx:56` | 코치 홈 |

**리포트 헤더가 즉시 깨진다.** `page.tsx:46` 이 `members.find(...)?.name ?? '참여자'` 이고, **`role<>'user'` 인 계정이 1기 사전 체크 응답을 1건 갖고 있다**(재측정 확인). RPC 에 필터를 넣으면 그 리포트 헤더가 `'참여자'` 로 폴백된다.

**진단이 정확하다** — 한 함수가 두 목적을 겸하고 있었다. **코칭 대상 명단**과 **`userId → name` 이름 조회**다. 내 원칙(*"명단은 코칭 대상이지 참가자 목록이 아니다"*)은 앞에는 맞고 **뒤에는 틀리다.** 이름 조회는 등록한 사람 전부를 알아야 한다.

**ⓑ' 를 채택한다.**

```sql
CREATE OR REPLACE FUNCTION public.cohort_member_directory(
  p_cohort_id uuid,
  p_only_participants boolean DEFAULT false   -- 기본값이 기존 동작 — 호출부 다섯 무변경
) …
  WHERE e.cohort_id = p_cohort_id
    AND (NOT p_only_participants OR u.role = 'user');
```

```ts
listCohortMembers(cohortId: string, onlyParticipants?: boolean): Promise<MemberRef[]>;
```

**회귀 0이고, 명단·격자만 `true` 로 부른다.** 계약 확장이 하나 더 늘지만 §3 을 이미 완화했으므로 범위 안이다.

**`checkin/page.tsx` 회차 현황도 `true` 로 부른다.** 거기서도 운영자가 참여자 행으로 뜰 이유가 없다. **의도된 변화이므로 보고에 명시하고 테스트로 잠근다** — 명단이 11 → 9.

나머지 셋(차수 상세·차수 목록·코치 홈)과 리포트 헤더는 **기본값 그대로**다.

## 3. 보완① — `AXIS_INDEX[3]=0` 유지, 주석을 고친다

3회차 `gap_area`(칩)가 `summaryFields` 어디에도 없다. `summaryFields[0]` 은 `gap_want` 다. 따라서 **인덱스 표로는 `gap_area` 를 잡을 수 없다.**

**`gap_want` 가 맞다.** 종단 축의 나머지 넷(갈망 쌍 · 한 문장 · 원씽 · 환경)이 전부 문장이고, `gap_area` 는 낱말 하나다. 3회차가 그것을 나눔 열에 안 넣은 것도 같은 이유다 — **한 낱말은 나눌 문장이 아니다.**

**대신 `index.ts:31` 주석을 고친다.**

```
갈망1 → 한 문장2 → 영역3 → 원씽4 → 환경5 → 남은 시간6 → 정체성 선언7
                    ↓
갈망1 → 한 문장2 → 바라는 것3 → 원씽4 → 환경5 → …
```

주석과 코드가 어긋난 채 두면 **다음 사람이 `gap_area` 를 축으로 되살린다.**

### 3-1. session6 지시서와의 충돌 — 조정 지정

`CC_ORDER_checkin_session6.md` §7 이 **같은 주석 한 줄**을 다른 이유로 고치라 한다(배속 정정). 그리고 클코1 검토가 **그 지시서가 파일을 `slots.ts` 로 잘못 적었다**(실제는 `index.ts:31`)고 보고했다.

**먼저 착수하는 쪽이 양쪽 정정을 함께 반영한다.**

착수 순서상 **이 작업(ADR-118)이 먼저다.** 따라서 여기서 **배속 정정까지 함께** 넣는다 — `바라는 것3` 과 6·7회차 배속을 한 번에 고친다.

**session6 지시서 §7 은 그 항목을 삭제하고, 파일 경로 오기(`slots.ts` → `index.ts`)도 함께 정정한다.** 6회차 착수 시 이 사실을 보고에 남긴다.

만약 6회차가 먼저 착수되면 반대로 하되, **양쪽이 각자 고치는 일은 없어야 한다.**

## 4. 보완②③ — 수용

**②** 자신감 응답자가 9명 중 5명이다. **화면 A 를 4명에 대해 열면 그 열이 전부 `—` 다.** 열을 지우지 않고 `—` 규칙을 유지하는 판단이 맞다. **4명에게 빈 열이 정상이라는 것**을 주석에 남긴다.

**③** 7회차는 인도자 세션이라 참여자 카드가 없다. `AXIS_INDEX` 에 더할 것은 **6회차 한 줄뿐**이다.

## 7. 이번 라운드 기록

**두 라운드에 걸쳐 내 오류가 열두 건 나왔고, 성격이 셋으로 갈린다.**

**사실 대조 누락** — 호출부를 하나만 센 것, `summaryFields` 인덱스를 안 본 것. 소스를 보면 5분이면 확인된다.

**측정 도구 오류** — `->>` + 정규식으로 `number` 를 걸러낸 것. 값이 그럴듯해 아무도 다시 재지 않는다.

**지표 선택 오류** — `16건` 을 재료로 쓴 것. **쿼리가 맞아도 그 수가 그 판정의 재료가 아닐 수 있다.** 이번에 처음 특정한 유형이고, 앞의 둘보다 잡기 어렵다. 도구도 사실도 맞는데 **연결이 틀렸기 때문**이다.

그리고 **자기 규율을 같은 문서 안에서 어긴 것이 두 번째다** — 5회차 지시서에서 검증 조건과 문안이 어긋났고, 이번에는 §10 규율이 §1-2 에서 바로 깨졌다. **규율을 문서 끝에 적으면 그 문서에는 적용되지 않는다.** 앞으로 규율은 적는 순간 그 문서를 되짚어 확인하겠다.
