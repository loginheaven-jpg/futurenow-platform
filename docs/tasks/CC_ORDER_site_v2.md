## 3. S-2 · 가치 카드 개인 응시 경로 (B′ 확장안)

### 3.1 문제

`value_assessments.cohort_id`가 `NOT NULL`이고 `UNIQUE(user_id, cohort_id)`다.
차수 미소속 회원(§4의 개인 회원)은 응시할 수 없다. 개인 회원의 존재 이유가 상시 진단이므로
회원 모델 자체가 성립하지 않는다.

### 3.2 방침 — 되돌리지 않고 연다

**완주된 슬라이스(V-3~V-13)는 한 줄도 버리지 않는다.** 기존 차수 경로는 그대로 살린다.

| 대상 | 변경 |
|---|---|
| 마이그레이션 | **새 파일**(불변식 15). `cohort_id` DROP NOT NULL. 기존 `UNIQUE(user_id, cohort_id)` 제약을 **부분 유니크 인덱스 둘**로 교체 — 차수분 `(user_id, cohort_id) WHERE cohort_id IS NOT NULL` · 개인분 `(user_id) WHERE cohort_id IS NULL` |
| DEFINER RPC | `cohort_id` 인자 nullable 수용. **NULL이면 차수 소속 검증을 건너뛰고, NOT NULL이면 기존 검증 그대로.** 이동·삭제(`move_cohort_member`) 충돌 제거 절이 개인 행(NULL)을 건드리지 않는지 확인 |
| 계약 | `cohortId: string \| null`. 계약 파일 변경은 §1로 승인됨 |
| 라우트 | `/my/values` 신설. `/my/cohorts/[id]/values` **유지** |
| 화면 | **컴포넌트 공유.** 라우트 파일 둘이 `cohortId` 해석만 달리한다. 화면 코드를 복제하지 않는다 |
| `safeReturn.ts` | `/^\/my\/values$/` 추가 |

### 3.3 판정 규칙 (§4와 맞물림)

- **응시 시점의 소속을 행에 새긴다.** 차수 회원이 응시하면 `cohort_id`가 박히고, 개인 자격
  응시는 NULL이다. 나중에 소속이 바뀌어도 **기존 행의 `cohort_id`를 갱신하지 않는다.**
- `/my/cohorts/[id]/values`는 그 차수 소속일 때만 연다(기존 게이트 유지).
- `/my/values`는 **진단 응시 자격**(§4.4)이 있을 때만 연다.
- 인도자 열람은 `cohort_id`가 자기 기수인 행에 한정한다. NULL 행은 인도자에게 보이지 않는다.

### 3.4 하지 않을 것

- 기존 차수 경로 제거 금지
- `cards.ts`·`ordering.ts`·`stages.ts` 변경 금지 (미결 N-1·P1은 이 발주 범위 밖)
- 카테고리를 참여자 렌더 타입에 넣지 않는다(불변식 8)

## 4. S-1 · 회원 상태와 승인

### 4.1 상태 다섯

| 상태 | 진단 응시 | 기존 결과 열람 | 전이 계기 |
|---|---|---|---|
| `pending` 승인 대기 | ✕ | — | `/signup` 직후 |
| `individual` 개인 회원 | 상시만 | ○ | 운영자 승인 |
| `cohort` 차수 회원 | 여정 + 상시 | ○ | 코드 가입 · 기수 배정 |
| `expired` 만료 | ✕ | ○ | 유효기간 종료 |
| `held` 보류 | ✕ | — | 운영자 판단 |

**승인 여부가 가르는 것은 진단 응시 하나다.** 소식·공개 자료실·계정은 상태와 무관하다.

### 4.2 역할과 상태를 섞지 않는다

`role`(`user`·`coach`·`admin`)은 그대로 둔다. 상태는 **별도 축**이다.
기존 자가승격 방지(`20260629100002`)의 보호 범위를 흔들지 않는다.
상태 변경 RPC도 **자기 자신에게는 걸리지 않아야 한다**(운영자가 자기 상태를 바꾸지 못한다).

차수 회원 여부는 `enrollments`가 이미 알고 있다. **상태 컬럼에 차수 소속을 이중 기록하지
않는다** — 진실이 두 곳에 있으면 반드시 어긋난다. `cohort` 상태는 저장값이 아니라
**판정 함수의 산출**로 둘지, 저장할지 설계 판단 후 보고한다. 지휘부는 판정 산출을 선호한다.

### 4.3 승인 대조 키 — 이 발주의 급소

운영자 화면에 이름과 이메일뿐이면 승인은 추측이 된다. **`/signup` 폼에서 받는다.**

| 필드 | 필수 | 비고 |
|---|---|---|
| 포럼 가입 시 사용한 이름 | **필수** | 계정 이름과 다를 수 있다 |
| 포럼 가입 연락처 | **필수** | 불변식 13 — `user_contacts` 격리 · `getPhone` 게이트 경유 |
| 가입 경위 | 선택 | 한 줄 |

**연락처 표시는 마스킹을 기본으로 한다**(`010-****-1234`). 전체 노출은 게이트를 지난다.

이 필드가 없으면 승인 큐는 며칠 만에 판단 불가로 쌓이고, 나중에 필드를 추가해도
**이미 들어온 신청 건은 영원히 대조할 수 없다.**

### 4.4 판정은 한 함수로

진단 응시 가능 여부는 **단일 순수 판정 함수 + 서버 강제** 두 겹이다.

- 화면에서 버튼을 감추는 것은 안전장치가 아니다. **응시 시작 RPC에서 막는다.**
- 게이트 검증은 HTTP 200이 아니라 **본문 민감 콘텐츠 0 + 리다이렉트 목적지**로 판정한다(불변식 19).

### 4.5 승인 화면 (`/admin` 하위)

- 대기 목록: 신청자 · 계정 이메일 · **포럼 이름·연락처(마스킹)** · 가입 경위 · 신청일 · 승인/보류
- 승인 시 함께 정한다: **유효기간**(기본값은 §12-2 확정 후) · 근거 메모. 부여자·부여일은 자동
- **만료 임박 목록**(30일 이내)을 같은 화면에. 사람이 매번 달력을 보지 않는다
- 보류는 사유를 내부 메모로만 남긴다. 사용자에게는 확인 필요 안내와 문의처만

### 4.6 `/pending` 대기 화면

빈 화면은 고장으로 읽힌다. **네 가지를 문장으로 말한다** — 지금 어느 단계인가, 무엇을
기다리는가, 대개 얼마나 걸리는가, 어디로 문의하는가. 아래에 지금도 할 수 있는 것
(소식 · 공개 자료실 · 세미나 신청)을 둔다.

**딥링크가 여기로 떨어져도 오류를 띄우지 않는다.** 대기자가 진단 경로에 닿으면 이 안내로
받고, 승인 후 원래 자리로 돌아간다(returnTo 보존).

### 4.7 승인 통지

승인 시 안내 메일 1통. 없으면 사람이 다시 오지 않는다.
발송 수단은 저장소 현황을 확인하고 **가장 적은 것을 새로 들이는 쪽**으로 정해 보고한다.

## 5. S-3 · 진단 허브 `/home/assessments`

### 5.1 왜 `/home` 아래인가

`/assessments`로 최상위에 두면 `PROTECTED_PREFIXES`에 항목이 하나 늘고 커버리지를 다시
증명해야 한다. 기존 접두사 안이면 자동으로 따라온다. **불변식 17을 건드리지 않는 배치다.**

### 5.2 두 계열

| 계열 | 항목 | 1차 처리 |
|---|---|---|
| 여정 | 사전진단 | 기존 경로 연결 |
| | 사후진단 | **자리만.** "6회차를 마친 뒤 열립니다" |
| 상시 | 가치 카드 | `/my/values` 또는 차수 경로로 분기 |
| | **그림자(SAIL)** | **연결만.** §5.3 |
| | 사랑의 언어 | **자리만.** 미착수 표기 |

### 5.3 그림자 = SAIL — 손대지 않는다

`shadow` 스키마 10개 테이블은 **클코3 소관**이다(CLAUDE §4).
**허브에 항목을 세우고 링크만 건다. 스키마·데이터·코드를 건드리지 않는다.**
연결 방식(외부 링크 / 동일 도메인 경로)은 현황 확인 후 보고한다.

### 5.4 고지 문안

차수 회원이 상시 진단을 시작할 때 한 줄을 보인다.

> **이 결과는 우리 기수 인도자와 함께 봅니다.**

개인 회원에게는 대신 **이 결과는 나만 봅니다.** 를 보인다.
허락을 구하는 문장이 아니라 알려 주는 문장이다. 동의 토글을 두지 않는다.

## 7. S-5 · PC 대응과 UI 제한

### 7.1 세 수준

| 영역 | 수준 |
|---|---|
| 공개 영역 | **PC 전용 레이아웃** |
| 인도자·운영자 콘솔 | **PC 우선** — 사이드바 + 넓은 표 |
| 참여자 화면 | **중앙 정렬 반응형** — 읽기 좋은 최대 폭 유지. 재설계하지 않는다 |

세 번째가 일정의 안전판이다. 참여자 화면을 PC 전용으로 다시 짜지 않는다.

### 7.2 UI 제한 — 중요

**design_system v4가 아직 오지 않았다.** 불변식 20에 따라 임의 디자인을 하지 않는다.

- 기존 토큰·공용 컴포넌트(`Button`·`Card`·`ListRow`·`AppHeader` 등)로 **조립 가능한 범위까지만** 만든다
- 새 색·새 문안 규칙·새 시각 언어를 만들지 않는다
- `AppHeader` `variant`는 기존 3종을 쓴다 — 공개 영역 `root` · 진단 응답 `flow` · 상세 `sub`
- 부품이 없어 막히는 지점은 **목록으로 보고한다.** 지휘부가 v4에 반영한다
- 지휘부가 이미 인지한 부재: 단일행 입력 · 카드 그리드 · 쌍대비교 2열 · 승인 큐 표 · 상태 배지 · PC 브레이크포인트

### 7.3 참여자 화면 금지 사항 (재확인)

경고색 · 순위 · 막대 · 게이지 · 백분위 · 평균 · 정렬키를 참여자 경로에 두지 않는다
(불변식 9·11). 상태 배지도 참여자에게 보이지 않는다.

## 8. 함께 처리 — ADR-120 대기 질의

`LoginClient` 예외 문구를 확정한다. **경로를 가른다.**

| 경로 | 문구 |
|---|---|
| 자격 증명 실패 | `이메일 또는 비밀번호를 확인해 주세요` *(기존 유지)* |
| 예외(네트워크·서버) | **`연결이 되지 않았습니다. 잠시 뒤 다시 로그인해 주세요.`** |

원인을 사용자 잘못으로 돌리지 않는 것이 이 문구의 핵심이다. 동사는 버튼 이름과 같다.

검증 수치는 기준 커밋과 짝일 때만 의미가 있다. 지우면 왜 어긋났는지가 사라진다(ADR-94의 정신).

**딥링크 검증 표** — 아래 조합을 전부 돌리고 결과를 표로 낸다.

| 진입 | 상태 | 기대 |
|---|---|---|
| `/my/values` | 미인증 | `/login?returnTo=/my/values` → 인증 후 `/my/values` |
| `/my/values` | 승인 대기 | `/pending`(오류 아님) → 승인 후 원래 자리 |
| `/my/values` | 개인 회원 | 정상 진입 |
| `/my/values` | 만료 | 응시 차단 · 기존 결과 열람 가능 |

**실브라우저 검증**(`fetch 200 ≠ browser normal`) — Vercel 프리뷰 URL에서 확인한다.
게이트는 **본문 민감 콘텐츠 0 + 리다이렉트 목적지**로 판정한다(불변식 19).
포트에 남은 이전 빌드 좀비 프로세스를 먼저 정리한다(ADR-120에서 위양성 실사례).

## 11. 하지 말 것 (요약)

1. `main`에 커밋하지 않는다. 브랜치는 `refactor/site-v2`
2. **SAIL(`shadow` 스키마)을 건드리지 않는다.** 클코3 소관
3. 적용된 마이그레이션 파일을 수정하지 않는다. 변경은 항상 새 파일
4. `PROXY_MATCHER`를 좁히지 않는다
5. 기존 경로를 옮기거나 지우지 않는다. 이번 발주에 301 대상은 없다
6. design_system v4 없이 새 시각 언어를 만들지 않는다
7. `cards.ts`·`ordering.ts`·`stages.ts` 변경 금지(미결 N-1·P1은 범위 밖)
8. 역할과 회원 상태를 한 컬럼에 섞지 않는다
9. 차수 소속을 상태 컬럼에 이중 기록하지 않는다
10. 참여자 화면에 상태 배지·경고색·순위를 두지 않는다

## 12. 미확정 — 막히면 질의한다

이 넷은 아직 정해지지 않았다. 필요해지면 **작업을 멈추고 질의**한다. 임의로 정하지 않는다.

1. `/recruit`과 `/join`의 연결 관계 — 소개·자료실에서 어느 쪽으로 보낼지
2. 개인 회원 자격 기본 유효기간
3. 수료자 상태 전이 — 지휘부 권고는 **승인 없이 개인 회원 자동 전이 + 유효기간**
4. 승인 처리 목표 시간 — `/pending` 문구가 달라진다
5. 이용약관·개인정보처리방침과 기존 `user_consents`·`privacy_consents`의 관계
