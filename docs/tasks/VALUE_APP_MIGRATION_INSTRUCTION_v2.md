## 2. 핵심 재설계 — 2단계 사용 구조

검토 R-4가 지적한 모순("사전 과제인데 워크북 대조를 묻는다")은 사용 시점을 하나로 잡았기 때문에 생겼다. 이 앱이 하는 일은 실제로 성격이 다른 두 가지다.

| 작업 | 맥락 필요 | 적정 시점 |
|---|---|---|
| 72장을 훑어 후보를 넓게 잡는다 | 불필요 | 1회차 이전 (집) |
| 후보를 3개로 좁힌다 | **필수** | 1회차 진행 중 |

앞의 것은 **선정이 아니라 노출**이다. 가치 어휘를 마음에 심어 두는 것이 목적이므로 맥락이 없어도 손해가 없다. 뒤의 것은 라이프 커브·패턴 찾기·재해석을 거친 뒤라야 "삶이 실제로 증명한 것"과 대조할 수 있다.

### 2-1. 두 세션의 정의

```
[1차 · 1회차 이전, 집에서 10~15분]
  안내 → 카드 5화면(72장) → 정리 화면 → 8~12개로 좁히기 → 저장하고 종료
  결과물 : 후보 8~12개

[2차 · 1회차 진행 중, 7~8분]
  이어하기 → 저장된 후보 표시 → 정확히 5개 → 쌍대비교 10회 → 최종 3개
  → 내 말로 바꾸기 → 대조·정합 판정 → 결과
  결과물 : 핵심가치 3개 + 라벨 + 정합 판정
```

2차 진입 시 첫 화면에서 1차 결과를 그대로 보여준다. 참여자가 **자기 선택의 변화를 목격하는 것**이 이 구조의 핵심 효과다. 지난주에 그냥 끌려서 고른 것과, 오늘 삶이 증명한 것이 같은지 다른지를 스스로 본다.

### 2-2. 이것이 R-4를 해소하는 방식

§6 대조 화면은 **2차에서만** 나타난다. 2차는 1회차 진행 중이므로 참여자는 이미 존재감 봉우리·강점·갈망을 손에 쥐고 있다. 건너뛰기율 100%가 될 이유가 없다.

### 2-3. 구현 요구

| 요구 | 내용 |
|---|---|
| 세션 상태 | `stage` 컬럼으로 진행 지점 저장 (`candidates` / `final`) |
| 이어하기 | 1차 완료자가 재진입 시 2차 첫 화면으로 자동 이동 |
| 1차 미완료자 | 2차 시점에 들어오면 1차부터 진행. 단 카드 5화면을 3화면으로 압축한 단축 경로 제공 (현장 시간 대응) |
| 되돌아가기 | 2차에서 1차 후보를 수정할 수 있게 한다. 단 최종 3개 확정 후에는 잠근다 |

## 3. 데이터 설계

### 3-0. Q3 판정 근거

검토 S-7이 제시한 `responses` 재사용 대안은 매력적이나 채택하지 않는다. 세 가지 이유다.

첫째, `responses`는 불변 제출 기록이다. 본 앱은 §2-3대로 **중간 상태를 저장하고 갱신**해야 하므로 성격이 다르다.
둘째, 중간저장 `response_drafts`의 PK가 `(user_id, cohort_id, wave)`로 `instrument_id`를 포함하지 않아 사전진단 작성본과 충돌한다(검토 S-7이 자인).
셋째, 가치 결과는 `stage`·`alignment`·라벨 등 진단 응답과 다른 구조의 컬럼을 요구한다. JSONB에 밀어넣으면 조회·집계가 불편하다.

다만 **`instrument_id` 컬럼은 유지**하여 ADR-14의 진단 간 격리 규약을 따른다.

### 3-1. 테이블

```sql
-- supabase/migrations/[timestamp]_value_assessments.sql

create table public.value_assessments (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.users(id) on delete cascade,
  cohort_id uuid not null references public.cohorts(id) on delete cascade,
  instrument_id text not null default 'futurenow_values',
  card_set_version text not null default 'v1',
  client_request_id text not null,

  -- 진행 상태
  stage text not null default 'candidates'
    check (stage in ('candidates','final')),

  -- 1차 결과 : 후보 8~12개
  candidates jsonb,

  -- 2차 결과 : 최종 3개
  value1 text, value2 text, value3 text,
  value1_label text, value2_label text, value3_label text,

  -- 대조
  wb_peak text, wb_strength text, wb_longing text,
  alignment text check (alignment in ('aligned','different','unsure')),

  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  unique (user_id, cohort_id, instrument_id),
  unique (client_request_id)
);

create index value_assessments_cohort_idx on public.value_assessments (cohort_id);
create index value_assessments_user_idx on public.value_assessments (user_id);
```

`name`·`email`·`custom_value`·`lookup_code` 컬럼은 없다. 순서대로 R-1(계정에 있음), S-4(§7로 일원화), R-8(로그인이므로 불필요)에 따른다.

`unique (user_id, cohort_id, instrument_id)`로 1인 1행을 강제하고, 1차·2차가 같은 행을 갱신한다.

### 3-2. RLS

```sql
alter table public.value_assessments enable row level security;

grant select, insert, update on public.value_assessments to authenticated;
revoke all on public.value_assessments from anon;

-- 본인 삽입
create policy value_assessments_insert_own
  on public.value_assessments for insert to authenticated
  with check (user_id = auth.uid());

-- 본인 갱신 (증분 저장)
create policy value_assessments_update_own
  on public.value_assessments for update to authenticated
  using (user_id = auth.uid())
  with check (user_id = auth.uid());

-- 본인 또는 같은 차수 코치 또는 운영자
create policy value_assessments_select
  on public.value_assessments for select to authenticated
  using (
    user_id = auth.uid()
    or public.is_cohort_coach(cohort_id, auth.uid())
    or public.is_admin(auth.uid())
  );
```

정책이 테이블을 직접 참조하지 않는다. 기존 DEFINER 헬퍼만 쓴다(`CLAUDE.md` §5, `architecture.md` §6.1). 기존 `responses_select` 정책을 본으로 삼는다.

DELETE 정책은 두지 않는다. 참여자 탈퇴 시 `on delete cascade`로 처리된다.

### 3-3. 트리거

`updated_at` 자동 갱신 트리거를 단다. 저장소 기존 패턴을 따른다.

## 4. 화면 흐름

### 4-1. 카드 노출 — R-7 조건부 수용

검토 R-7의 지적을 수용한다. 카테고리 주제어를 화면 제목으로 쓰면 "이 영역에서 무엇을 중시해야 하는가"라는 사회적 프레임이 생기고, 화면당 균등 배분 행동이 작은 카테고리를 과대 대표시킨다. 원본이 카드를 섞어 둔 것은 설계였다.

**채택안**

1. 72장을 카테고리가 고르게 섞이도록 **고정 배열**한다. 참여자별 셔플이 아니다(재개·비교 가능성 유지). `core/response/ordering.ts`의 제약 셔플 선례를 따른다.
2. 15/15/14/14/14로 잘라 5화면. **화면 제목은 주제어 없이 진행 표시만**(`1 / 5`).
3. 탐색 중에는 **상한을 걸지 않는다.** 끌리면 다 고른다.
4. 5화면 이후 **정리 화면 한 장.** 고른 전부를 한눈에 놓고 줄인다. 여기서 처음 개수를 말한다.

**단서** — 검토가 지적하지 않은 문제가 하나 있다. 카테고리를 완전히 지우면 참여자가 "비슷한 단어가 왜 이렇게 많지"라고 느낄 수 있다(관계 14장이 흩어져 나오므로). 대응으로 **카드 상세(탭하면 펼쳐지는 한 줄 설명)를 반드시 유지**한다. 원본 `description` 필드가 그 역할을 한다. 설명 없이 단어만 노출하면 유사어 혼동이 커진다.

### 4-2. 선택 개수 — S-1 수용

하한은 하드, 상한은 소프트로 한다.

| 화면 | 하한(진행 차단) | 상한 |
|---|---|---|
| 카드 5화면 | 없음 | **없음** |
| 정리 화면 | 12 (다음 단계 상한 이상) | 없음 — 안내만 |
| 후보 좁히기 | 8 | 12 초과 시 안내만 |
| 5개 고르기 | 5 고정 | 5 고정 (쌍대비교 전제) |
| 최종 | 3 고정 | 3 고정 |

### 4-3. 진행 표시

`STEP_CONFIGS` 배열을 그대로 쓰지 않는다. 검토 S-2의 6번 지적대로 원본은 단계 설정과 실제 라우팅이 어긋나 있다. 진행 표시는 **본 지시서의 2단계 구조**를 기준으로 새로 정의한다.

## 5. 참여자 문안

검토 R-6을 전면 수용한다. **원본 문안은 하나도 그대로 쓰지 않는다.** `futurenow_copy_principles.md`가 최상위 규범이며 회귀 테스트로 잠겨 있다.

### 5-1. 준수 사항

| 금지 | 대체 |
|---|---|
| '워크북' | '1회차에 쓰신 것', '지난 시간에 찾으신 것' |
| '진단' | '가치 카드' |
| '충분합니다', '괜찮습니다', '~하셔도 됩니다' | 축 1에 따라 허락 어휘 제거 |
| '선택 사항입니다' | 값을 말하는 문안으로 대체 (축 2) |
| 책 페이지 본문 삽입 | 문장 끝 괄호로만 — "(책 53~58쪽)" |

### 5-2. 단계 문구 정본

Q5 회신 전까지 아래 문자열을 정본으로 한다. 워크북 확정본 전달 후 대조하여 최종 확정한다.

| 화면 | 문구 |
|---|---|
| 카드 5화면 | "마음이 더 끌리는 카드를 골라 주십시오. '이게 중요한 게 맞지' 하는 생각은 내려놓으십시오." |
| 정리 화면 | "고르신 카드를 한눈에 놓았습니다. 여기서 15~25장으로 줄여 주십시오." |
| 후보 좁히기 | "이것이 없으면 내 존재가 희미해진다 싶은 것을 8~12장 골라 주십시오." |
| 5개 고르기 | "다른 것을 희생해서라도 끝까지 지키고 싶은 5장을 골라 주십시오." |
| 쌍대비교 | "둘 중 하나만 남긴다면 어느 쪽입니까?" |
| 최종 3개 | "당신의 삶을 이끄는 세 가지를 골라 주십시오." |

'5개 고르기' 문구는 워크북 활동 5의 **우위 기준** 정의와 같은 문장이다. 참여자가 1회차에서 같은 표현을 다시 만나 연결을 인식하게 하는 장치이므로 임의 변경하지 않는다.

### 5-3. 축 2 적용 — 값을 말한다

허락을 지운 자리에 이 칸이 어디로 이어지는지를 넣는다. 검토 R-6이 제안한 문장을 채택한다.

> 여기 적으신 문장이 1회차에 쓰실 존재가치 선언문의 첫 칸이 됩니다.

`identity_sentence` 칸이 실재하므로 축 2의 제약("제품이 지금 이행할 수 있는 것만 말한다")을 통과한다.

## 6. 대조 화면 (2차 전용)

### 6-1. 입력

```
지난 시간에 찾으신 것을 여기 옮겨 주십시오. 한 단어로 적으십시오.

  존재감이 가장 높았던 순간    [                    ]
  그때 드러난 나의 강점        [                    ]
  상처 뒤에서 찾은 나의 갈망    [                    ]

  [ 다음 ]            [ 아직 못 찾았습니다 — 건너뛰기 ]
```

- 세 입력 모두 비워도 진행된다. **다만 "선택 사항입니다" 같은 허락 문구를 쓰지 않는다.**
- 건너뛰기 버튼은 '다음'과 **동등한 시각적 비중.** 검토 R-6이 확인한 대로 이는 원칙 §3의 결측 안내 예외 자리와 같은 사고다.
- `maxLength=20`, 한 줄 input만. textarea 금지.

### 6-2. 정합 판정

```
지난 시간에 찾으신 것    봉우리: ○○ · 강점: ○○ · 갈망: ○○
가치 카드에서 찾은 것    ○○ · ○○ · ○○

이 둘이 같은 곳을 가리킵니까?
[ 같습니다 ]  [ 다릅니다 ]  [ 아직 모르겠습니다 ]
```

**판정은 사용자가 한다.** 문자열 유사도 등 자동 판정을 넣지 않는다.

| 선택 | 응답 문안 |
|---|---|
| 같습니다 | "서로 다른 길로 찾았는데 같은 곳을 가리켰습니다. 그것이 진짜라는 뜻입니다." |
| 다릅니다 | "어긋남은 이 작업의 재료입니다. 머리로 고른 가치와 삶이 증명한 가치가 다르다는 뜻이니, 어느 쪽이 진짜인지 1회차에서 한 번 더 보십시오." |
| 아직 모르겠습니다 | "지금 결론 내지 않습니다. 세미나에서 함께 봅니다." |

### 6-3. 운영 지표 — R-4 후단 수용

검토가 지적한 자기모순을 해소한다. **`alignment='different'`를 결함 지표로 쓰지 않는다.** 어긋남은 워크의 재료다. 운영 지표로는 **건너뛰기율**과 **단계별 이탈률**을 쓴다.

## 8. `identity_sentence` 연결 (Q7)

1회차 갈무리(`session1.ts:53`)의 `identity_sentence` 필드에 **프리필 힌트**를 제공한다.

- 가치 앱 2차를 완료한 참여자가 1회차 갈무리에 들어오면, `identity_sentence` 입력란 위에 본인이 적은 라벨 3개를 표시한다.
- **자동 입력하지 않는다.** 참여자가 보고 직접 쓴다. 선언문은 손으로 쓸 때 새겨진다.

배선은 인스트루먼트 내부에서 처리한다. 코어를 경유하지 않는다.

## 9. 코드 배치 — R-5 수용

```
src/instruments/futurenow/values/
  cards.ts        ← values.json → TS 상수 (fetch 제거)
  ordering.ts     ← 고정 배열 정의 (§4-1)
  stages.ts       ← 2단계 구조·개수 규칙
  copy.ts         ← 참여자 문안 (회귀 테스트 잠금 대상)
  reflection.ts   ← 성찰 질문
  pairwise.ts     ← 쌍대비교 순수 로직 (단위테스트 필수)

src/app/my/cohorts/[cohortId]/values/
  page.tsx        ← 라우트
  actions.ts      ← 서버 액션 (Route Handler 아님, S-6)
```

`/my`는 `proxy.guard.ts`의 `PROTECTED_PREFIXES`에 이미 있어 미인증 차단이 자동으로 걸린다.

UI는 `core/ui` 컴포넌트와 `design_system.md` 토큰으로 **새로 짠다**(S-5). 원본 스택(wouter·tRPC·shadcn·sonner·lucide)은 이 플랫폼에 없으므로 컴포넌트 이식은 불가능하다. 셸은 `AppHeader variant='flow'`를 쓴다.

## 11. 재반박 2건

### 11-1. R-7 카테고리 — 수용하되 근거는 다르다

검토는 카테고리 노출이 "사회적 프레임을 만든다"고 했다. 이 지적은 옳으나, **더 결정적인 이유는 예산 배분 문제**다(R-7 ③). 5화면에 총량 15~25를 나눠 쓰게 하면서 뒤 화면을 미리 보여주지 않으면, 앞 화면에서 많이 고른 참여자가 뒤에서 막힌다. 이는 §4가 없애려던 압박을 형태만 바꿔 되살린다.

따라서 **"카테고리를 버린다"보다 "탐색 중 상한을 걸지 않는다"가 핵심 처방**이다. 상한이 없으면 카테고리로 나눠도 예산 문제가 없다. 다만 사회적 프레임 문제가 남으므로 결과적으로 검토안(주제어 없는 분할 + 정리 화면)을 채택한다. 근거의 우선순위를 바로잡아 둔다.

### 11-2. S-3 성찰 질문 — 전면 정비는 하지 않는다

검토는 72장 중 32장에 질문이 없으므로 "1개만 교체가 아니라 전면 정비"라고 했다. 실측은 맞으나 결론에 동의하지 않는다.

**최종 3개에만 성찰 질문이 붙는다.** 그리고 이 앱의 결과는 1회차 현장에서 인도자와 함께 다뤄진다. 앱이 모든 가치에 대해 완결된 성찰 질문을 갖출 필요가 없다.

**조치**: 질문 없는 32장에는 **가치 공통 질문 3개**를 기본값으로 둔다. 카드별 전용 질문 49개는 문안 규범에 맞춰 재작성하되, 없는 32장을 새로 채우는 작업은 **후순위(V-9 이후 별도 슬라이스)**로 미룬다.

공통 질문 초안:
- "이 가치가 가장 선명하게 드러났던 순간은 언제였습니까?"
- "이 가치를 지키느라 포기한 것이 있습니까?"
- "이 가치가 무너졌을 때 어떤 기분이었습니까?"

## 13. 주의사항

- **`web_fetch` 200은 판정 기준이 아니다.** 각 화면은 본문 콘텐츠 확인과 리다이렉트 목적지 확인으로 검증한다(`CLAUDE.md` §9). V-1 검증란도 이에 맞춰 적었다.
- **`proxy.ts`의 matcher는 신원 헤더 위조 strip 보장이지 인증 게이트가 아니다.** 게이트는 `PROTECTED_PREFIXES`가 정한다. v1이 이 둘을 혼동했으므로 바로잡는다.
- **가치 카드 72장 문구는 임의 수정하지 않는다.** `VALUES_REVIEW.md` 검토 이력을 존중한다. 변경 필요 시 지휘부에 보고 후 결정한다.
- **문서 정합은 완료판정 게이트다.** 코드만 푸시하고 `architecture.md`·ADR을 미룬 상태는 작업 미완으로 간주한다. ADR 번호는 **108**부터.
- **착수 전 검토 보고서**를 `docs/reports/`에 올린다. 본 지시서에 대한 재검토 의견이 있으면 그 자리에 적는다.
