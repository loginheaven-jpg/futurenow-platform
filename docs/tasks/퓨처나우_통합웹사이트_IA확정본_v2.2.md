## 0. v1.x에서 폐기한 것 — 기록으로 남긴다

잘못된 설계가 왜 나왔는지 지우면, 다음에 같은 자리에서 또 넘어진다.

| 폐기 | 이유 |
|---|---|
| `/s/[n]` 갈무리 딥링크 신설 | **이미 있다.** `/c/[code]/[session]`(ADR-89)이 같은 일을 한다 |
| `/a/[slug]` 진단 계열 신설 | 기존 체계(`/my/cohorts/[id]/…`)와 원장이 둘이 된다 |
| `/precheck` 별칭 | 위와 같음 |
| "정문이 없다"는 전제 | `/`가 이미 공개 현관이고 `/home`이 통합 홈(ADR-51) |
| 상시 진단 결과 기본 비공개 | 지휘부 판단으로 차수 소속 기준으로 확정(§4.2) |
| 결제 연동 · 유료화 단계 | 수납은 촉진자포럼에서. 플랫폼은 자격 반영만(§5) |
| 그림자 진단 **흡수통합** | SAIL은 운영 중이며 **클코3 소관**. 통합이 아니라 연결(§4.5) |
| 1차-A / 1차-B 분할 | 골격(라우트 그룹·인증 경계·returnTo)이 이미 서 있어 분할 실익 없음 |

교훈 하나 — **저장소를 먼저 읽고 기획한다.** 이번 개정의 비용 대부분이 이 순서를 뒤집은 데서 나왔다.

## 1. 설계철학 — 다섯 원칙

### 원칙 1 · 정문과 옆문은 병행한다 (딥링크)

모든 도착점은 고유 URL을 가지며, 사용자는 두 길로 온다.

| 길 | 경로 | 용도 |
|---|---|---|
| 정문 | 홈 → 역할 카드 → 원클릭 | 스스로 찾아올 때 |
| 옆문 | 공유된 링크 → 바로 도착 | 카톡·QR로 받은 링크를 누를 때 |

옆문이 운영 동선의 척추다. 인도자가 "오늘 갈무리 → `/c/ZR4KB/3`" 한 줄을 보내면
참여자는 메뉴를 탐색하지 않는다. **이 구조는 이미 구현되어 있다**(ADR-89 · `safeReturnTo`).
1차가 하는 일은 신설이 아니라 **확장**이다 — 진단·자료실로 같은 패턴을 넓힌다.

### 원칙 2 · 로그인 벽은 길을 끊지 않는다

`/c/{code}/{n}` 진입 → 미인증 → `/login?returnTo=…` → 인증 → 원래 자리.
`safeReturnTo` 화이트리스트가 오픈 리다이렉트를 막는다(ADR-81).

**1차에서 화이트리스트에 추가할 것** — `/my/values`(개인 진단). 추가 시 짝을 맞춘다:
한쪽 형태만 넣으면 나중에 반드시 어긋난다(기존 주석의 원칙 그대로).

### 원칙 3 · 홈은 거치되, 한 번의 탭으로 벗어난다

`/`는 비로그인 현관, `/home`은 로그인 통합 홈이다. 통합 홈 최상단에 **역할 카드 하나**를
크게 둔다 — 참여자는 차수 홈으로, 인도자는 콘솔로, 운영자는 본부로. 탭 한 번을 넘지 않는다.

### 원칙 4 · 참여자 화면은 판정하지 않는다

기존 불변식 9·10·11의 재확인이다. 경고색·순위·막대·백분위·평균을 참여자 경로에 두지 않는다.
통합 사이트가 되어도 이 선은 이동하지 않는다.

### 원칙 5 · 기록으로 이긴다

카톡을 알림으로 이기려 하지 않는다. 플랫폼의 존재 이유는 남는 기록이다 —
6주의 갈무리, 매일의 걸음, 사전에서 사후로 이어지는 궤적.
모든 화면 판단의 기준은 "6주 뒤 참여자 손에 무엇이 남는가"다.

## 2. URL 원장 — 기존 체계 기준

한 번 공개된 경로는 바꾸지 않는다. 바꿔야 하면 301을 남긴다.

### 2.1 현행 (실측 · 유지)

**공개**

| 경로 | 화면 |
|---|---|
| `/` | 공개 현관(소개) |
| `/login` `/signup` `/reset` `/reset/confirm` | 인증 |
| `/join` | 가입 러너(코드 입력 → 미리보기 → 인증 → 프로필 → 완료) |
| `/recruit` | 모집 랜딩 (ISR 300s · ADR-106·110) |
| `/c/[code]/[session]` | 갈무리 QR 진입 (ADR-89) |
| `/c/[code]/values` | 가치 카드 QR 진입 (ADR-121) |

**보호** — `PROTECTED_PREFIXES = ['/home','/my','/coach','/admin','/account','/preview']`

| 경로 | 화면 |
|---|---|
| `/home` | 통합 홈 (ADR-51) |
| `/my/cohorts` · `/my/cohorts/[id]` | 차수 목록·차수 홈 |
| `/my/cohorts/[id]/checkin/[session]` | 회차 갈무리 |
| `/my/cohorts/[id]/journey` | 참여자 세로 (ADR-118) |
| `/my/cohorts/[id]/report` | 갈망 거울 (ADR-30) |
| `/my/cohorts/[id]/values` | 가치 카드 (ADR-121) |
| `/coach/…` (9) · `/admin` · `/account` · `/preview/…` (4) | 콘솔 계열 |

### 2.2 신설 (1차)

| 경로 | 화면 | 비고 |
|---|---|---|
| `/about` | 퓨처나우 소개 상세 | `SeminarIntro` 단일 출처를 확장 재사용 |
| `/library` | 자료실 | 3단 권한(§6) |
| `/contact` | 문의 | **DB 적재 + 운영자 열람**(v2.2 정정 — SMTP 부재. `contact_messages`) |
| `/news` | 소식 | 운영자 게시 |
| `/home/assessments` | **진단 허브** | 여정·상시 두 계열 목록(§4) |
| `/my/values` | 개인 가치 카드 | 차수 미소속 응시(§4.3) |
| `/pending` | 승인 대기 안내 | 대기·보류 계정 착지(§5.6). **보호 접두사에 넣지 않는다** — 대기자는 이미 인증된 사용자이므로 페이지에서 세션 확인 |
| `/admin/approvals` | 가입 승인 큐 | 시안 P4. `/admin` 접두사 안이라 matcher 무영향 |

**진단 허브를 `/home` 아래 둔다.** `/assessments`로 최상위에 두면 보호 접두사가 하나 늘고
`PROTECTED_PREFIXES`를 건드려야 한다. 기존 접두사 안에 들어가면 커버리지가 자동으로 따라온다.
불변식 17(matcher를 좁히지 말 것)의 취지에 맞는 배치다.

### 2.3 리다이렉트

신설 경로뿐이므로 **301 대상 없음.** 기존 경로는 한 줄도 옮기지 않는다.

## 3. 정보 구조

```
퓨처나우
├─ [공개] /            현관 — 소개 요약 · 모집 배너 · 소식 · 로그인
│   ├─ /about          소개 상세
│   ├─ /recruit        모집 랜딩
│   ├─ /join           가입 러너 (코드)
│   ├─ /signup         일반 가입 → 승인 대기
│   ├─ /library        자료실 (공개분)
│   ├─ /news  /contact
│
├─ [로그인] /home      통합 홈 — 역할 카드 · 바로가기 · 소식
│   ├─ /home/assessments      진단 허브
│   │   ├─ 여정: 사전 · 사후
│   │   └─ 상시: 가치 · 그림자(SAIL 연결) · 사랑의 언어(미착수)
│   ├─ /my/cohorts/[id]/…     차수 여정 (갈무리·되비추기·리포트·가치)
│   ├─ /my/values             개인 가치 카드
│   └─ /library               자료실 (권한 확장)
│
├─ [인도자] /coach/…   콘솔 9화면
└─ [운영자] /admin     본부 + 가입 승인(신설)
```

**전체 메뉴 시트(햄버거)** — 하단/상단 탭이 매일 쓰는 것이라면 시트는 나머지 전부와 계정이다.
참여자 시트에는 **회차 1~6을 직접 편다.** 링크를 못 받았거나 지난 회차를 열 때의 정문이며,
잠긴 회차도 감추지 않는다(여정의 전체 길이가 보여야 한다).

## 4. 진단 체계

### 4.1 현황 — 셋의 처지가 각각 다르다

| 진단 | 상태 | 1차에서 할 일 |
|---|---|---|
| 사전진단 | 운영 중 | 허브에 연결 |
| **사후진단** | 미착수 | 3차 |
| **가치 카드** | **전 슬라이스 완주**(ADR-121) | **개인 응시 경로 확장**(§4.3) |
| **그림자** | **SAIL — 운영 중 · 클코3 소관** | **연결만**(§4.5) |
| 사랑의 언어 | 미착수 | 4차 |

### 4.2 결과 열람 — 소속이 정한다 (확정)

| 응시자 | 결과를 보는 사람 |
|---|---|
| **차수 회원** | 본인 + 해당 기수 인도자 + 운영자 |
| **개인 회원**(소속 없음) | 본인만 |

기수 안에서 진단은 코칭의 재료다. 참여자는 세미나 등록으로 그 관계에 이미 동의했다.
상시 진단이라 해서 예외를 두지 않는다 — 가치와 그림자야말로 인도자가 알아야 할 것이다.

**두 규칙을 함께 둔다.**

> **① 동의가 아니라 고지다.** 진단 시작 화면에 한 줄 —
> "이 결과는 우리 기수 인도자와 함께 봅니다."
> 허락받을 일은 아니나 모른 채 쓰게 두지도 않는다. 특히 그림자 계열에서 이 한 줄의 유무가
> 응답의 정직함을 가른다. 나중에 알게 되면 다음 진단부터 방어적으로 쓴다.
>
> **② 응시 시점의 소속으로 판정한다.** 응답에 소속을 새긴다(불변). 기수 재직 중 실시한
> 진단은 그 기수 인도자에게 계속 보이고, 수료 후 개인 자격으로 실시한 것은 보이지 않는다.
> 코칭 관계가 끝났는데 열람만 남으면 안 된다.

인도자 열람은 자기 기수에 한정, 운영자는 전체. 본인 결과는 수료 후에도 본인에게 남는다.

### 4.3 가치 카드 — 개인 응시 경로 확장 (B′안)

**문제.** `value_assessments.cohort_id`가 `NOT NULL`이고 `UNIQUE(user_id, cohort_id)`다.
개인 회원은 `cohort_id`가 없으므로 응시할 수 없다. **개인 회원의 존재 이유가 상시 진단인데
그것이 차수에 매여 있으면 §5 회원 모델이 성립하지 않는다.**

**되돌리지 않는다. 연다.** 완주된 슬라이스는 한 줄도 버리지 않는다.

| 변경 | 내용 |
|---|---|
| 마이그레이션 | `cohort_id` → nullable. `UNIQUE`를 부분 유니크 인덱스 둘로 분리 — 차수분 `(user_id, cohort_id) WHERE cohort_id IS NOT NULL` · 개인분 `(user_id) WHERE cohort_id IS NULL`. **새 파일로**(불변식 15) |
| RPC | 기존 DEFINER 함수의 `cohort_id` 인자를 nullable 수용. 소속 검증 분기 추가 |
| 계약 | `cohortId: string \| null` 수용. 계약 변경이므로 **지휘부 승인 대상**(CLAUDE §1) — 본 문서가 그 승인이다 |
| 라우트 | `/my/values` 신설. `/my/cohorts/[id]/values` **유지** |
| 화면 | 컴포넌트 공유. 라우트 파일 둘이 `cohortId` 해석만 달리한다 |
| safeReturnTo | `/my/values` 추가 |

**지금이 가장 싼 순간이다.** `value_assessments` 행이 **0건**이라 데이터 이관이 없다.
2기가 9/20에 시작해 가치 카드를 쓰면 그날부터 이관 비용이 붙는다.

미결 2건(N-1 후보 상한 12 · P1 정리 하한 8)은 이 변경과 독립이며 `stages.ts` 한 곳에서 정한다.

### 4.4 사후진단 개방

운영자·인도자가 **기수 단위로 수동 개방**한다. `cohort_sessions` 게이팅과 같은 방식이다.
6회차 갈무리 완료를 자동 조건으로 삼지 않는다 — 종료일이 기수마다 유동적이고, 미완료
참여자가 남은 상태에서 자동 개방되면 여정이 끝나지 않은 사람에게 마감이 통보된다.

### 4.5 그림자 = SAIL — 통합이 아니라 연결

`shadow` 스키마에 테이블 10개(`journals`·`reminders`·`groups`·`consents`·`audit_log` 등)가
운영 중이다. **클코3 소관이며 본 작업공간에서 코드를 수정하지 않는다**(CLAUDE §4).

`plan.md` §1이 정한 길은 **코어 패키지 추출 이후의 이관**이다. 그 전까지 SAIL은 참고·차용의
원본으로만 본다. 따라서 1차에서 할 일은 하나다.

> **진단 허브에 그림자 진단을 항목으로 세우고 SAIL로 연결한다. 데이터·스키마는 건드리지 않는다.**

같은 Supabase 프로젝트를 공유하므로 **공유 테이블 변경은 반드시 지휘부 확인**을 거친다.
`instrument_id` 규약(`'futurenow'` · `'sail'`)이 격리의 축이다(ADR-14).

### 4.6 진단 화면의 안전

불변식 6·7·9·10·11을 그대로 적용한다. 구인명·STEP·강의 어휘를 문항에 노출하지 않고,
코드가 원형·감정을 판정하지 않으며, 참여자 경로에 경고색과 순위를 두지 않는다.
그림자 계열은 결과 문안이 낙인이 되기 쉬우므로 돌봄 안내를 말미에 둔다.

## 5. 회원 유형과 가입 경로

### 5.1 두 유형

| 유형 | 정의 | 진단 접근 | 결과 열람 | 자격 근거 |
|---|---|---|---|---|
| **차수 회원** | 기수 소속 | 여정 + 상시 | 본인 + 기수 인도자 + 운영자 | 세미나 등록 |
| **개인 회원** | 소속 없음 | 상시만 | 본인만 | 촉진자포럼 유료 가입 → 운영자 확인 |

수료자는 기수 종료와 함께 개인 회원으로 이동한다. 유형은 상태이지 등급이 아니다.

### 5.2 결제는 플랫폼 밖에 둔다 (확정)

유료 가입과 수납은 **촉진자포럼에서** 이루어진다. 플랫폼은 결과를 반영할 뿐이다.
결제 연동·PG 심사·환불 동선·전자상거래법 표시 의무가 전부 범위 밖으로 나간다.

> 다만 이용약관·개인정보처리방침은 유료 여부와 무관하게 필요하다. 진단 응답을 보관하기
> 때문이다. 기존 `user_consents`·`privacy_consents` 체계와의 관계는 별도 확인 사항이다.

### 5.3 가입 경로 두 갈래

| 경로 | 절차 | 도달 상태 |
|---|---|---|
| 세미나 신청 | `/join` 코드 입력 → **즉시 가입** | 차수 회원 |
| 일반 가입 | `/signup` → **운영자 승인** | 개인 회원 |

차수 코드는 그 자체가 승인이다. 정원(`cohort_seats_taken` · ADR-110)과 유효기간이 이미
문지기 역할을 하므로 사람 손을 한 번 더 거칠 이유가 없다.

### 5.4 회원 상태

| 상태 | 진단 응시 | 자기 결과 열람 | 전이 계기 |
|---|---|---|---|
| **승인 대기** | ✕ | **○** | 일반 가입 직후 |
| **개인 회원** | 상시만 | ○ | 운영자 승인 |
| **차수 회원** | 여정 + 상시 | ○ | 코드 가입 · 기수 배정 |
| **만료** | ✕ | ○ | 유효기간 종료 |
| **보류** | ✕ | **○** | 운영자 판단 |

> **정정(v2.1).** v2.0에서 대기·보류의 열람을 `—`로 적었다. 그것은 "가입 직후라 결과가 없다"는
> 서술이었으나 문언상 금지로 읽혔고, 실제로 기수 마감 시 수료자 전원이 자기 리포트를 잃는
> 절벽을 만들었다(클코1 S-1 보고 §2.4가 발견).
>
> **자기가 응시한 결과의 열람은 상태와 무관하게 언제나 본인에게 열린다.**
> 상태가 가르는 것은 **새 응시** 하나다. 이것이 §5.4 원문의 취지였다 —
> "승인은 문을 여는 열쇠가 아니라 도구를 쥐여 주는 절차다." 도구를 거두어도 만든 것은 남는다.

보류는 거절 통보를 대신한다. 사용자에게는 확인이 필요하다는 안내와 문의처만 보이고,
판단 사유는 내부 메모로만 남긴다.

> **역할(role)과 상태(membership)를 섞지 않는다.** `role`은 `user`·`coach`·`admin`이고
> 상태는 위 다섯이다. 기존 자가승격 방지(`20260629100002`)의 보호 범위를 흔들지 않으려면
> 상태를 별도 축으로 둔다. 상태 변경 RPC도 자기 자신에게는 걸리지 않아야 한다.

**정정(v2.1) — `enrollments`만으로는 차수 회원을 판정할 수 없다.**

v2.0은 "차수 회원 여부는 `enrollments`가 이미 알고 있다"고 썼다. 실측이 이를 뒤집었다.
휴지통 차수(ADR-84)·체험 차수(ADR-63)·test 차수가 모두 `status='active'`이므로
`EXISTS(enrollments)`로 판정하면 **휴지통에 버린 사람이 차수 회원이 되어 응시 자격을 얻는다.**
정확히 반대 결과다.

차수의 성격을 가르는 컬럼을 `cohorts`에 신설한다 — `kind IN ('seminar','general','trash')`.
이는 차수 소속의 이중 기록이 **아니다.** 차수의 성격은 차수의 사실이고 `cohorts`가 그
유일한 주인이다. §11-9가 금지한 것은 "이 사람이 차수 회원인가"를 복사하는 것이며, 그
사실의 주인은 여전히 `enrollments` 하나다.

부수 이득이 크다 — ADR-63 예약 차수 보호와 ADR-84 이동 대상 목록이 코드 문자열
(`GENERAL_CODE === 'JOINF'`) 대신 구조적 사실을 보게 된다. ADR-110이 세운 규칙
("이름이 아니라 역할로 거른다. 이름 목록은 낡는다")이 여기에도 그대로 걸린다.

**판정 우선순위 (확정)**

```
1. held        저장된 보류가 무조건 이긴다
2. cohort      EXISTS(enrollments ⋈ cohorts WHERE kind='seminar' AND status='active')
3. 저장된 상태  individual | expired | pending
4. pending     행이 없으면
```

`held`가 `cohort` 위인 이유 — 보류가 아래 있으면 차수 등록 한 번으로 운영자의 차단이
무력화된다. `expired`가 `cohort` 아래인 이유 — 유효기간은 개인 회원의 자격 근거이고
차수 회원의 근거는 세미나 등록이지 기간이 아니다.

**저장 enum에서 `cohort`를 뺀다.** 규칙으로 "저장하지 마라"를 두면 지켜지는지 매번 사람이
확인해야 하지만, enum에서 빼면 **저장할 경로 자체가 없다.** ADR-121이 `ValueCard`에서
`category`를 뺀 것과 같은 사고다.

### 5.5 승인의 실무 — 대조 키

운영자 화면에 이름과 이메일뿐이면 승인은 추측이 된다. 촉진자포럼 명단과 맞춰 볼 근거가
화면에 있어야 한다.

> **일반 가입 폼에서 포럼 가입 시 사용한 이름과 연락처를 함께 받는다. 선택이 아니라 필수다.**
> 가입 경위 한 줄(선택)을 더 받으면 애매한 건이 갈린다.

이 필드가 없으면 승인 큐는 며칠 만에 판단 불가로 쌓이고, 그때 필드를 추가해도 **이미 들어온
신청 건은 영원히 대조할 수 없다.**

연락처는 불변식 13에 걸린다 — `user_contacts` 격리 · `getPhone` 게이트. 승인 화면의 노출도
그 게이트를 지난다. 표시는 마스킹(`010-****-1234`)을 기본으로 한다.

### 5.6 승인 대기자가 보는 화면

**빈 화면은 고장으로 읽힌다.** `/pending`은 네 가지를 문장으로 말한다 — 지금 어느 단계인가,
무엇을 기다리는가, 대개 얼마나 걸리는가, 어디로 문의하는가. 그리고 지금도 할 수 있는 것
(소식·공개 자료실·세미나 신청)을 아래에 둔다. 막다른 골목이면 사람은 돌아오지 않는다.

딥링크도 같은 원칙으로 받는다. 대기자가 진단 경로에 닿아도 오류가 아니라 이 안내로 착지하고,
**승인 후 원래 자리로 돌아간다**(returnTo 보존).

### 5.7 승인 통지

승인 시 안내 메일 한 통. 없으면 사람이 다시 오지 않는다 — 승인은 조용히 일어나고
정작 당사자만 모른다.

### 5.8 판정은 한 함수로

진단 응시 가능 여부는 **단일 판정 함수**가 결정한다. 화면마다 조건을 흩뿌리면 언젠가 새는
곳이 생긴다. 화면에서 버튼을 감추는 것은 안전장치가 아니다 — **응시 시작 RPC에서 막는다.**
불변식 4·19의 연장이다(게이트는 200이 아니라 본문과 리다이렉트 목적지로 판정한다).

## 13. ADR-121 검증 수치 드리프트 — 판정

클코1이 스스로 신고한 건이다. ADR-121에 `vitest 661(643→661)`로 적혀 있으나 이는 리베이스
전 기준 커밋 `4e4d759` 위의 수치이고, 같은 표의 ADR-119는 815, ADR-120은 816이다.

**정정하되 덮어쓰지 않는다.**

- 원값 661을 지우지 말고 정정 주를 단다 — "리베이스 전 기준 `4e4d759` 위 661 → 리베이스 후 (실측값)"

근거 둘. **검증 수치는 기준 커밋과 짝일 때만 의미가 있다** — 661은 그 시점에서 참이었다.
지우면 왜 어긋났는지가 사라지고 다음에 같은 일이 생겼을 때 또 처음부터 판단한다.
그리고 **결론이 맞아도 어긋난 근거는 기록하고 정정한다**(ADR-94의 정신).
